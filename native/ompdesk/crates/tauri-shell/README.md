# Tauri system-WebView host

`ompdesk-tauri-shell` pins Tauri 2.12.6. WKWebView on macOS and WebView2 on Windows host the existing React page. The crate imports the existing shell's authenticated host wire, Node child supervisor and logger by path. `shell_core` is linked with default features disabled. This crate does not depend on CEF.

The runtime finds the actual Node main from `OMPDESK_APP_DIR` or the packaged `resources/app` layout. `OMPDESK_APP_ENTRY` can select an existing main bundle. Its sibling `renderer/index.html` and `preload/tauri.js` must exist. Missing assets are startup errors, not a fallback UI. An unpackaged run with `ELECTRON_RENDERER_URL` (`bun run dev`, `scripts/dev.ts`) takes the page from that Vite dev server instead: it must be a loopback `http` origin with a port, and it becomes Tauri's dev URL so the page's IPC is accepted. A packaged app ignores the variable.

Node assigns window and webContents IDs. The registry never reuses them. Tauri labels bind native IPC callers to those IDs. App pages can load only the app custom origin (and the dev server's origin above). New-window requests and remote navigation are denied. The app document has no remote Tauri capabilities or child frames. Navigation advances a document generation and rejects late invoke responses. Generation numbers travel in the preload's captured closure, not in React's API. Native-requested pushes also check that generation before page-side execution. The ready transition and retained-push drain run in one UI-thread task.

`createOmpApi` uses the native `omp_ipc` command. Binary values retain the existing `$bin` representation. Node pushes queue until the preload is ready. Queue overflow produces the renderer's stream-reset signal. Native drag interception is disabled so HTML5 file drops reach the existing composer. `fs.pathForFile` returns an empty string for DOM `File` objects; picker, drop and clipboard attachments use the composer's existing text or upload-bytes fallback. No filename-to-path mapping is retained. Node-requested JavaScript runs through the engine's own evaluation, outside the page's CSP (`src/evaluate.rs`): WebView2's DevTools `Runtime.evaluate` on Windows, WKWebView's `callAsyncJavaScript` on macOS; both await a Promise. The page's `script-src` carries no `unsafe-eval`, and no page-side evaluator exists.

`runtime:log-path` and `runtime:log-tail` run in the shell after the app page and generation checks. Paired pages need the existing `workspace` grant and reach the same reader through main. The tail reads at most 256 KiB of the current regular log without following a linked log or logs directory (empty result). A positive fractional limit below 1 selects one line; no request returns more than 50. `log:snapshot` still reads main's live log sequence.

The host implements app initialization, authenticated Node startup, app exit receipt, relaunch, ordinary app windows, native geometry/focus/visibility changes, app-page load, JavaScript evaluation, zoom and native Web Inspector. State updates precede their corresponding events. Exit keeps the host writer and Node stdin alive while Node receives its receipt, then joins the Node child and releases the single-instance listener before relaunch. Fatal Node loss exits instead of asking the disconnected backend to quit. Windows uses Tauri's local `http://app.localhost` custom-protocol origin. Saved outer-window sizes account for measured native frame insets.

The host watches each app window's page (`src/page_watch`). Once a second, on the UI thread, it has the engine evaluate an empty script in every app page that is due. A page is due 5 s after its last probe was sent, never while a probe is unanswered, and during a load only once 30 s passed. The probe is WKWebView's `evaluateJavaScript` or WebView2's `ExecuteScript`, so it uses neither the page's IPC nor a resource load. A probe unanswered for 20 s sends `unresponsive` once for the page and its window, and its late answer sends `responsive`. One turn counts 2 s at most, so a sleeping computer or a held UI thread does not count against a page. A page whose Web Inspector is open is neither asked nor timed (macOS only: wry cannot tell on Windows). `wc.op forcefullyCrashRenderer` ends the page's content process. On macOS that is `-[WKWebView _killWebContentProcessAndResetState]`. `_killWebContentProcess` is not usable: on macOS 27.2.1 it left the process running, called no delegate, and the view never loaded again (measured 19 Nov 2026). On Windows the host calls `TerminateProcess` on the renderer that `ICoreWebView2Environment13::GetProcessExtendedInfos` lists for the page's main frame: learned right after the page answered a probe, checked against the live renderers (`GetProcessInfos`), else looked up at the kill. DevTools `Page.crash` ended nothing on the Windows runner, warm session or cold (19 Nov 2026). A content process that ended sends `render-process-gone`, with reason `killed` after that op and `crashed` otherwise (Windows adds `exitCode`). The page is then not ready: its document generation advances, pushes queue until the next document's `ready`, and Node loads the page again. Setting Tauri's `on_web_content_process_terminate` hook replaces wry's own reload of the view. On Windows `ProcessFailed` also reports WebView2's own `RenderProcessUnresponsive` as `unresponsive`.

On macOS the page's Tauri IPC goes through `window.ipc.postMessage` (`src/ipc_post_message.js`, installed with `tauri::Builder::invoke_system`), not Tauri's stock `fetch` to `ipc://localhost`. The script posts the same envelope as the postMessage fallback of Tauri's `ipc-protocol.js`, and the answer comes back through Tauri's callback. WebKit forwards the content process's log lines to the host over one stream, and a page whose main thread waited on that stream froze for hours (19 Nov 2026). Measured that day on macOS 27.2.1 with a WKWebView and a custom-scheme handler: 500 `fetch` calls added about 3 000 forwarded lines (`SubResourceLoader`, `WebURLSchemeTaskProxy`, `ResourceLoader`, `WebLoaderStrategy`), and 500 script messages added none per message. `OMPDESK_TAURI_IPC_FETCH=1` keeps the stock transport for comparison. Windows keeps the stock transport.

On Windows, `win.state.focused` and window `focus`/`blur` follow actual native activation (`GetActiveWindow`, `WM_ACTIVATE`), not WebView2's `GotFocus`/`LostFocus`. Hidden windows are created with both the window and WebView initially unfocused, which only marks tao's creation-time show. tao 0.37.2 shows a later window with `ShowWindow(SW_SHOW)`, which activates, and tracks visibility only in its own flag, which its other flag changes (maximize, minimize, `setFocusable`) read. So `showInactive`, and `show` on a window that cannot take focus, show the window with `SW_SHOWNOACTIVATE`, then call tao's `show()` to set its flag; while that call runs, a `WM_STYLECHANGING` handler keeps the window's `WS_VISIBLE`, so tao's `SW_SHOW` finds a visible window. That a visible window ignores `SW_SHOW` is taken from Wine and ReactOS, not from Microsoft's documentation. Focusability stays tao's flag, so it survives later flag changes. Native activation and WebView-focus diagnostics are retained in the shell log; the Windows interaction gate must verify these effects, in particular `active:false` in the `window.inactive` line after tao's `show()`.

The official embedded WebDriver (`tauri-plugin-wdio-webdriver`) is a test build only: the cargo feature `test-automation` (`bun scripts/build-tauri.ts --test-automation`, recorded as `features` in `ompdesk-tauri.build.json`) compiles it, and a default or released build contains neither the plugin nor `automation.rs`. In a test build it is installed only with `OMP_GUI_TEST_NODE_INSPECT=1`, an existing `OMP_GUI_TEST_USER_DATA_DIR` equal to this launch's canonical profile, and an explicit unprivileged `OMP_GUI_TEST_WEBDRIVER_PORT`. `scripts/tauri-native-smoke.ts` drives the actual system WebView through W3C commands, on the packaged release app with its host swapped for a test build; `scripts/tauri-release-automation-check.ts` proves the shipped host holds no plugin string and opens no port even with those variables set. The automatic-update fixture reads the migrated profile through the same transport, then writes and reopens it; the old Electron producer continues to use its original CDP endpoint. These consumers still require an actual built-host run.

## Incomplete runtime paths

This source is not a released application or a claim of parity. A real isolated-profile run with the actual Node bundle, handler invoke, push, second-window close and exit receipt is still required. A local cold Tauri build is intentionally not run by this worker. Main owns the hosted native compile and final artifact run.

The app WebView is not a CDP target. Preview uses the separate `shell-preview` Chromium driver. Native window, webContents and view IDs still come from Node and share one nonreused registry. Each Preview entry holds the actual Page and its CDP sessions; phone frames, capture, PDF, input, native painting and accessibility address that Page, not another browser target.

The native Preview surface adapts the same Page's PNG screencast, frame ACKs, OS input, UTF-16 composition, backend-node accessibility snapshots and DOM-range text geometry. This is a native raster surface, not an embedded Chromium view or a claim of WebContentsView parity. Actual macOS and Windows interaction, audio, clipboard/drag behavior and accessibility remain release gates until observed on the packaged app.
Paint placement, trusted visual-viewport input and DOM text/AX geometry share `FrameGeometry`, derived from the metadata and PNG dimensions of the last successfully presented frame, not the latest submitted frame. It preserves top inset, pinch scale, scroll origin and native view-DIP size; native interaction at non-identity transforms still needs the hosted artifact gate.

Preview titles travel through the existing isolated-world binding, accepted only from a live context of the primary root frame. Browser target metadata is not a title producer: the Windows consumer run did not deliver the required page titles through it. Page setup toggles `Runtime.disable`/`Runtime.enable` to replay the page's contexts, and `Runtime.disable` drops every binding the session added ([V8 `V8RuntimeAgentImpl::disable`](https://chromium.googlesource.com/v8/v8/+/refs/heads/main/src/inspector/v8-runtime-agent-impl.cc) removes the context and global bindings), so setup adds the binding again after the enable; without it no title, text or layout notice of a page reached the owner (Windows: a page that set `w=459` after load stayed `w=390` in the panel). A denied document request fails with `net::ERR_ABORTED`, so Chromium retains the original document instead of committing a blocked-navigation error page; subresources still fail as blocked by client. A download is refused by the context's download behavior; the page's own `Page.downloadWillBegin` becomes `session.download`, which the Electron shim serves as that session's `will-download` with the page. Hosted browser and panel scenarios are the runtime verdict for these paths.

Test-automation builds log title binding admission, named-world lifetime, title publication, and load-time title reads. Title values use fingerprints rather than raw text; these diagnostics are absent from production builds. `preview.event.slow` reports an event handler only after it completes, so its absence does not prove that the event loop was unblocked.

Preview submits `Page.navigate` in the host FIFO but waits for its reply outside that queue. A server that sends headers without a body must not hold Stop or the next navigation behind its unfinished reply. The same rule applies to raw CDP navigation on its actual debugger session. Page ownership and a load sequence prevent a replaced load's late failure from changing the current page. `preview.navigation.queued`, `start`, `stop`, `reply`, `failure`, `deduplicated`, and `superseded` record the producer, generation, loading state, and error code without recording page URLs. Hosted smoke and agent navigation remain the runtime gates.

Offscreen Preview keeps CSS layout, emulated DPR, and compositor view size separate. `Page::resize_framed` sizes the view for the requested stream pixels and records the emulation scale used for spatial CDP input. Native Preview surfaces keep their existing resize path. Until a surface of the resized view activates, Viz letterboxes the previous surface into the new capture size and the frame is cut to it (Windows: 780×520 from a 240×160 view, 647×1400 from the 390×844 default); the host drops an offscreen frame whose size is not the window's frame pixels (`frames::pictures_window`, logged as `preview.frame.stale`) and streams the next one. The real-browser scenario asserts that a raw 780×1400 frame follows those transition frames, a 390×700 CSS layout at DPR 2, trusted corner clicks, and wheel position and magnitude; `e2e/preview-stream.e2e.ts` asserts the phone's first frame is 780×1400 on Windows.

Framed resize requests the browser view size before awaiting the renderer's metrics update. Chromium's `Emulation.setVisibleSize` response is browser-side, not a rendered-frame receipt ([Chromium 153 implementation](https://chromium.googlesource.com/chromium/src/+/refs/tags/153.0.8010.12/content/browser/devtools/protocol/emulation_handler.cc?format=TEXT)). The existing strict first-frame dimension assertion remains the hosted gate; a metrics acknowledgement alone does not prove fresh compositor pixels.

AX default actions verify the original focused backend immediately before trusted input, but a later asynchronous focus change can still occur between those two CDP commands because CDP exposes no backend-bound native DoDefault action.

Canonical session policy, cookies and streamed protocols remain in `sessions`. The private HTTP gateway reserves a partition listener before the actual BrowserContext is created. Mapping requires the canonical context's successfully applied explicit proxy bypass and live reservation. System proxy mode is preserved; it does not silently become DIRECT. Native Windows app-media requests redirect to a separate capability-bound loopback stream; only its exact allocated origin and the registered media origin are added to image/media CSP, never `connect-src`.

Visual pages keep the same canonical Session identity and reserved gateway transport, but each page owns a separate actual Chromium BrowserContext. The cookie boundary therefore covers `document.cookie`, CookieStore, and workers, rather than only filtering HTTP headers or hiding a JavaScript property. Ordinary web pages keep their shared partition context. Page close disposes its visual context before releasing the native entry; partition storage cleanup includes all owned visual contexts. The cross-visual document-cookie and CookieStore browser probes remain the runtime gate for this isolation.

A Preview page's own `alert`, `confirm`, `prompt` and `beforeunload` are answered over CDP (`src/preview/dialogs.rs`): Chromium reports `Page.javascriptDialogOpening` on the session that owns the dialog and keeps the page blocked; the owner sends the host wire's `ipc.sendSync` request (channel `preview-web:dialog`, whose Node handler is the streamed page's viewer sheet, `src/main/web/preview-dialog.ts`) and answers with `Page.handleJavaScriptDialog` on that session, directly on the transport and never on the Preview service queue. `Page.javascriptDialogClosed`, a replacing dialog and the page's end withdraw the request (`{cancel}`, Node's `event.signal`); `beforeunload` is accepted unasked; a failed, lost or 75 s unanswered request dismisses the dialog. A page that no viewer streams is dismissed by Node, not shown. No preload or injected function is involved.

With the `test-automation` feature, `automation::install` registers Main's native WebDriver only with the explicit Node test inspector, matching canonical test profile and requested unprivileged port; without a requested port it opens no driver listener. Without the feature the module is not compiled. `OMP_GUI_TEST_SHELL_FAIL_START=1` also requires that matching nondefault test profile; it fails after native initialization and before Node/page startup with phase `native-initialized-before-node`. macOS requires 14 or newer.

Profile import uses a private durable journal and an app-origin bootstrap before React reads localStorage. Missing destination keys are written and read back; existing destination values are retained. Source data and failed/partial imports remain available for retry. Automatic update/relaunch packaging, native interaction, original-profile upgrade/rollback and application-level parity still need Main's artifact gates. Unknown operations return `unsupported`, not simulated Chromium facts. The resource tree must be immutable while the app runs; canonical-path checking does not protect against a hostile local writer replacing files during an open.

The bootstrap page's progress is watched per app page (`src/migrate_watch.rs`): each step (`navigate`, `served`, `loading`, `loaded`, `read`, `handover`, then `app` when the app page starts) is a `profile.migrate` line in `tauri-shell.jsonl`, a refused `profileRead`/`profileAck` is `profile.migrate.refused`, and the page's own error `profile.migrate.failed`. A step with no next one in 10 s is `profile.migrate.stalled` and loads the page again; after three tries `profile.migrate.gave_up` shows the window with the reason and a Retry, and tells Node (`preload-error`). Windows e2e saw the page's request sent and never answered (nightly 44612826698, rc 44581968887). Test builds leave the first n requests for the page unanswered with `OMP_GUI_TEST_SHELL_STALL_MIGRATE=<n>` (`e2e/profile-migrate-stall.e2e.ts`).
