# Correspondence: session-listing

Sync commit: set by `verify-all.ts formal --only session-listing --stamp` (the same value as `syncCommit` of `session-listing` in `formal/manifest.json`; the manifest wins when they differ).

The `@code path:lines` tags in `tla/SessionListing.tla` are the machine-checked half of this map. This table records what each tag abstracts and the assumptions the model relies on.

How the code is laid out, so the table reads: the host numbers its list of sessions once (`LocalHostServices.#deviceList`, a `SessionListShare`: `epoch.n`) and sends every connected device what changed (`{base, version, set, remove}`, `SESSIONS_CHANGED`); a paired computer keeps one copy per host (`HostSessionList`) and applies a change of the version it holds; every window of that computer keeps its own numbered copy of that (the global feed in `session-list.ts`) and does the same. Whoever holds no copy or missed a version reads the whole list once.

## Assumptions

- A1: the host's messages reach a device computer in the order they were sent (`LinkMode = "fifo"`): one encrypted socket whose frames carry a counter and are refused out of order (`remote/codec.rs` `Sealer::seal`, `Opener::open`), and the host sends the reply in the continuation of the call that took it. In order is not the same as "the reply's read continues before the next frame is handled": the core drains the link in order; in main `FrameReader.push` delivers every complete frame of a stdout chunk in one synchronous loop and a read's `await` continues only after it, so a change sent behind the reply can apply to the copy before the read resumes (F7, found 30 Oct 2026; F5 had assumed only a reordering link could do this, which was wrong). `HostReplyArrive`/`HostReplyResume` model it and `HostSessionList.#read` guards it by version. `LinkMode = "gap"` (a reply sent after a later event) is a run that passes with the guard (matrix run `link-reorder-is-handled`; without the guard TLC finds the older read overwriting the newer delta, as in F5).
- A2: a window gets events in order but a reply at any position (`IpcMode = "free"`): the code sends them on two IPC paths (`webContents.send`, the invoke reply) and enforces no order between them.
- A3: the host's read (`sessions.list`, or the debounce) is one block that samples what the index lists and what tabs hold when it ends; the list it awaits (`sessionIndex.list`) includes every change notified before the read began. Every global `sessions.list` calls `stale()` first and waits for a read that starts after the call, so an asker sees at least everything that happened before its call. The model starts the host's debounce at the index change. The implementation calls `sessionsChanged()` from the index share's `onListChange`: when the share has a copy, `SessionListShare.changed` reads before publishing the delta. The model does not check the timing of that intermediate read.
- A4: the generation counters of `SessionListShare` are two booleans: `dstale` (a `stale()` the copy has not served) and a read's `clean`/`dirty`. A window has at most one ask at its computer's copy (`OneAsk`: its `inFlight` makes the next one queue), so an ask that must wait for a later read than the one under way does not arise. This assumption does not cover the successful-delete path below.
- A5: a host's numbers are one epoch: a host that restarts numbers from another epoch, no old copy matches it, so a change of the new epoch is a missed version (the same branch as a lost event) and the link came back anyway (`LinkUp` marks the copy stale). Epochs are not modeled.
- A6: a host's `emit` does not fail: `emitSafely` drops an event over the frame cap (16 MiB), which for a delta would mean the whole list is over it too and the read fails.
- A7: every change of what a host tab holds calls `listingChanged()` in the block that makes it (the core pool's `onSessionFilesChanged` covers each window tab's take and let-go (`register_session_file_of`, `unregister_session_file_of`, in that order: file and owner map first, then the ask); `LocalHostServices` covers its own tabs). With that, the single shared snapshot always equals the listing at the last announce or read, so any change from what any device last read is announced; a per-device snapshot is not needed.
- A8: a row is its journal state, `heldOnHost` and `openedBySession`; the other fields (`status`, `messageCount`, titles) are not modeled. The row a window shows is the content of the last answer or applied change (`reconcile` keeps a row object only when `sameRow`).
- A9: one window feed per paired computer and host. Several windows share the computer's copy and each has its own numbered copy: they are separate instances of the same code. The windows of the host's own computer read `SessionIndex`'s copy over IPC with the same feed code; that source has no link and no tabs' overlay and is not modeled apart.
- A10: the feed stays held for the entire model run. The model excludes the generation changes on release and on successful deletion. The latter also affects a feed that stays held.
- A11 (H2, Nov 2026, hub timing; `native/ompdesk/crates/core/src/hub/mod.rs` header): a handler's mutation and its `listingChanged()` stay one synchronous block. The pool is a hub instance: main feeds each sidecar event to it at the moment the sidecar emits it (`listen.rs` `feed`) and calls its methods, each a blocking call; a call is one job that runs to its end on the hub's thread, and main's synchronous questions (`onSessionFilesChanged`, `onRunningChange`, `onWindowTabsChanged`) are answered inside it while the method is suspended. So `register_session_file_of` sets the file, asks `onRunningChange` when the tab runs or waits, sets the owner map, and asks `onSessionFilesChanged` (-> `listingChanged()`) with no other main macrotask in between; a nested read of `windowSessionFiles()` from those handlers sees the new file and the owner map in the order TypeScript had (`unregister_session_file_of`: owner dropped and file cleared before the ask). Not modelled and not changed: the hub's microtasks of such a call (woken tasks of other instances, e.g. a resume continuation) run after the job, before main's next macrotask.

## Delete during a read (F6)

F6 describes the feed before `ee5efb0a7`. In `PostFeed`, deleting a row changes `fshow` but preserves the numbered copy and any outstanding read. `RefreshFx` queues a refresh behind that read. A late `FeedReply` can show the deleted row again.

The current feed calls `forgetSession` for both scopes after a successful delete. It increments `generation`, clears the copy, timers and in-flight state, removes the row and starts a fresh read for each held feed. `refresh` ignores the old generation's success, failure and `finally`. The earlier request may still be outstanding when the new one starts. The model neither rejects the old answer nor represents the overlapping requests. `OneAsk` and F6 therefore do not establish the current feed's behavior across a delete. F6 is a historical observation, not a current reproduction. This mismatch predates phase 2.

## Granularity

One action = one event handler, timer or microtask chain. Merged steps: a handler's mutation and its `listingChanged()` call (one synchronous block); a read's `#listing()`, snapshot, publish and row building; the host's reply with its delta (the delta leaves first); the reply's delivery with `accept` and `.finally`; `HostReplyResume`'s `finally` branch, its `queueMicrotask(stale)` and the publish (microtasks of one macrotask). The `await sessionIndex.list` inside `sessions.list` is the gap between a device's request and `HostRequest`; the device computer's read of the host spans request, reply and every event that arrives between. Split steps: the reply's arrival and the read's continuation (`HostReplyArrive`, `HostReplyResume`, F7): later frames of the same stdout chunk run between them in `FrameReader.push` and nothing else on that computer does (a timer, an IPC message, the socket's close are other tasks), which the model states by `Busy` (every action but `HostEvent` of that computer and the continuation is disabled while a reply waits in `rp`). The host's own steps are not blocked in reality but commute with the computer's synchronous block, so they are not interleaved inside it. The queue bound `MaxCh` is checked at the arrival; the events of the drain and the continuation may take the computer-to-window queue past it (TypeOK allows `MaxCh + 5`).
