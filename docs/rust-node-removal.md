# Removing the packaged Node main (phase F)

Plan of 24 Nov 2026 for the last step of `.omp/rules/native-rust.md` › Order 4: the packaged Tauri app starts, serves and quits with no Node process on macOS and Windows. Counts are from `docs/rust-inventory/*.tsv` at d9c634351; the slices change as rows land.

**Recommendation:** put the channel router at Tauri’s existing `omp_ipc` boundary. Move one **state owner and its callers** at a time, not one TypeScript file at a time. Remove `node::spawn` last. Removing it earlier would disable not just unported IPC, but also startup, second-instance delivery and quit handling.

## 1. Scope and slices

The eight inventory files contain **372 `port` or `mixed` rows**: `root` 144, `services` 84, `host-imports` 65, `remote` 23, `web` 19, `helpers` 17, `shell` 13, `preview` 7. They are **not 372 `src/**` files or 372 Node implementations**: some rows describe stock Bun code or page-shared logic. `scripts/rust-runtime-scope.ts:74–110` selects rows by status, not Node reachability. Conversely, a `native-client` row is excluded from 372 but still needs a non-Node caller before exit. See `docs/rust-remaining-units.md:22–28`.

The reason letters below quote the actual §1.3 rule, `docs/rust-remaining-units.md:77–81`: **a** “every caller that stays TypeScript already awaits what it calls”; **b** “it does I/O of its own”; **c** “no staying code reads its in-memory state in the same tick”; **d** “moving it duplicates no logic of stock omp, of the page or of `src/shared`.” These are tests for whether a unit can move **alone**, not reasons to retain the desktop Node process.

## 2. The cutover seam

1. **Desktop ingress today.** `src/shared/omp-api.ts:186–198` defines the transport and constructs the page API. `src/preload/tauri.ts:57,128–155,323` calls Tauri `omp_ipc`, unwraps invoke results, serializes sends and installs `createOmpApi(transport)`. Preserve that page API and browser preload.
2. **Rust already has a working interception point.** `native/ompdesk/crates/tauri-shell/src/main.rs:1459–1498` checks the actual WebView URL, registered page identity, document generation and profile-migration gate. At `:1589–1652`, it validates channel/args, handles native feedback reads, otherwise sends `ipc.send` or waits for `ipc.invoke` over the host connection, then rechecks the document. Windows media translation sits on this path. The Tauri command is installed at `:1883`.
3. **Node registration and other callers.** `src/main/shell-host/electron/ipc-main.ts:73–93` receives invoke/send and the separate Preview `sendSync`. `src/main/web/ipc-registry.ts:186–211` exposes registrations both to the Electron-shaped caller and to non-Electron callers; `src/main/web/ws-router.ts:547` calls the registry directly. Some channels already go **Node → Rust**: `src/main/index.ts:924`, `src/main/web/ipc-registry.ts:104–120,147–181`. That path hands policy to a restarted core and queues waiting calls in order. A desktop-only routing change would leave paired clients behind.
4. **Proposed dispatch.** After ingress checks, select by **`(direction, channel)`** from one native ownership table. Registered → native handler; explicitly unmigrated → existing Node handler. Unknown, wrong-direction, denied or failed native calls **never** fall back to Node. In particular, do not retry a mutation on Node after an ambiguous native result. Keep the same envelope, binary handling, deadlines, caller identity and document-generation recheck. Start with the existing feedback reads as the parity case.
5. **Paired calls and events.** For a migrated channel, the still-running Node web adapter must delegate to that same native handler, retaining the authenticated connection identity. Once F lands, the Rust edge dispatches directly. Preserve the distinctions in `src/main/web/ipc-policy.ts:103–119`: pass, web-specific implementation, pairing-admin boundary, transformed/client-only push. Reuse the existing targeted delivery path (`main.rs:1309–1327`, `src/preload/tauri.ts:128–131`); never broadcast a private response as a shortcut. Preview’s cancellable dialog reply is a separate contract, not an ordinary fire-and-forget send.
6. **Each landing.** Move production callers, state, registrations and event producers together; remove that Node implementation in the same change. Reuse the existing parity cases for desktop, paired and core-restart paths. Add a registry check rejecting duplicate ownership and identifying every unserved channel. For ordering-sensitive work, make the **outer** call async but keep check + reservation + effect admission on one owner before yielding. A fresh RPC between those steps does not preserve same-tick semantics.

### Landed: the router (H foundation, first step)

- **Table.** `native/ompdesk/crates/tauri-shell/src/ipc_router.json` lists the channels the shell serves, by direction; `ipc_router.rs` maps each to its handler. Main hands over the rest of `IPC_POLICY` with `ipc.routes` before its first window (`IpcRegistry.routeShell`, `src/main/index.ts`). `omp_ipc` then has three outcomes: native, main, or refused (unknown, wrong direction, before the hand-over). A native call is answered by the shell whatever its handler returns, so no call is ever tried on both owners.
- **Main's callers.** Main learns the native channels from `hello`'s `nativeIpc` and registers them only in its web table, never on `ipcMain`. A paired page (after `ws-router.ts`' permission and quota checks) and an agent's `ompdesk_app` reach the same handler through `ipc.call` with the caller's lane key (`w<wcId>`, `c<connId>`). `handle`/`on` refuse a native channel, and `routeShell` refuses one main already serves.
- **Native today:** `runtime:log-path`, `runtime:log-tail` (the parity case; their Node relay was deleted) and `updater:version` (deleted from `updater.ts`). Then the page's file dialogs, `system:save-dialog`, `system:open-dialog` and `system:save-image` (`page_dialogs.rs`, over the page's window through the dialog presenter main's `dialog.*` requests use), and `session:consume-pending` (a constant `null` on the desktop).
- **Blocked: `system:open-external`.** It needs no Node state, but e2e specs capture opened URLs by replacing Node's `shell.openExternal` (`desktop-tabs`, `first-run-walk`, `github-*`, `mobile-web`, `oauth-login`, `panels-flows`, `real-core`, `remote-devices`, `sign-in-relay`); every URL that came through the page channel would then reach a real browser on the runner. It moves together with a shell-level capture those specs read, so no test opens a real browser.
- **Meter.** `src/main/web/ipc-policy.test.ts` gives every `invoke`/`send` channel exactly one owner and prints how many main still serves.
- **Moving a channel:** add its handler and its line in `ipc_router.json`, delete main's registration, keep `IPC_POLICY`'s entry (the web permission is still checked there until F). A `send` moves only with its order against main's sends settled, since the page's sends reach main in order and a native one overtakes them. A channel whose web answer `ws-router.ts` reshapes (`#shape`) keeps that shaping in main until F.

### Design: the shell owns the core (next H step, not built yet)

Today Node main owns `ompdesk-core`: `CoreProcess` (`src/main/core/process.ts`) spawns it on the first request, holds its stdio, numbers each start (`generation`) and puts the hub's address and token in its environment. It also restarts it and tells 26 `CORE_EXITED` listeners when one ends. The shell cannot reach the core, so every core-owned page channel goes page → shell → Node → core (`IpcRegistry.routeCore`, `crates/core/src/ipc`). Target: the shell owns the process, Node becomes one client of it, and core-owned page channels go shell → core.

**1. Who owns what.**

| Concern | Today (Node) | After (shell, `crates/tauri-shell/src/core_owner.rs`) |
|---|---|---|
| Spawn | lazily on the first request; detached; POSIX process group; Windows job object (the core joins its own) | at shell start, before Node; same flags; the shell holds stdin/stdout/stderr |
| Identity | `generation` = start count; per start a fresh hub address and token (`hubPlace`); `OMPDESK_LEFT_BEHIND` | the same, made by the shell; the core's env also gets a **client endpoint** and token (below) |
| Ends with | Node's stdin pipe | the shell's stdin pipe: the core outlives a Node crash only as long as the shell does, which already exits on Node loss (`node_gone`) |
| Restart | next request after an exit; 3 exits before any answer → 30 s rest | right after an exit unless resting; the same budget; a demand during the rest is refused `core_unavailable` |
| Loss report | `report("abandoned"/"ended"/"rest")` → `gui-runtime.jsonl` (`core-loss`) | the shell logs to `tauri-shell.jsonl` and pushes `core.loss {step, details}` to Node, which keeps writing the same `gui-runtime` line |
| Settling a dead core | callers are rejected only once its process group is gone (POSIX `groupGone`, 3 s) | the shell waits for the group the same way before it announces `core.exited` |
| Abandon on a missed hub deadline | `abandon(reason)` kills the tree | Node asks `core.abandon {generation, reason}`; the shell kills only that generation |
| Quit | `shutdownCore(force)`: stdin closes, kill after 5 s | Node asks `core.shutdown {force: false}` inside the quit chain's `settle` effect (H lifecycle, `quit_chain.rs`), where `shutdownCore()` runs now: after teardown, after the omps and the schedules journal are done, and so after an installer's receipt. A failed `core.shutdown` makes `settle` return 1, the exit code. The shell never stops the core on its own when `settle` answers, because a failed `settle` is retried and must reach the core again. The shell's exit closes the core's stdin as the backstop. `endMain` (a lost shell connection) stops calling `shutdownCore(true)`: the shell's exit already ends the core. The hang watchdog's and console poll's `core().pid` come from `core.started` |

**2. Node as a client: its own connection, not a relay.** The core gains a second listener beside the hub: `OMPDESK_CLIENTS` + `OMPDESK_CLIENTS_TOKEN`, accepted the way `hub/listen.rs` accepts (`crates/core/src/clients.rs`). Each connection runs the existing `server::serve_as` (generic over `AsyncRead`/`AsyncWrite`), and a connection's first line is `{token, client: "main" | "shell"}`. Node gets `{generation, clients, token, hub, hubToken}` in `hello`'s facts and in a `core.started` event at each restart. `CoreProcess` keeps its API (`call`, `push`, `on`, `generation`, `hubEndpoint`, `abandon`) and its 91 callers. Only its transport changes, from a child's pipes to that socket. The shell carries none of Node's frames, so transcript-sized answers and their `bin` tails take no extra hop.
- `hubEndpoint()` stays synchronous: it returns the endpoint of the latest `core.started`. With no core running (a rest, or a restart not yet announced) it throws `core_unavailable`, as a rest does today, and `hub.ts` treats that as a lost hub, as it does now. **Difference:** a core that ended is restarted by the shell, never by a synchronous call of Node's; the first hub call in that window fails once instead of spawning.
- `CORE_EXITED` listeners fire on `core.exited {generation}`, which the shell sends only once the group is gone. They then re-seed on the next `core.started`, as they re-seed on the next spawn today. `call(…, {generation})` and `push(…, generation)` keep fencing by that number.
- Vitest runs against the real binary with no shell. There, `CoreProcess` spawns the core itself and connects over its pipes: a bare child for tests only, with no restart budget, rest or report. Those rules exist once, in Rust, and `process.test.ts`'s restart and rest cases move to `core_owner`'s tests in the same change.

**3. Events fan-out.** A core event goes to the connection whose request started it (`Events` is per request). A watch Node opened reports to Node, one the shell opened to the shell; nothing is broadcast. The one process-wide sink, `disk::saves::attach` (`store.saveFailed`/`store.saved`), stays on main's connection until its consumer moves: `serve_as(…, main)` attaches only a `client: "main"` connection (or stdio while main still owns it), never the shell's. The core's questions to main (`web.ask`, `remote.ask`, `upkeep.ask` and the rest) are events on Node's connection, answered by pushes on the same connection, as today.

**4. Page channels the core serves.** `ipc_router` gains a third route, `Core`. Node hands the shell `IPC_POLICY` once, inside `ipc.routes` (`{invoke, send, policy}`). On each core start the shell sends `ipc.start {policy}` first, holds core page calls until it answers, and routes the channels it returns to the core. Node's `routeCore` and its held-call queue are deleted.
- **One writer per lane.** Every `ipc.call` reaches the core from the shell: a desktop page's calls with key `w<wcId>`, and a paired page's or an agent's calls delegated by Node through the shell's `ipc.call` (as native channels are now) with `c<connId>` or `w<id>`. The core's lane order is then the order of one stream again. Node never calls `ipc.call` on its own connection.
- **Order across owners is what it is today.** The preload serializes a page's sends, each waiting for its acknowledgment, and the shell acknowledges a send once it is queued for its owner (Node's socket, the core's stdin, or a native handler started). Sends therefore start in page order whoever owns them. No order is promised between two invokes (each `omp_ipc` is its own task today too), nor between the completions of handlers on different owners. A `send` channel moves to the core only with its ordering peers, as for native channels.
- A core page call that finds no core, or a core that ends while the call waits, fails `core_exited` to the page. It is never retried on Node, and never on the next core, since it may have run.

**5. Core loss, end to end.** The core exits. The shell marks the generation gone, holds new core page calls, and waits for the process group. It then sends `core.exited {generation}` to Node, fails its waiting core calls, and restarts unless resting. On the new core it sends `ipc.start`, sends `core.started`, and releases the held calls. Node's `CoreProcess` sees its socket close but fails Node's own waiters only on `core.exited`: a repository lock's next holder must not start beside a git of the dead core, which is why `groupGone` exists today. It then runs the `CORE_EXITED` listeners and reconnects on `core.started`. The web edge, the remote link and the stores reopen as today. `web.answer {generation}` and `push(…, generation)` still drop answers meant for a dead core.

**6. Order of landing.** (a) Core side: the client listener and `attach` by client kind, inert until used. (b) Shell `core_owner` with its spawn, restart, rest, group wait and reports, plus Node's `CoreProcess` client mode, with `process.test.ts`' rules moved to Rust; the core page route stays Node's. (c) The `Core` route in `ipc_router`; `routeCore` deleted. Each lands green on its own. (b) crosses slice C's pool, the hub and the quit sequence: the pool lives in the core, and `hub.ts` reconnects on `core.started`. It lands only after slice C (pool owner) and H lifecycle (quit placement) have read this section.

**7. Node restarts while the core lives.** Today the shell exits when Node is lost (`node_gone`), so the core ends with it. That stays the rule (H lifecycle and slice C agree). What follows makes the core side safe for a later decision. It does not enable a Node restart:
- What Node's connection owned ends with it: its requests in flight are cancelled, and `serve` returns only once their processes have exited (a git a request ran included). Node's watches report nowhere. The shell's connection and its `ipc` lanes are untouched.
- **One main connection at a time.** The core admits a new `client: "main"` connection only after the previous one's `serve` has returned (`clients.rs`). A restarted Node's first repo-lock holder therefore cannot start beside a git of the old Node's last request. The repository lock lives in Node's memory and starts empty after a restart, so this gate is the fence. It holds the new connection's hello, never refuses it.
- **Not yet safe: the tabs.** A connection's end already closes what it opened: `serve` (`server.rs` 395–404) runs every subsystem's `close_all(&ending)`, `sidecar::close_all` among them (it picks lanes by the `Events` of their `sidecar.open`, `sidecar/mod.rs` 869–881), and waits until its `JoinSet` is empty. The gate above admits the next main only after that `serve` returned. But `sidecar::close_all`'s 2 s bound is no exit receipt: an omp may still run when it returns, and a pool instance closing is no receipt either (slice C). Before a lone Node restart can be supported, each old lane must be seen to exit, or be handed to the new Node for real, and `session-processes` must agree. Until then a lost Node ends the shell and the core with it.

**7a. Slice C's contract for (b)** (the hub session's written answer):
- On `core.started(g)` Node publishes the authenticated endpoint synchronously but opens no pool at once. `Hub.#connect` keeps a live connection and does not re-read the endpoint. At G's end or replacement, Node invalidates the old worker and instances once; only the next use opens a new connection and runs `SidecarPool.#reseed`. A seed is not retried, and no acquire is made twice (`sidecar-pool.ts` 514–579).
- With no G, a hub call fails `core_unavailable`. Main's thread never blocks waiting for `core.started`.
- `abandon(g)` invalidates the local endpoint before it asks the shell, so Node never reconnects to the same G.
- `core.exited(g)`, and late events of the old socket, apply to G only. The repository lock and `onEnded` are released only behind the group-gone fence, never on a bare EOF.
- `hub.out` items and asks are applied on the dedicated hub connection before the answer of the synchronous call they precede. A delayed ask's reply is written only to the connection that asked (`hub.ts` 349–364, 444–459).
- The Node client that opened `sidecar.open` receives its lane's events, questions and binary frames in order. They are never broadcast to the shell's `ipc.call` connection.
- Verification for (b): G's acquire is applied and its answer lost, then G+1 starts. An old generation's abandon, ask and exit are delivered late. Expected: one tab, its new process kept, and zero events on any other connection.
- **The restart window (sidecar).** `sidecar.ts` 914–931 calls `#ensureOpen()`/`start()` straight from its `core_exited` rejection. Today the next request spawns the core, so that works. After (b) there is a window between `core.exited(g)` and `core.started(g+1)`. A start in that window fails `core_unavailable`, the second `#laneLost` stays in its error state, and the tab never restarts. (b) must therefore resume each live handle exactly once after `core.started(g+1)`, rechecking that it is not closed or asleep, or hold new calls without a generation until then. An intended quit, a stop and a rest keep today's outcome. G's commands and bridge calls are never queued and replayed. A test pins this case.

**8. The core restarts while Node holds a lease or a lock.** Today's fence holds. A request Node has in the core when the core dies is failed to Node's caller only after the dead core's gits have exited (POSIX: its group is gone or the 3 s bound passed, `groupGone`; Windows: the core's own kill-on-close job ended them). Only then does `withRepoLock`'s next holder run. After the move the shell does the group wait and sends `core.exited`, and Node fails its waiters only on that event, not on its socket's close. `onEnded`, the step's tracked effect, keeps its meaning. A hub lease (a pool instance, a turn-resume claim) is lost with the hub connection and re-seeded on the next one, as today. A terminal viewer lease lives in the stock worker, which the core supervises, so it ends with the core and is claimed again.

**9. Job object and process group.** On **Windows** the core joins its own kill-on-close job at its start (`end_children_with_this_process`, `crates/core/src/sys.rs`), so who spawns it does not change what ends its children. The shell spawns it detached and hidden (`DETACHED_PROCESS`/`CREATE_NO_WINDOW`, as Node's `detached: true, windowsHide` does). On **macOS** the shell spawns it as the leader of a new process group (`process_group(0)`). After its exit the shell kills what is left of the group and waits up to 3 s for it to be empty before `core.exited`, which is `groupGone`, moved. Proof: `repo-lock-core` (it covers `process.ts` and the core's `main.rs`/`server.rs`) and `session-processes` (it models a crash and a launch at any moment) are updated from the code, their `@code` tags moved to `core_owner.rs`, and restamped on the branch of (b). The client listener of (a) changes `server.rs` and `main.rs` without changing a modeled step: stdio is still main's connection, and no client connects. (a) restamps `repo-lock-core` as a drift check.

**Out of scope here:** `ompdesk-core --supervise` (Node's setup supervisor spawns it per hook) and `--mcp-hub` (the core spawns it). Neither is the core process this section moves.

### Design: slice C, one ordered stream per tab (not built)

**C2: the Files-edit store moves into the core's web router (built).** It frees the close step above from main.

- **Store.** `FileEditReports` becomes `web/file_edits.rs`. It is a field of the router's `State`, under the same lock as the connections. - **Intake.** `Host::dispatch` answers `FILE_EDIT_REPORT` itself after authorizing it as today (`workspace`). ### Design: the shell owns the windows and the entry points (H final's prerequisite, not built yet)

Today `WindowManager` (`src/main/window.ts`) is Node's: it numbers windows, builds them through the shim's `win.create`, persists geometry, decides the last window's close, recovers a crashed or stuck page, and is read synchronously by every entry point that opens or shows a window (`deep-link.ts`, `index.ts` `activateWindow` and the global shortcut, `menu.ts`, `tray.ts`, 13 `ipc.ts` sites). The shell already owns the OS windows, their pages' identities (`registry.rs`), bounds restore (`window_bounds.rs`), activation (`window_activation.rs`), ordered page pushes (`page_push.rs`), the quit chain (`quit_chain.rs`) and the second-instance and macOS open events (`startup.rs`), and hands each to Node as an event. Target: the shell decides, and asks the session owner only for what it cannot know.

**1. The split.** What a window *is* belongs to the shell; what runs *in* it belongs to the pool (slice C).

| Concern | Owner after | Today |
|---|---|---|
| Window id, record (`slot`, `mica`), create, close, destroyed | shell | `WindowManager.#records`, ids from `host.nextWindowId()` |

**2. Two commands to the pool owner.** An entry point that needs a window the shell does not have asks the owner of the pool, never the window manager:
- `session.spawnWindow {cwd?, session?, kind?, device?, presence?} → {win} | null`: today `index.ts` `spawnWindow` (refused once a quit is approved; the target from `resolveWindowSpawnTarget`; the window's tab acquired before it answers, closed again when no tab could be made). With no arguments it restores the saved layout, as now.
- `session.openPath {path} → {focus: win} | {spawned: win} | null`: today `deep-link.ts` `handleOpenPath` (the first window whose cwd is the path, else a spawn there).
- The owner is Node until slice C, reached over the shell's host connection. After C the shell sends the same two commands to the core over the client connection it gets in the core-owner step (c) above (in (b) the shell only spawns and holds the core; the shell's own request channel to it comes with the `Core` route). Only the transport changes; neither command exists twice.
- The owner creates the window through the shell (`win.create`, answered with the shell's ids) before it acquires the tab, so a window never exists in Node that the shell did not make. Node's `createWindow` becomes async; its three callers already are.

**3. Ordering kept.**
- Entry points stay serial: an open waits for the one before it (`deep-link.ts` `pending`), and a link or file that arrives before the first window is replayed after it, in order.
- A payload for a page (`DEEP_LINK`) goes through `page_push`'s outbox, which holds it until that document is ready, as `did-finish-load` holds it today; a document that is replaced first never gets it.
- `win.closed` reaches Node after the window's last page send on the same stream. Node handles it in one tick, in today's order: the window leaves the live list, `persistTabLayouts` runs, then the pool's `windowClosed` releases its tabs. A closed window must be gone from the list before the first save after its close, or its layout comes back on the next launch. Releasing before or after that save must give the same file (today both run and the last save wins). During an approved quit, `layoutsToSave` keeps the stored layouts, and a paired page's window is never saved (slice C's answer).
- Until C, Node keeps one thin `ClientWindow` per shell window with what the pool uses: `webContents.id`, `webContents.send`, `isDestroyed()`, `once("closed")` and `isWebWindow(id)` (and `instanceof WebClientWindow`/`deviceId`, which `onWindowTabsChanged` uses to save paired layouts), as the shim's mirror does now. Its ~25 "send to every window" loops become one shell broadcast to the live app pages. The broadcast and Node's other sends share one stream, so they stay in order.
- **The pool owner in the core needs three things first** (slice C's answer): a core→shell path to create a window, the quit state (now `quit_chain.rs`'s), and the session list and prefs `resolveWindowSpawnTarget` reads (prefs are slice B's). Until all three exist, Node serves both commands.

**4. Units, each green alone.**
1. **W1 OS window state.** Shell: ids, geometry and its file, chrome/Mica, first show and presence, focus/target/show, run progress, renderer recovery and its two dialogs. Node's `WindowManager` keeps the pool-facing record and `cwd` only. Vitest `window-chrome`, `window-show`, `renderer-recovery` cases move to Rust tests. e2e: `first-launch-window`, `window-theme`, `windows-caption`, `sidebar-prefs-two-windows`, `renderer-hang` (`e2e/renderer-hang.e2e.ts`).
2. **W2 entry points.** Shell: Dock `activate`, the global shortcut, second instance, `open-url`/`open-file`, the `omp://` parse (`deep-link.ts`'s cases become Rust tests), using the two commands. Node's `setupDeepLinks`, `activateWindow` and the shortcut handler are deleted. e2e: `first-launch-window` (second launch), `multi-viewer`, `opened-close-relaunch`, `relaunch-child-ids`.
3. **W3 menu and tray** (`menu.ts`, `tray.ts`, `tray-labels.ts`, root rows 306/490/491): the last readers of the target window. The tray's labels read the updater status (slice G) and the quit risk (pool): the shell asks for them when the menu opens, never from a mirror.
4. **W4 last-window close.** `lastWindowCloseAction` in the shell. The close-to-tray pref reaches it as a fact its owner pushes on every change (Node now, slice B's owner later), as the theme does, never as a read on the close path: the close must decide at once, also while a core restarts. The once-only tray notice is a shell notification whose pref write goes to B's owner. Lands after B. `WindowManager` is then deleted; the pool's window entry carries `cwd`.
- Depends on: W1–W3 need neither (b) nor C. W4 needs B. Moving the two commands' owner to the core needs C and (c).
- Formal: `session-processes` and `tab-session` tag `index.ts` spawn and restore lines; W1/W2 move their `@code` tags with the code and restamp both on the branch.

**5. Behaviour differences.** None intended. Two to watch: the window id is the shell's (positive, unique for the app's life, never a paired page's negative virtual id, `isWebWindow`; the pool's tab layouts and core lanes key on it), and a spawn the shell asks for while Node is busy waits on Node's answer instead of running inside Node's own tick, which is the order the shell's events already arrive in.

## 4. Open product decisions

**No inspected inventory reason establishes that the desktop Node process must remain.** The existing product choice explicitly retains Tauri’s system WebView, React and installed stock omp, not the desktop Node host (`.omp/rules/native-rust.md:11–24`). Three boundaries must not be treated as implicit permission to change the product:

- `src/main/models-config.ts` must preserve YAML comments/layout and stock normalization (`root.tsv:321`). A lossy serializer is not an acceptable port. A product decision is needed **only if proposing to drop that guarantee**.
- `src/main/model-release-dates.ts` must preserve existing trust roots, extra CAs, opt-in proxy handling and last-good cache (`root.tsv:310`). Switching silently to platform defaults is not equivalent. Changing network compatibility would need a decision.
- `resources/gui-bridge/stock-helper/{accounts,models,terminal-service,terminals}.ts` and `stats-host.ts` retain installed-stock APIs by design (`helpers.tsv:10–11,21–25`). Removing **all Bun/JavaScript processes** would be a different product goal. Their continued presence is not evidence that Node removal failed.
