# 새 omp를 스스로 따라가기 (0.134.1 뒤 첫 일) — 설계 한 장

## 목표
새 omp가 나오면 OMPdesk가 곧 따라간다. 녹색이면 OMPdesk 새 판 없이 기기들이 그 omp로 올라간다. 빨강이면 그 판만 잠깐 붙잡고, 호환 작업이 바로 시작되고, 창구에 알린다. 사람에게 스위치를 끄라고 하지 않는다.

## 자료 모양: 앱 판별 검증 목록 (하나뿐인 진실)
- 저장소의 데이터 가지 `omp-compat`(main 아님, 워크플로 권한 문제 없음)에 `omp-compat.json` 하나:
  `{ "<앱 판>": { "verified": ["19.0.0","19.0.1"], "holding": {"version":"19.1.0","since":"…","issue":123} } }`
- 키가 앱 판인 까닭: 기기는 main이 아니라 **내놓은 앱**을 돌린다. 그래서 검증은 main과 함께 **최신 릴리스 태그**의 코드로도 돈다.
- 앱은 기존 GitHub 조회 길로 자기 판의 항목만 읽는다(15분 캐시, 못 읽으면 직전 값; 처음부터 못 읽으면 앱에 든 omp-tested만).

## 흐름
1. omp-latest(지금 있는 워크플로)를 매시간 npm `dist-tags.latest`로 깨운다. 새 판이면 최신 태그와 main 두 곳에서 돈다.
2. 녹색 → `omp-compat.json`의 그 앱 판 `verified`에 추가(push 단계). 기기들은 다음 확인(켤 때·4시간, 0.134.1의 규칙)에서 `verified` 가운데 가장 새 판을 정확한 판으로 깐다(`bun install -g …@판`, 0.134.1에 이미 있음).
3. 빨강 → `holding`에 적고, 이미 있는 `omp/bump/<판>` 가지와 이슈를 만들고, **창구에 알림**(OMPdesk의 `ompdesk_schedule {on: github}`이 그 이슈를 보고 Main 세션을 깨움). 고쳐서 녹색이 되면 그 고침을 담은 앱 판(패치)이 나가고, 그 판의 `verified`에 들어간다.
4. 붙잡힌 동안 설정 › 업데이트 및 정보의 omp 줄: "omp 19.1.0 검증 중 — 끝나면 저절로 올라가요". 스위치를 끄라는 말은 없다. '지금 업데이트'는 그대로 사람이 누르면 깐다(아래 4번 받침).

## 올리는 길이 둘: 주인을 OMPdesk 하나로
- 길 A: OMPdesk(켤 때·4시간·복구, 0.134.1부터 정확한 판). 길 B: stock omp 자신의 `update.auto`(터미널에서 omp를 켤 때 몰래 최신을 깖; 맥북은 true였음).
- 정함: **주인은 OMPdesk 하나.** OMPdesk가 '도구 최신으로 유지'가 켜진 기기에서 stock `update.auto`가 true면 한 번 false로 바꾸고(stock 설정 API `omp config set update.auto false`), 로그에 남기고, 설정에 "omp 자동 업데이트는 OMPdesk가 맡아요(검증된 판만)" 한 줄을 보인다. OMPdesk 스위치를 끄면 OMPdesk는 stock 설정을 건드리지 않는다(사람이 고른 상태 존중).
- 까닭: 둘 다 두고 같은 목록을 따르게 하려면 stock이 그 목록을 읽어야 하는데 stock은 판을 고를 수 없다(`omp update`는 대상 판을 받지 않음, 확인). 원본 omp에 제안하지 않는다는 스풋 규칙도 있다.
- 사람이 터미널에서 `omp update`를 직접 친 경우(막을 수 없음): OMPdesk는 깔린 판이 `verified`에 없음을 알아채고 omp 줄에 "검증 안 된 omp X를 쓰는 중 — 맞지 않는 기능만 꺼져요"를 보인다. 4번(기능 단위로 꺼지기)이 받침: 없는 내부 함수를 쓰는 동작만 꺼지고 나머지는 산다. 그 판이 검증되면 안내는 사라진다. OMPdesk가 스스로 내리지는 않는다.

## 시험(이것이 녹색이기 전에는 "빨강이면 기기가 안 올라간다"고 쓰지 않음)
1. 길 A: 가짜 레지스트리 최신이 `verified` 밖 → 켤 때·타이머·복구 모두 설치 0, 설정에 '검증 중'; 목록에 들어오면 다음 확인에서 정확한 판 설치(e2e, 빌드한 앱).
2. 길 B: 가짜 `~/.omp/agent/config.yml`에 `update.auto: true` + 스위치 켬 → OMPdesk가 false로 바꾸고 로그 한 줄; 스위치 끔 → 손대지 않음(단위 + e2e).
3. 목록 못 읽음(오프라인) → 직전 값/앱 내장 판으로, 새 판 설치 0.
4. 사람이 검증 밖 판을 깐 상태 → 안내 줄, 기능 단위 꺼짐(4번 시험과 같이).
5. omp-latest 쪽: 녹색이 `omp-compat`에 그 앱 판으로 적히고, 빨강이 holding·이슈·알림을 만든다(워크플로 리허설 입력으로).

## 0.134.1의 '시험한 주 판까지만' 규칙과의 관계
0.134.1의 규칙은 이 설계의 앞단(정확한 판 설치, 로그, 사람의 버튼)으로 그대로 쓰고, 기준만 '앱에 든 omp-tested의 주 판'에서 '`omp-compat.json`의 내 앱 판 verified'로 바꾼다.

## 남는 위험
- 맥북 11:01 업데이트가 길 A인지 B인지는 그날 로그가 없어 끝내 모름(0.134.0 이전 길 A는 로그를 안 남겼음).
- 검증은 vitest·e2e까지만이다; 실제 공급자 계정이 필요한 흐름은 검증 밖.

## 창구 검토(19 Nov, hub-follow-omp-design-review-20261119) — 시작할 때 반영
1. 목록 보호: omp-compat 가지는 그 워크플로만 씀(가지 보호); 앱은 엄격 검사(패키지 이름 고정, 정확한 semver만, 범위·태그·주소 거절), npm에 실제 있는 판인지 확인, 깔린 판보다 낮게 스스로 내리지 않음, 모양 틀리면 직전 값. 망가진·악의적 목록 시험.
2. 알림은 ompdesk_schedule 쓰지 않음: 앱이 자기 판 holding을 읽으면 알림 한 번 + 설정 줄.
3. 러너 시간: 새 판마다 (태그+main) omp-latest 한 번의 OS별 분, 조직 포함 시간 안인지 숫자로; 추가 요금이면 먼저 알리고 줄이는 길(패치=빠른 검사, 주·부=전체).
4. '맞지 않는 기능만 꺼져요'는 기능 단위 꺼지기가 들어간 뒤에만.
5. holding 24시간 넘으면 알림 한 번 더 + 며칠째인지 표시.
6. 놓을 때 돌려주기(hub-follow-omp-design-unmanage-path-20261119): (a) 맡기 전 값을 기록(누가·언제·무슨 값), 스위치 끔/앱 지움 때 되돌림, 사람이 사이에 바꿨으면 덮지 않음; 시험 4가지(왕복, 사이 변경, 원래 false, 설정 파일 없음); 맥북 원래 true(창구가 13:04에 false로)를 첫 기록으로. 또는 (b) 앱 전용 omp. 창구 생각 (a).
