## OMPdesk control tools

### Overview and safety
- Switch: Settings › Tools & extensions › OMPdesk control tools, pref `agentControl`, default **on**. Contract `src/shared/agent-control.ts`, schemas `tools.ts`, app seam `host.ts`, skill `resources/omp-builtin/skills/ompdesk/SKILL.md`.
- **Where the service lives (batch H3/H4a, 9g–9k)**: the rules and tool bodies run in the Rust core (`native/ompdesk/crates/core/src/agentctl/`: `service/` the tools, `journal/` the files, `rules/` mail, custody, pickup, auto-close and tab-close, `runtime/` what the host did over the service's own state, `app/` `ompdesk_app`). Every later bullet that names `service.ts`, a `#method`, or a file of the old TypeScript service (the journals, the mail, custody, pickup, auto-close and tab-close rules, `ompdesk_app`'s catalog, settings, guard, channels and schema) means the Rust module named beside it (the TypeScript twins are deleted; `#method` names are the Rust functions' snake_case names, `agentctl/service/{sessions,messages,work}*`). One close rule: `rules/tab_close.rs` decides every agent close, and main's release only asks again whether the page now holds unsaved Files edits. `app-control-test-rig.ts` is the TypeScript `AppControl` kept as the parity rig of `app-control.test.ts` (no production caller). `service.ts` is main's seam and typed client: `AgentControlHost` (what the core asks of main, and the snapshot it reads: the open tabs and their windows, the switches, summaries, who opened what, tombstones, the language's texts) and `AgentControl` (one `agentControl.open|call|close` instance over a `CorePort`; a core that started again is opened again by the next call). Main pushes the snapshot when it observes a change (the pool's activity, the preferences, summaries, deleted sessions, outside callers) and before every call; every answer carries it. `host.ts` keeps what reads the pool, windows, preferences, the remote link or Electron: the snapshot builder, the spawn, git, cards, schedules and app ports as the core's asks. **The runtime** (`runtime/`, opened with the service when `host.runtime` is given; `AgentControlHostDeps.sweepMs`) owns the sweep of the opened sessions (`SWEEP_*`: one `autoClose` pass 1 s after activity, every 10 s for every opener), the work board's review settle and push (`REVIEW_SETTLE_MS` 400 ms; main sends the frames to the windows), the redelivery of reports (`mail-outbox`) and messages still owed, and a routine's wake-up (`wakeSession`: main reaches the session, the core keeps the mail and follows the turn). Tests: `service.test.ts` and `host.test.ts` run against the real core (their waits are shortened through `tuning`, as the TypeScript tests moved fake timers); the Rust modules carry the pure rules' tables captured from the TypeScript.
- **A core call that never waits does its work as its line is read** (`at_once`, `server.rs`; the `agentRuntime.*` handlers `activity`, `afterRun`, `pushReview`, `sweepOpeners`, `forgetDeleted`, `acknowledge`, `wakeStop`), because the body of a `Box::pin(async fn …)` handler starts only when its own task is first polled and two such tasks start in either order. Main sends a tab's busy edge and then a wake's stop in that order, and the stop reads whether the turn had started: run in the other order it found "not started" and aborted nothing (`host.test.ts` "ends the run with the turn the wake started…" red on win-platform 3/3, run 43387432689). Pinned by "aborts the turn of a wake stopped right after the tab's busy edge". A new handler whose effect a later call of the same caller reads does its work before it returns, as `ipc.call` and `stock.request` do.
- **Full control** (the user's decision): Settings › Tools & extensions, first row "Give agents full control of OMPdesk" / "에이전트에게 OMPdesk 모든 권한", pref `agentControlFull` (`AGENT_CONTROL_FULL_PREF`), default **on** (`agentControlFullEnabled`: only a stored `false` is off). While on, **no control tool or app action raises an `[OMPdesk]` card**: the `always` set (deletes, MCP/plugin install, sign-in starts, proxy, mobile web on, pairing, update apply, quit), a foreign session delete, Autopilot release or main targets, every power pref. It implies `agentControlApprove` and `agentControlManage` (`host.ts` resolves both as `full || stored`; their Settings rows show checked and disabled). The catalog action `agent_power.set` (`fullOnly`; `FULL_CONTROL_PREFS`/`FULL_CONTROL_SETTINGS` in `agentctl/app/guard.rs`, the terminal-omp wiring through ai-memory's own channel; memory and learning have no switch) lets an agent change the agent-power switches, this one included. Every action is still journaled and toasted with undo where one exists. Kept whatever it says: an agent never answers an `[OMPdesk]` card, secrets/tokens/passwords are never readable, git safety (no force push, Autopilot's guard bans destructive git), OS security prompts (UAC, TCC). Its tooltip names the risk (prompt-injected content can make an agent delete data or install code). **Every card rule below applies only while full control is off.** Pinned by `shared/agent-control.test.ts`, `app-control.test.ts` (`always` actions card-free when on, `agent_power.set` refused when off), `service.test.ts`, `host.test.ts`, `AgentControlRow.test.tsx`, and the on/off cases of `e2e/agent-app-control.e2e.ts`, `e2e/agent-control.e2e.ts`, `e2e/agent-review.e2e.ts`.
- **Every power on by default, no setup** (the user's decision). The switches `agent_power.set` exposes all resolve on while unset: `agentControl`, `agentControlFull`, `agentControlManage`, `agentControlApprove`, `pstack`, `ecc`, stock `computer.enabled` (OMPdesk's held default on, `.omp/rules/models-accounts.md` Held stock defaults) and stock `tools.approvalMode` (stock's default `yolo` already means no approval card; no held default, since Autopilot's own `yolo` override would clear one). Only a stored `false` (or another mode) is off, so a person's opt-out is kept.

- **A send whose answer never came is not confirmed, never "nothing was sent"**: a paired host's `tab.command` that timed out on the link reaches the core as `{success: false, code: "rpc_delivery_unknown"}` (the host may have delivered it), and a local omp's as `RPC timeout (…)`; both are `RpcResponse::unanswered` (`agentctl/service/types.rs`). `hand_send` then keeps the outbox entry as handed and records the receipt under `caller|target|request_id`, so a resend with that id is answered from it and never delivered twice; the receipt reads `Sent to …: not confirmed; … did not answer in time (…)`. The outbox sweep and a card answer (`attach.rs`) read it the same way. Pinned by "an unanswered send is not confirmed" in `messages_tests.rs`.
- **Subagents have no control tools** (stock registers host tools on the RPC session only; `host_tool_call` carries no caller id). `e2e/real-agent-control.e2e.ts` checks it (`NO_TOOL`, no tab opens). A subagent can run the `ompdesk` CLI through bash and then acts as an outside caller, under the same rules and cards.
- **No count or rate caps** (the user's rule; none in `src/main/agent-control`): any number of sessions, messages, schedules and Autopilot runs. Only a self-send is refused. Provenance ("opened by you") is main-owned state, never read from text or tool args; it survives a relaunch (`#openedBy` adds every tab whose `host.parentOf` is the caller: the pool's `openedBy`, else the tab holding `openedBySession`).
- Session tools touch no accounts, settings or permissions. **Deleting a saved session the caller did not open** (`ompdesk_session_stop delete:true`) always raises one confirmation card (stock extension-UI `confirm` via the calling tab's omp, bridge `agent_control.confirm`, title prefix `[OMPdesk]`, so it survives a reload and reaches a paired device), whatever "Let agents manage other sessions" says, because a delete cannot be undone. Stopping or closing a session it did not open raises the same card only while that switch (`agentControlManage`, **default on**: `agentControlManageEnabled` in `shared/agent-control.ts`, only a stored `false` is off) is off. Sessions it opened itself need none, delete included.
- Closing a resting session's tab (not busy, no open ask, not in the person's view, no draft or prompt of theirs since: `ControlTab.looked`/`userTouched`) raises no card whoever opened it. Each close is journaled as one quiet `ompdesk.mail` note in both sessions **only once the tab is confirmed gone** (`#journalClose` runs after `close_tab` (`agentctl/service/sessions/stop.rs`)/`#deleteWhenIdle` returned), so a kept or held-back close sends no "Closed" note. The closed session's own line is best effort (its omp has exited).
- **A session the person typed into, or one the caller did not open that is in the person's view, is stopped, closed or deleted only in a turn the person's own message started**, so an agent never does it on its own initiative while a person's typed request still can. **A session the caller opened is never held back because the person looks at it** (the owner's rule): stop, close and delete go through in any turn, and none is kept as a pending cleanup; one the person typed into keeps the rule, since their own words are in it. One predicate decides, `needs_person_turn(tab, own)` in `agentctl/rules/tab_close.rs` (`userTouched`, or `looked` and not `own`): `#stop` applies it before the card and again right before the close or delete, and `tab_close_step` applies it to a close nobody cleared (auto-close, a failed open's cleanup, Autopilot's source tab). The auto-close pass is no caller's request and still keeps a tab the person looks at (`auto_close_decision` `looked-at`, the renderer's `autoCloseHeld`) until a later pass finds it unseen. It decides from turn provenance, never text: `AgentControl::stop` asks the caller's omp (`agent_control_turn` → bridge `agent_control.turn`, `resources/gui-bridge/turn-origin.ts`) whether the main agent's current run was started by a prompt main said a person typed (`typed_prompt`: a window's or the phone page's prompt in `ipc.ts`, a paired device's in `remote/host-services.ts`; never an agent's wrapped message, Autopilot's prompts, a schedule or a relaunch's continuation). The bridge reads it at the run's start (prompt messages between `agent_start` and the first answer): a user message whose whole text a typed note names makes it the person's, a report mail that wakes the session does not, a run with no prompt (stock's retry) keeps the one before, a steer or follow-up never changes it. Refused otherwise for stop, close and delete, with the reason in the error; an outside caller, an omp that cannot answer and a failed request count as not the person's. A close `#stop` let through also releases a paired web page's tab the person is at (`tab_close_step(tab, cleared)`); unsaved Files edits still keep it. Pinned by "in a turn the user's own message did not start" (own and looked, own and typed, not own and looked) and the person/agent-turn cases in `service.test.ts`, `bridge-turn-origin.test.ts` and `bridge-turn-origin-stock.test.ts`.
- **A refused cleanup is kept and told once**, so finished sessions do not stay open unnoticed; the rule above is unchanged. `#refuseInUse` (the one refusal for stop, close and delete, re-checks included) adds the call to `PendingCleanups` (`agentctl/journal/pending_cleanups.rs`, `<userData>/agent-pending-cleanups.json`, newest 200): caller (its session file), target session file and tab id, action, time. A caller that is no tab (the control socket) keeps nothing. When main hears the person typed a prompt to the caller (`ipc.ts`: the IPC channel and `personsPrompt`, the same word `noteTypedPrompt` goes by; never the text) and the caller runs no turn, `AgentControl.personTyped` takes its list and sends one quiet `ompdesk.mail` note (`triggerTurn: false`, so it is in context ahead of that prompt's turn) with the exact `ompdesk_session_stop` call per entry; entries whose tab closed since (unless a delete of a still-saved session was asked) or whose call later went through (`#stop` drops it) are left out. A prompt joining a running turn starts none, so the list waits; a note the omp could not take puts the list back. Told once, never nagged; a call refused again is kept again. Pinned by "a cleanup refused while the person was in the session" in `service.test.ts`.
- **Arguments written as JSON text are read as what they spell**. `looseArgs` (`tools.ts`, run by `#dispatch` before the strict `ARGS` parse, for every tool and nesting) walks the tool's JSON schema: where a field takes no string, a string spelling a boolean, a number, or object/array JSON becomes that value; a text field keeps it, and text that spells nothing the field takes still fails. An invalid-arguments error names each field's path. `reopen` with `folder` is refused only when the folder differs from the one the session worked in (`folderKey`). Pinned by "arguments a model wrote as JSON text" in `tools.test.ts` and the open case in `service.test.ts`.

- **Attachments** (the owner's call, 13 Nov 2026: a screenshot a person pasted into one session reached another only as a retyped description). `ompdesk_session_send` and `ompdesk_report` take `attachments: ({path} | {image: n})[]`: `{path}` a file on the computer the CALLER's omp runs (absolute, or relative to its folder), `{image: n}` the n-th newest picture of the caller's own conversation (1 = newest; a person's and a tool result's both count). Each is read by the caller's own omp (`agent_control_attachment` → bridge `agent_control.attachment`, `agent-control.ts`; a blob reference through stock's store, `agent-control-blobs.ts`; a free command in `quota-commands.ts`), so a caller on a paired host hands over its own computer's bytes. `ATTACHMENT_MAX_BYTES` 10 MiB each (inside the link's 16 MiB frame after base64; stated in the schema and its description, no `maxItems`: no count cap). A picture (`png|jpeg|webp|gif`, by its bytes, not its extension) goes inline: stock `prompt.images` for a message, image blocks of the report's custom message (`agent_control_mail` `content` as text and image blocks; `mailCommand` and the bridge take them); at most `INLINE_IMAGE_BUDGET_BYTES` 8 MiB of pictures per message, the rest land as files. Any other file lands on the RECEIVER's computer: this one through main's `land` ask (`host.ts` `#land`: `attachHere`'s upload store, `LOCAL_UPLOAD_DEVICE`), a paired host's through `uploadToHost` (`host.files.upload`/`uploadPart`, no new protocol method; `file_too_large`, `upload_refused`, `unsupported` become the refusal text), and the text gets one `Attached: <path>` line per file. The same bytes (SHA-256) twice in one call land once, and bytes that landed on that computer within the upload store's lifetime reuse their path (`LandedCache`, `journal/attachments.rs`). Any attachment that cannot be read, is over the cap or cannot land refuses the whole call with the attachment named and nothing delivered (reads and landings happen before anything is kept or sent). The tool result says `attached: 2 (1 image inline, 1 file at <path>)`. **Durable**: the outboxes keep only references (`attachments` of an `OutboxSend`/`OutboxMail`: SHA-256, name, type, size, and for a file its landed path and time); the bytes are in `AttachmentStore` (Rust, `agentctl/journal/attachments.rs`, `<userData>/agent-attachments/<sha256>`, 0600, atomic writes), swept hourly and at launch of what no entry names and is older than an hour, and a redelivery after the upload's lifetime lands the files again and rewrites the paths (`rehome`). **Replay fails closed**: a message or report that names an attachment is delivered with it or not at all. A damaged `attachments` record (`readAttached` → `attachmentsCorrupt`, never read as none), a picture whose bytes `AttachmentStore` no longer holds, and an expired upload that cannot be landed again (bytes gone, or the receiver's computer refusing or offline) raise an `AttachmentProblem`: nothing is handed over, the entry stays owed and is retried at every pass, and the sender is told once per cause through `Host::trouble` (`Host::tell_sender` in `service/attach.rs`: a waking note into the sender's session, found by its session file and computer; `OutboxSend.from`/`fromDevice`, `OutboxMail.from`/`fromDevice`) naming the attachment and why. Pinned by `agentctl::service::attach` and `agentctl::journal` Rust tests. `request_id` and report-id idempotency are unchanged (a report's default id includes the attachments' hashes). `ompdesk_session_answer` takes `attachments` as well: a stock extension-UI response or plan approval cannot carry a file, so the answer is ONE step on the computer that runs the answered session (`agent_control_answer`, answered by `TargetAnswer` in `agent-control/target-answer.ts` from `dispatchRpcCommand`; a paired device's tab forwards it through the link to its own host's main, an older host refuses it as an unknown command and nothing is delivered): the question must still be open (`SidecarPool.isRequestOpen`, `pendingPlan`), the companion note (`ompdesk.mail` kind `note`, id `answer-<hash>`, pictures inline, files landed with `Attached:` lines, no turn) is appended, then the answer is routed; idempotent by `requestId` (`<note id>|<ask id>`: a resend after a lost reply appends and answers nothing twice, a resend after a failed answer appends nothing twice because the bridge refuses a repeated note id). A question gone (or held by another answer) before the step appends nothing and refuses; a failed append releases the claim; omp cancelling the question itself while the note goes in is the only partial case and says that the attachments reached the session and the answer did not (the bridge cannot resolve stock's own pending asks). The sender is never told the answer went when it did not. Attachments are read before anything else and the answer is validated first. The `ompdesk` CLI/control socket (a caller outside OMPdesk has no omp to read from) carries none and is refused. Pinned by the Rust tests above, `tools.test.ts`, `bridge-agent-attachment.test.ts` `target-answer.test.ts` and `e2e/agent-attachments.e2e.ts`.
- The user can hide a session from agents (Sidebar session menu › "다른 에이전트가 이 세션을 보지 못하게", `agentHidden` in the `sidebar` prefs blob, this computer's sessions): it lists as hidden and refuses read, send, wait, answer, show and stop.

### Memory and idle release
- **No agent work ever waits for memory** (the owner's order). There is no memory admission: an agent's open or message, a scheduled run or wake and a relaunch's continuation start at once, on every computer. A paired older host's `memoryWait` tab event is not in `TabEventMessage`, so `devices.ts` drops it unread; an older device's `tab.startNow`, `tab.memoryWaitedOn` or `host.memory.status` gets the unknown-method answer, which it reads as an older host. Agent processes run at lower scheduling priority (the core’s `sidecar/process.rs`, nice +10 / BELOW_NORMAL, inherited by their children).
- **The memory watch** (`src/main/memory-watch.ts`, started in `index.ts`) reads every `SAMPLE_MS` = 5 s, for idle release and for the record a stall leaves (`machine-state.ts`, interrupted-work › Probes › Machine state): the OS's reading and the process list, both read by the core process (`native/ompdesk/crates/core/src/memory/`, methods `memory.reading` and `memory.watchProcesses`; the latter returns process rows and idle-tree facts from one OS snapshot; `memory-sampler.ts` is their client and counts a failed or late answer, `SAMPLE_TIMEOUT_MS` = 4 s, as no sample). macOS: one `sysctl` for `kern.memorystatus_vm_pressure_level`, `kern.memorystatus_level` % of `hw.memsize` and `vm.swapusage`, and one `ps -axo pid=,ppid=,rss=,time=`, each process this user may read then counted by its `phys_footprint` (`proc_pid_rusage`, `sys.rs` `footprint`; another user's keeps its rss), because rss drops as macOS compresses a process's pages: the `memory short` lines named the Mac mini's Main omp at 136 to 486 MB in hours it held about 1.9 GB (19-20 Nov 2026), and idle release, which gives back the largest quiet tab first, took a smaller one. Windows: `GlobalMemoryStatusEx`'s available physical memory, warn/critical under 10 %/5 % of RAM, its commit charge and limit, the processor and disk queues (PDH), and a Toolhelp32 snapshot with each process's `K32GetProcessMemoryInfo` working set and `GetProcessTimes` processor time (`crates/core/src/sys.rs`; no WMI). A test launch reads `OMP_GUI_TEST_MEMORY` (JSON file: totalGb, availableGb, pressure) every `OMP_GUI_TEST_MEMORY_MS` for idle release instead; a Playwright launch without one reads ample memory. The stall record gets the real reading in a test launch too.
- **A quiet session gives its omp back while memory is short** (`src/main/idle-release.ts`; the owner's goal: many sessions without weight, no slower and nothing lost). The memory watch asks it each sample; it acts only while the OS reports memory short **now** (pressure warn or critical, or under `RESERVE_FRACTION` = 15 % of RAM available; never a growth prediction, which would release sessions with memory free), so while memory is fine no session waits for its omp to restart. A tab may go when the pool reads it quiet (`SidecarPool.#quiet`: this computer's own ready tab on a saved session, shown in no window, split pane or device, opened by the person (an agent's child closes by itself); no turn, compaction, ask, plan, draft, retry, continuation, sign-in or pending restart) and its omp has started no process (an eval worker holds eval state; a job, daemon or MCP server is live), continuously for `IDLE_RELEASE_QUIET_MS` (5 min); the largest tree goes first, one per sample. `SidecarPool.releaseIdle` checks again, asks stock's `isSettled` (no queue, background job or delivery that could wake it), checks once more, then `SidecarManager.sleep()` stops the omp as a restart does and the tab reads `asleep`: it starts again on its session file when shown or messaged, as a restored tab does, rows painted from the tab's transcript snapshot meanwhile; a prompt sent while it starts waits for ready (`installTabReadyGate`). One `memory release` line in `gui-runtime.jsonl` per release (`memory release kept` when the pool's checks refused). Tests: `idle-release.test.ts`, `sidecar-pool.test.ts` "SidecarPool releaseIdle", `e2e/idle-release.e2e.ts` (fake omp: kept while fine, released when short, a shown tab and one with a working background subagent kept, a sidebar click shows its rows within 1 s and the same transcript after restart, a next turn answers).
- **On Windows the tab's pid is a launcher, not the omp**: `SidecarManager` spawns bun's `omp.exe` shim, or cmd.exe for an `omp.cmd`, whose children are `conhost.exe` and the omp (`bun.exe … cli.js`). "Its omp has started no process" therefore reads the launcher's one child besides the console host as the omp and counts that omp's children; a console host (`conhost.exe`, the image name the core reads from `szExeFile`) never counts, and a launcher of any other shape (no omp under it, or two) reads busy. Counting the launcher's own children would keep every Windows tab from release. macOS spawns the omp itself (`ps` names no images). Pinned by the Windows launcher cases in `memory/idle.rs` and `e2e/idle-release.e2e.ts` on Windows.
- **What a session costs** is measured with `bun scripts/session-footprint.ts run --fake 20 --real 3` (opt-in spec `e2e/session-footprint.e2e.ts`: built app, macOS `phys_footprint` of every process under main, CPU per window). Rough baseline: app fixed cost about 510 MB and about 2 % of a core idle (the extensions worker exits 60 s after its last answer); each real session one omp of about 255–280 MB fresh, growing with its transcript, plus what it starts (an eval worker per session, a daemon broker shared per project); main and the renderer add under 1 MB per open tab; an omp reads ready in about 1.5 s (real), 60 ms (fake).
- **Who uses the memory is written down when it runs short** (the owner's report, 12 Nov 2026: the 16 GB Mac mini froze and `gui-runtime.jsonl` held no line that said what had filled it). As a sample reads memory short (idle release's own `memoryShort`), and every `RECORD_EVERY_MS` (5 min) while it stays short (`RecordClock`), the watch writes one `memory short` line (source `memory`; `recordShort` in `memory-watch.ts`, the native `procs.pressureRecord` in `procs/pressure_record` ranks the scan using the owners and tabs main supplies after it finishes): the reading, `top` (the `RECORD_TOP_PROCESSES` = 8 largest processes: name, pid, MB, age in minutes, whose) and `sessions` (the `RECORD_TOP_SESSIONS` = 6 sessions that hold the most: title, folder, the device it runs for, MB, process count), both JSON text because the log keeps only primitive details, and `sessionsMb`, `ompdeskMb`, `otherMb`. Whose a process is (`processOwners`): the session whose tag it carries (Session processes, below), else the tab whose omp it runs under (a parent that started after its child is a reused pid and is not followed), else OMPdesk when it runs under main, else `closed session` for a tag no open tab holds (a session that is gone, or another OMPdesk's), else `not OMPdesk's`. Never a full process list and never a command line (arguments hold tokens). The record itself is on no screen (the owner asked for the record); what each live session holds is (next bullet). Pinned by `memory-record.test.ts` and the short step of `e2e/session-processes.e2e.ts`.
- **The person sees and acts on it too** (All sessions › Resources, `components/board/ResourcesView.tsx`; after Orca's resource usage and sleep, FB100/FS101/FB33): `RESOURCES_READ` answers `SessionProcesses.use` (one `procs.list`, grouped by each live tag, the omp first, the largest session first; the tab and the pool's `quiet` joined by the omp's pid), read every 5 s while the page shows and painted from its last read. **Stop** ends one process by pid and start (`endProcess`: `procs.end` with `only`, the session's tag; never its omp, whose end is closing the tab; stock's workers kept by `keepArg`). **Give back now** releases a quiet tab's omp at once whatever memory reads, by idle release's own rule (`canGiveBack` in `idle-release.ts`: the pool reads it quiet and `memory.watchProcesses` finds its omp with no busy child; `SidecarPool.releaseIdle` checks again), else answers `busy`. A paired computer's page shows that computer's sessions (the channels pass).

### Session processes
- **The owner's report (12 Nov 2026)**: work done through OMPdesk on the Mac mini (16 GB, hosting other computers' sessions) left `next dev` servers, Playwright's browser, an Android emulator and an `adb` daemon running until the machine froze. The user's rule: **a computer does not fill up with what finished work left behind**, and a session's processes live as long as its tab.
- **Whose process it is** (`src/main/session-processes.ts` `SessionProcesses`, one per app in `index.ts`, handed to every `SidecarManager` through `sidecar-factory.ts`): a tab's first spawn makes its tag (16 random bytes as hex), kept for every later omp of that tab (a restart, a crash, a wake after idle release) and set as `OMP_GUI_SESSION_TAG` (`SESSION_TAG_ENV`, in `sessionEnv` and `SESSION_OWNED_ENV`, so a tag inherited from another OMPdesk session's shell is never passed on). Whatever the omp starts inherits it, however deep, and keeps it once its parent is gone (a daemon, a double fork, `nohup`, `&`). The tags are kept in `<userData>/session-processes.json` (0600; tag, folder, session file, the device a hosted tab runs for), parsed with zod, and **only a tag in that file is ever ended**.
- **Read back and ended by the core** (`native/ompdesk/crates/core/src/procs/`, native-rust › 3d): `procs.list {env}` answers every process with pid, parent, resident bytes, start, image name and the tag in its environment; `procs.end {env, tags, keepArg, graceMs, timeoutMs}` ends what carries one of the tags. macOS reads `sysctl KERN_PROCARGS2` (the arguments and environment a process was started with), Windows the process's own environment block through its PEB (`NtQueryInformationProcess`, `ReadProcessMemory`), Linux `/proc/<pid>/environ`. Asked first, then killed: SIGTERM, `END_GRACE_MS` (5 s), SIGKILL; on Windows `WM_CLOSE` to each top-level window a target owns (never a console's window, which would end every program on that console), the grace only for those asked, then `TerminateProcess`. It scans again after each round, at most 5, because a supervisor starts its child again. The pid is checked at the point of risk: Unix reads the pid's tag again right before each signal; Windows terminates through the handle it read the environment through, so a reused pid is never hit.
- **When they end**:
  - **The tab is released** (the person's close, an agent's `ompdesk_session_stop {close}` or `{delete}`, the auto-close of a finished child, a deleted session, a closed window, a paired device's close, a hosted tab whose grace ended): `SidecarManager.dispose` waits for the tab's omps to exit (so an omp's own cleanup of its tools comes first) and then closes its tag (`#endEntry`). A turn's Stop ends nothing: the tab is still open.
  - **A quit ends nothing** (`frozen: quitApproved`): tabs come back at the next launch and a "Restart to update" must not take every open session's dev server with it. The tags stay in the file.
  - **The next launch** (`sweep`, called in `index.ts` once the saved tabs exist): every tag in the file is one the last launch left. Kept: a session with a tab in the restored layouts (desktop and paired web pages) or a marker of interrupted work (`interrupted-turns.json`, read before `TurnResume.launch` drops what it settles); the tab that starts on that session takes the tag over (`open`), so the session's processes are its own again and end with it. Ended at once: every other tag, also one with no session file (a first turn that was never written starts over). This is the cleanup after a crash or a forced quit, where no close ran. A tag of a tab this computer ran for a paired device waits `HOST_TAB_GRACE_MS` (the device may be reconnecting) and ends then unless a hosted tab holds its session.
  - **A restored tab closed before it ever started** has no tag of its own: the pool's `released` activity ends what the last launch left for its session (`sessionReleased`).
  - **Idle release leaves them** (the owner's condition for it is "nothing lost"): it gives back only an omp with no child process, the tab stays open, and the omp that wakes carries the same tag. What a quiet session left running shows in the `memory short` line instead.
- **What a kept session's commands left with a closed output path is reported** (the relaunch of 20 Nov 2026: a Playwright run's `next dev`, in a process group of its own, outlived the omp and the runner that read its output; each write failed with EPIPE, Next logged the failure, which failed again, and next-server spun at 100 % CPU and grew to 4.4 GB). For the tags the launch keeps, the sweep asks the core once (`procs.list` with `tags`, `keepArg` and `sampleMs`) which processes have their **output path closed**: standard output or error a pipe or socket a write to which fails, with what is known of its other end, the **peer** (`closed`, `open` or `unknown`). macOS `proc_pidfdinfo`: a pipe at EOF (peer closed); a stream socket that can send no more (`SS_CANTSENDMORE`), which XNU sets both when the peer closes (`unp_disconnect` also clears `SS_ISCONNECTED`) and when the process shuts its own end down for writing (`uipc_shutdown`, still connected, the peer alive and reading), so a Unix socket's peer is `closed` when disconnected and `open` when connected, any other family's `unknown`. Windows: the handles in the process's parameters, copied and asked `FilePipeLocalInformation`; the closing state comes only from the other end's last handle closing (no half-close of a pipe; ReactOS's NPFS sets it only in cleanup, `DisconnectNamedPipe` gives disconnected), so its peer is `closed`. Linux, tests and CI only, never. Of those it reads the TCP ports they listen on (macOS `lsof`, Windows `GetExtendedTcpTable`) and the CPU they use over `SPIN_SAMPLE_MS` (3 s), **spinning** at `SPIN_PERCENT` (half a core: the loop measured 99-100 % of a core, the same server with nothing to write 0 %). It writes one `output path closed` warning per tag to `gui-runtime.jsonl` and the tab that takes the tag over names them in the relaunch's continuation (interrupted-work › What a relaunch continues beyond the cut-off turn); both say only what was observed (`output path closed (peer open)`), never that a reader is gone. A process is named by pid, image name, start, ports, CPU and its working folder relative to the session's folder (`outside the session folder` otherwise), **never by its arguments** (a command line can hold tokens); the core never answers arguments. Only the one exception in the next bullet ends any of them. Cost: one detailed listing per launch for the kept tags, plus the 3 s sample only when one has a closed output path. Between a quit and the next launch nothing looks: a spinning process spins until then. Pinned by `session-processes.test.ts` (a chatty, a quiet listening and a busy file-writing process of a kept session; the exception and its peer condition) and the `procs/mod.rs` tests (which processes have a closed output path, their CPU and folder, no arguments answered; a socket shut down for writing reads peer `open` and `closed` once the peer closes, macOS; `only` by start).
- **The one exception: a process that keeps spinning on an output path whose other end is closed ends** (the owner's answer of 20 Nov 2026: "the app ends automatically a process whose output's other end is confirmed closed AND that keeps using CPU"; everything else above stays report-only): at the launch that keeps its session, a process whose peer is `closed` (never `open`, a path it closed itself, nor `unknown`) that measures at least `SPIN_PERCENT` in each of `SPIN_SAMPLES` (3) samples `SPIN_SAMPLE_GAP_MS` (30 s) apart, a minute in all, so a dev server busy compiling for a while is only reported, is ended by pid and start (`procs.end` `only`, which ends nothing whose pid now names a later process); one `ended` line in `gui-runtime.jsonl` and the continuation name it with every sample measured, never its arguments. Hidden pref `endSpinningOnClosedOutput` (default on, only a stored `false` turns it off; no Settings row, as Settings has no home for session processes).
- **Never the wrong process**:
  - A process started outside OMPdesk, or by another OMPdesk (another `userData`: a dev or test app), carries no tag of this file.
  - A tag is ended only after its tab is gone. **An end in flight keeps the scratch folder and the tag is never handed out again**: a reopened session gets a new tag. If the core cannot confirm the end, the tag stays in the journal. A surviving worker gets one retry after `RETRY_REMAINING_MS` (60 s); disk care and the next launch can try again. Disk care retries only tags already released, never a restored or hosted tab waiting to open. Taking a tag over clears its earlier release.
  - **Stock omp's own shared workers are stock's to end** (`STOCK_WORKER_ARG` `__omp_worker_`, sent as `keepArg`): a tagged process whose command line has an argument starting with it, and every live process under it, is never signalled. That is the project's service broker (`__omp_worker_daemon_broker`, started by the project's first omp with that omp's environment, so its services carry that tab's tag whoever asked for them): its services stop with the project's last omp, or stay while the person's `launch.persist` is on (models-accounts › Held stock defaults), as before. Also the other selectors of stock's `cli/worker-selectors.ts`: the LSP multiplexer, the blob broker, the embedding server, the updater.
  - A tag the app itself runs under (OMPdesk started from that session's shell) is refused whole by the core (`own`: the core or one of its ancestors carries it), and logged.
  - ai-memory's service is launchd's or the logon entry's, and its `setup` is started by main, isolated: neither is an omp's child, so neither carries a tag.
- **What it does not see**: a process that cleared its environment (`env -i`, `sudo`); a program the system started on the session's behalf instead of as its child (macOS `open`, a launchd job, a VM's XPC service: Docker Desktop's and the Android emulator's hypervisor helpers); on Windows a process this user may not read (elevated, protected) and one that removed the variable from its own live environment; scheduled `omp -p` runs, benchmarks and model setup, which carry no tag and end by themselves. **What it ends that a person may have come to use**: a program an agent's command started as a child is the session's, also a browser or editor (`start <url>`, `code .` on Windows, where the launch is a child; not on macOS, where `open` hands it to the system), and a daemon another session shares (`adb`, a Gradle daemon) goes with the tab that started it and starts again on its next use. Stock's own daily `omp gc --compress` carries the tag too and ends with the tab.
- **Cost**: nothing per sample: `procs.pressureRecord` scans for the `memory short` line only, `procs.end` once per released tab and per tag the launch sweeps. One Windows listing with every environment read took 90 ms (median of 20, 608 processes, 406 readable, the machine at 99 % CPU from other work): 55 ms the snapshot and handles, 33 ms the environments. A session that left nothing writes no log line; one that did writes one `session-processes` line (`ended`: why, folder, session file, device, how many, how many had to be killed, MB, names; `left` when something survived the kill; `not ended` and `refused…` as warnings).
- **Rejected**: a Windows job object per session (main spawns the launcher through node, so a job could only be assigned afterwards by another process, racing the launcher's own children, and a job cannot be found again after a relaunch without a name); a walk down the omp's process tree (it loses exactly the re-parented processes the report was about); `ps -E` (it cannot tell an argument from an environment entry).
- **Model-checked** by `formal/session-processes` (TLC; `skill://session-processes-verify`): only a tag whose tab was closed outside a quit or whose session did not come back is ended, an open tab never has its processes ended, nothing is left in the file at rest, a tag with running processes is never forgotten. Pinned by `session-processes.test.ts` (real processes through the real core: a tagged tree with a re-parented grandchild found and ended, another tab's and an untagged process untouched, stock's worker kept, a quit and the takeover, the launch sweep; the reopen, failed-end, frozen, released and hosted-grace cases on held ends), the Rust tests of `procs/mod.rs` (the same on each OS, SIGTERM before SIGKILL, `keepArg`, `own`, the parsers), `omp-launch.test.ts` (the variable is session-owned) and `e2e/session-processes.e2e.ts` (the built app on the fake omp: a detached child ends with its closed tab, another tab's stays).

### Control socket and the `ompdesk` CLI
- **The user's decision (30 Oct 2026)**: anything running on this computer (a terminal omp, a shell script, another agent CLI such as Claude Code or Codex, a subagent through bash) drives OMPdesk the way OMPdesk's own agents do with the `ompdesk_*` tools. Modelled on Herdr's external control surface (https://herdr.dev, Apache-2.0): JSON lines on a per-user socket, server-owned waits, `agent_blocked`, `events_lost`. No Herdr code is copied, so `THIRD_PARTY_NOTICES.txt` is unchanged; copying any would need its Apache-2.0 attribution there (`bun run gen:licenses`).
- Files: wire contract `src/shared/control-protocol.ts`; CLI `native/ompdesk/crates/cli` (Rust, binary `ompdesk`, shipped as `extraResources` `ompdesk-bin`; build, staging and packaging: native-rust). Server `native/ompdesk/crates/core/src/control/`: `endpoint.rs` folder, token and endpoint file, `listen.rs` Unix socket and Windows named pipe, `conn.rs` framing and auth, `router.rs` methods and waits, `events.rs` event ring, `link.rs` asks to main. Main `src/main/control-socket/`: `endpoint.ts` synchronous path naming and typed folder/token clients, `server.ts` the core client and backend relay, `backend.ts` the seam to `AgentControlRuntime`, `index.ts` `startControlSocket` (called from `ipc.ts`), `cli-install.ts` launchers and `env.ts` per-spawn plumbing.
- **One service**: a `tool` request is `AgentControlRuntime.runOutside(caller, tool, args)` → `AgentControl.run`, the same rules, tiers and cards as a host tool call; `credentials.read` and `cards.answer` stay `never`. Pinned by "a caller outside OMPdesk" in `host.test.ts`.
- **The outside caller** (`OutsideCaller`, `host.ts`): id `outside:<name>#<connection>`, one per socket connection. The name (hello `caller`, `OMPDESK_CALLER`, `--caller`, `[a-z0-9_-]{1,32}`, default `cli`) is the process's own claim, never an identity: another process claiming it owns none of the first's sessions or reports. Title `outside process "<name>" (self-declared)`; cwd the CLI's folder. It has no tab: `AgentControlHost.outsideCaller` gives the service a stand-in `ControlTab` (never listed), it acts through the front desktop window (`outsideWindow` = `windowManager.getTargetWindow()`; none open refuses), and the sessions it opens are its own (`#parents`: stop/close need no card, their `ompdesk_report`s reach it as `report` events) but get no pool opener (they sit in the sidebar like the person's), no review list, no auto-close and no provenance after a relaunch (ids starting `outside:` are excluded wherever a tab opener is expected). A closed connection releases its caller (`releaseOutside`); its sessions stay open. Its cards are native `dialog.showMessageBox` over that window (`confirmOutside`, `[OMPdesk]` title, detail "Outside process: <name> (self-declared)" / "외부 프로세스: <name> (자체 표기)", `CARD_TIMEOUT_MS`, no answer = no), one at a time per caller (`#outsideCards`). Whatever goes through the caller's own omp (stock settings, models, usage, MCP app actions, the app action journal note) answers that an outside caller has none (`#hostCommand`).
- **Endpoint** (`control/endpoint.rs`): `<userData>/control/` (mode 0700, a real folder owned by this uid, else refused) holds `token` (32 bytes of OS randomness as 64 lowercase hex, 0600) and `endpoint.json` (`{version, socket, pid}`, 0600; `pid` is main's). The token survives close and is reused unless damaged or exposed: folder or file had group or other bits, or the file is another user's (`prepareControlDir` reports a repair, `readOrCreateToken({exposed})`). Entropy read failure refuses startup; no fallback. The listener removes `endpoint.json` only while it still names this socket, also at stdin EOF. A killed core leaves a stale endpoint file and, on POSIX, socket; the next listener overwrites the endpoint and clears a dead socket. macOS/Linux socket `<dir>/control.sock` is bound inside the 0700 folder then chmodded 0600, without a process-wide umask that could affect other core requests. Past `sun_path` (103 bytes), only the socket moves to `<tmpdir>/ompdesk-<uid>-<hash>/` (same checks). A socket is replaced only when nothing answers on it (`ECONNREFUSED` or `ENOENT`); a live listener or a non-socket fails startup (`SocketInUse`). Close removes only the dev/inode made at bind; tokio never unlinks another process's file at close. Nothing listens on TCP.
- **A failed start is shown, not only logged** (`startControlSocket`, Orca row R21): the reason (the error's message, errno included) is kept for this launch (`controlSocketFailure`, IPC `control-socket:failure`, `host-admin`) and shown under the "OMPdesk control tools" switch in Settings › Tools & extensions (`AgentControlRow`, `data-control-socket-failure`; no modal), and written to `<control>/start-failure.txt` (`START_FAILURE_FILE`, 0600), which the CLI appends to its "not running" error (exit 3) when `endpoint.json` is missing. A start that succeeds removes the file. Pinned by `AgentControlRow.test.tsx` and the CLI's `says_why_the_socket_did_not_start`.
- **Windows pipe**: `\\.\pipe\ompdesk-<32 random hex>`, new each app launch, published only in `endpoint.json` under the user's `%APPDATA%`. The Rust listener keeps the default pipe DACL, as Node did, adds `FILE_FLAG_FIRST_PIPE_INSTANCE` on its first instance (an existing pipe refuses startup), and sets `PIPE_REJECT_REMOTE_CLIENTS` on every instance. The folder and files inherit the user's profile ACL; that ACL is not checked, as before. A core restart listens again at the same pipe name, so running sessions' `OMPDESK_SOCKET` still works. Nothing is answered before the token.
- **Auth and limits** (`control/conn.rs`): the first line must be `hello {token, protocol}` within 10 s and at most 64 KiB; a wrong or missing token, any other first request or another protocol is answered `unauthorized`/`protocol_mismatch` and the connection ends. At most 64 connections (the next is answered `unavailable` and closed) and 16 running requests per connection. Past that, or while queued output reaches 16 KiB, the server stops reading until a request answers or the output drains. The CLI sends the token only to a socket that is this user's alone: on POSIX the socket, its folder and token file must belong to its uid with no group or other bits, else exit 3 before any byte (`owner_only`, `crates/cli/src/endpoint.rs`).
- **Env, per spawn** (`env.ts`): main never puts the socket's address in `process.env`. `controlEnvFor(foreign)` gives this computer's own tabs (`SidecarOptions.controlEnv`, read per spawn) and their terminals (`terminalRequest`'s `env`, merged by the terminals worker) `OMPDESK_SOCKET` and `OMPDESK_CONTROL_DIR`; a tab run for a paired device (`origin`) or owned by the phone page (the pool factory's `web` flag) and its terminals get only `OMPDESK_CONTROL_OFF=1`, which the CLI refuses on (exit 3), so neither acts as an outside caller beyond its device's grants and `PeerQuota` (threat models in `multi-viewer-web.md` and `remote-devices.md`). `withoutControlEnv` strips what a login shell or a parent OMPdesk passed on, for omp spawns and the stock helper workers.
  - **The CLI refusal is not the host tools' state, and it is fixed per omp** (13 Nov 2026: a coordinating session saw "OMPdesk control is off in a session OMPdesk runs for another device" while its `xd://ompdesk_*` tools were gone). `controlEnvFor(origin !== undefined || web === true)` runs once per spawn (`sidecar-factory.ts`), with `web` = the window that acquired the tab (`SidecarPool.acquire`: `isWebWindow(win)`), so a session of this computer's own person that a phone page opened or restored while no desktop window held it keeps `OMPDESK_CONTROL_OFF=1` for the life of that omp, however the person views it later. That is the rule of the section above, not a bug: the socket acts through this computer's front window and its full grants, which no phone page's tab may borrow. The host tools (`ompdesk_session_send`, `_report`, `_result`, `ompdesk_app` sidebar actions) do not read this env: `SidecarManager.#hostTools` follows the Settings switch alone, they run for the tab that called them, and attaching a viewer (`attachViewer`, a hosted view) changes neither set. Only the lane's skipped `set_host_tools` (the Host tools bullet above) made the tools themselves vanish.
- **Waits** (`control/router.rs`, Herdr's `prompt_agent` mechanics re-implemented): `state` is `SessionState` from `sessionState` (`backend.ts`): `blocked` = the tools' `waits` (an ask or approval that is no sign-in, or a plan up for review: the renderer's `lib/attention.ts` `pendingAsks`) over `working` (busy or resuming), `starting`, `stopped`, `idle`. Each request asks main to watch before resolving a name. Main sends every lifecycle step with the visible sessions at that moment; the core dates the steps by their push sequence and keeps each wait's snapshots (`link.rs` `Watch`, `Glance`). `wait --until idle|blocked|done|any`; no `until` = settled (idle, blocked or stopped). `done` and `any` are edges: a turn end (any step for `any`) after the mark satisfies them, replayed. `idle`, `blocked` and settled are states: only the current state at a check matches, not a past lifecycle step. `send` refuses a blocked session unless `force`. With `wait`, its mark is main's last push as it enters the send tool, so activity heard between resolve and send does not count as the sent turn's. The gate passes if it was working already, a step after that mark shows working, blocked or a turn end, or its state now is working or blocked (a plan raises no step). Within 5 s (`start_wait_ms`) or the remaining total timeout if nearer, else `agent_prompt_stalled`. The final wait counts from that mark, so a turn end the gate consumed still ends `done`. If it was already working, the final wait counts from the receipt instead (an end while send was in flight belongs to the older turn), and idle just after such an end is held for 5 s unless a new step comes (the queued follow-up's gap). A follow-up folded into the ended turn settles after that hold. One total timeout covers send, gate and wait. Known limit: a message steered into a turn still running at receipt settles at that turn's end.
- **Events** (`control/events.rs`): `subscribe` starts live; `session_state`, `ask`, `turn_finished`, `session_closed`, and `report` only to its addressed caller; never a hidden session. A ring of 1 024 events, one cursor per subscriber; falling behind the oldest retained event gives one `events_lost` frame (count and resync hint: subscribe again, resync with `ompdesk sessions`/`state`) and ends the subscription, never a silent skip. `control/link.rs` turns main's activity forwarding on only while a wait or subscription needs it. Main answers `control` events through numbered `control.push` requests; their numbers preserve main's order across the core's concurrent request tasks. Main holds `control.closed` to notice a dead core and rebinds the listener; the disconnected callers are released and the new callers' decimal ids include a new incarnation, so no ownership is inherited across that restart.
- **CLI and PATH** (`cli-install.ts`, called from `index.ts`): every launch writes `<userData>/bin/ompdesk` (and `ompdesk.cmd` on Windows) running the app's `ompdesk` executable by its absolute path (`<resources>/ompdesk-bin/ompdesk[.exe]`; an unpacked run: `resources/ompdesk-bin/<platform>-<arch>/`) and appends that folder to `process.env.PATH` for everything OMPdesk spawns; a packaged, non-headless app also writes it into Bun's global bin (where `omp` is, so an outside terminal finds it), only over a missing file or one with its marker line. The CLI needs neither Bun nor omp on the machine. Exit codes 0 ok, 1 failed, 2 usage, 3 OMPdesk not running or refused; `--json` prints the raw result. An interrupt ends `events` with 0 and any other command at once.
- Tests: `control-socket/server.test.ts`, `router.test.ts` and `events.test.ts` run through the real core and real socket (Windows named pipe). They keep auth refusals, modes, ownership, stale sockets, env, send/wait gates, events, hidden sessions and report routing, and cover EOF cleanup and killed-core recovery. `control/captured.json` has the original TypeScript's connection, caller, wait, send, ring, number and path rows, replayed in Rust tests on a paused clock. Exact ring loss counts are covered there; the real socket suite derives loss from the delivered cursor because OS buffering differs. `cli.test.ts` runs the built CLI unchanged against the real server (caller, folder, stdin, JSON, exit codes, ownership); the CLI crate's tests cover flags, numbers, stdin, output, events, owner checks and a fake server end to end. Also `cli-install.test.ts`, "a caller outside OMPdesk" in `host.test.ts`, and `e2e/control-cli.e2e.ts` (launcher against the built app and fake omp).

### Heavy slots and `ompdesk check` (`native/ompdesk/crates/checks`, local commands of the CLI)
- **The owner's order (13 Nov 2026)**: "검사 한번이 2시간 20분인게 말이되냐 … ompdesk로 작업할때 이 부분도 해결되는것을 기본 내장해야함". Measured that day: one project's release check took 142 min (Playwright 115 min, 1 144 tests, one worker) and ran from scratch three times, the last after a 7-line change; a check died with an OMPdesk restart; heavy slots were glued by hand per project; tests put a keychain dialog and an installer error box on the owner's screen; checks took 22-77 % of tool time in this computer's sessions. One product feature, no setting, on for every project.
- **Local commands**: `run`, `heavy` and `check` are answered by the CLI itself before anything else (`ompdesk_checks::cli::dispatch`, called first in `crates/cli/src/main.rs`): they need no running OMPdesk, no control socket and no token, and they work under `OMPDESK_CONTROL_OFF` (a paired device's tab), in CI and in a plain terminal.
- **Heavy slots** (`heavy.rs`): one counting pool per user and computer, in a fixed folder (`$XDG_CACHE_HOME|~/.cache/ompdesk/heavy`, Windows `%LOCALAPPDATA%\ompdesk\heavy`; `OMPDESK_HEAVY_DIR` for tests), never per app profile, so a dev OMPdesk, the installed one and any script share it. A slot is an OS file lock (`flock`, `LockFileEx`) on `slot.<i>`, held for the holder's life: a holder that dies gives it back at once, nothing judges staleness. Waiters queue in order of a numbered ticket each keeps locked (`queue/`); a `--release` check may take the next free slot ahead of older ordinary checks once, after which the bypassed tickets are protected. Existing holds are not preempted. Older `--all` holds eventually get the whole pool; a dead waiter's ticket is removed by whoever finds its lock free. Size `pool_size`: min(⌊(GB − 8) ÷ 8⌋, ⌊cores ÷ 2⌋), 1 to 7 (`OMPDESK_HEAVY_SLOTS` overrides). `ompdesk run --heavy [--all] -- CMD` holds a slot while CMD runs (SIGTERM/SIGHUP to the holder are passed on, so the slot is never given back while CMD runs) and sets `OMPDESK_HEAVY_HELD=<holder pid>`, under which a nested heavy command runs inside its parent's slot. `ompdesk heavy hold [--all]` prints `held <slots>` and holds until stdin ends (how this repository's `scripts/lock-slots.ts` takes the pool); `ompdesk heavy status [--json]` lists holders and the queue.
- **Per-computer opt-out**: `ompdesk heavy limit off` removes the shared slot, queue and start-time disk threshold for this user's local checks and builds. `ompdesk heavy limit auto` restores them for subsequent admissions. The command neither cancels running work nor changes another machine. Updated waiters observe the switch; waiters already running an older CLI do not. Project builds still exclude simultaneous writes to their build output. The running low-disk emergency stop and result validation are independent of admission.
- **Disk** (`heavy.rs` `Volumes`, `watch.rs`; the owner's main session's call, 13 Nov 2026, after a Mac mini's system disk reached 116 MB free: a test whose loop printed an error line after a panic wrote 26 GB in ten minutes, OMPdesk's settings write failed with an OS error box and another session's check died). Opening a session is never held back (the main session's decision).
  - **Before it starts**, heavy work also waits while a volume it writes to has less free than `min_free`: a tenth of that volume, at least 10 GB and at most 20 GB (`OMPDESK_HEAVY_MIN_FREE_GB` overrides). The volumes are those of its folder, the temp folder it is given (`TMPDIR`; Windows `TEMP`/`TMP`) and every folder its arguments name (`--output …`, `--outputFile=/Volumes/BACKUP/…`, the nearest existing folder), each read where it lives, so work on an external disk is judged by that disk. The admitted waiter holds the line while the disk is low, so a later small command never starts on the space it waits for. The wait line names each low volume, its free space and what it needs; `ompdesk heavy status` lists every volume with free and total and says when new heavy work waits. Work already running is not cut by this rule.
  - **While it runs**, `ompdesk run --heavy` and `ompdesk check` read those volumes every 5 s: under `min_free` they say so once per crossing (on stderr, or in the check's log) with how fast free space falls and how much was written there since the command started; under `DANGER` (3 GB; `OMPDESK_HEAVY_DANGER_GB` for tests) they stop the command's tree (SIGTERM to the command and every process under it, read from `ps` parent links so a shell wrapper's children are signalled too, SIGKILL 10 s later to what is left; Windows `taskkill /T /F`), keep its log and results, and say why. A check stopped that way ends `error` whatever its exit code (a runner that exits 0 on SIGTERM is no pass), and no later run reuses it. `ompdesk heavy hold` does not know its holder's command, so it only warns.
  - **Output cap** (`Capped`): a check's stdout and stderr, and `run --heavy`'s when they go to a pipe or file (an agent, a log; a terminal sees everything), pass their first 32 MB, then keep only the last 8 MB, written at the end after a note of how many bytes were cut. Files a command writes itself are not capped; the running watch covers them.
- **The shim** for a project's own heavy script (the one line that makes `heavy-run.sh`-style scripts join the pool):
  ```sh
  #!/bin/sh
  if [ "$1" = --all ]; then shift; exec ompdesk run --heavy --all -- "$@"; fi; exec ompdesk run --heavy -- "$@"
  ```
- **`ompdesk check [--full] [--light] [--release] [--] CMD`** (`check.rs`): runs a test suite or check command. What it reuses, against the newest earlier run of the same command in the same folder whose files did not change while it ran:
  - **Inputs** (`inputs.rs`): every file of the checkout by content (SHA-256; a stat cache per checkout skips unchanged files), `node_modules` and build output included, so uncommitted edits count and HEAD is only shown, never compared; except `.git`, folders tagged `CACHEDIR.TAG` (cargo's `target/`) and, where git ignores them, cache and report folders (`CACHE_NAMES`). A symlink counts by its target text and by what it points to (a linked `node_modules` is read through; a link to a folder that holds it, or one already read through another link, is not walked again). Plus files the command names outside the checkout (a wrapper script), every environment variable but named terminal and OMPdesk plumbing (`volatile_env`: a tab's `OMP_GUI_SESSION_TAG`, the check's own nesting and control variables; every other `OMP_GUI_*`/`OMPDESK_*`, such as `OMP_GUI_REAL_WORK`, is an input, by hash), and the tools: OS and kernel, `node`, `bun`, for cargo `rustc` and `cargo`, and the CLI's own version with its reporters' hash (a changed check program reuses nothing).
  - A tracked `.ompdesk/checks.json` can declare `inputs` and `outputs` for an exact `cwd` and `argv`. Undeclared paths still count as inputs. A full pass is reusable only when its input digest and every declared output match; missing or changed outputs require a full run. Changing inputs during the command never becomes a reusable success just because the process exited 0.
  - **Nothing changed** (same digest): a run that passed with every result passed is reused whole (nothing runs); a pass that held a quarantined failure is not, so that test runs again. Otherwise its passes are reused and only what did not pass runs again: Playwright `--test-list-invert` of the passes, Vitest by test name (the failed files and `-t` with their full names) or, when a failed file names no failed test (it did not load, a hook failed), `--exclude` of the files that passed, Jest `--runTestsByPath` of every listed test file but those that passed, `cargo test -- --exact <failed>` after a run that reported every binary (`--no-fail-fast` is added to every cargo run for that). A plain command is reused only whole.
  - **Only test files changed** (files the earlier run recorded tests from, or new files named with a suffix those had, `.test.ts`, `.e2e.ts`): those files run in full, the other passes are reused. **Anything else changed** (product code, a test helper, config, a lockfile, the environment, a tool): everything runs. Unknown means full.
  - **Runner signals not trusted**, and why: Playwright `--only-changed` selects only changed test files and the test files importing them, so it never finds the e2e tests that exercise changed product code (server or browser). Vitest `--changed`/`related` follow the import graph, which misses what a test runs without importing: in this repository the bridge loaded by a real omp (`-e`), `e2e/sidecar-fixture.ts` as the fake omp, the native binaries. Playwright `--last-failed` and Jest `--onlyFailures` read the runner's own record of the last run of any command in that folder, which another command overwrites and which a cut-off run leaves incomplete. Mapping product code to tests needs coverage recorded per test (stage 3); until then the only narrowing is by the run's own recorded results.
  - **A filter cannot pass for a test**: each result the earlier run did not pass that this run was meant to run again must come back; one that is missing or reported skipped reads `missing` and fails the verdict. A test this run left out by name (reported `skipped` by a `-t` filter) keeps the result it reused.
  - **Provenance**: `verdict.txt` lists every result with `run now` or `reused from run <id> (<commit>, <time>), log <path>`; `verdict.json` the same for programs. The reporters (`reporters/*.{cjs,mjs}`, written into the store per hash) record each result as it ends, so a run cut off half way keeps what passed; Playwright's rides in `PW_TEST_REPORTER`, so a Playwright run inside any script is recorded.
  - **Flaky quarantine** (`flaky.rs`): a test that passed and failed on the same input digest (a rerun of the same inputs, or Playwright's retried `flaky` outcome) is quarantined per check; its failures do not fail the verdict and are always listed with pass and fail counts and the inputs it flaked on; `--release` fails while a quarantined test failed (or flaked) in that run. It leaves after 5 passes in a row on different inputs (`CLEAR_AFTER`, reason in `flaky.rs`).
  - Disk care expires generated input lists and stat caches after three days idle, even for a check never run again. It does not scan on command start. An identical digest can still reuse the verdict; different inputs need an available comparison list or a full run. The log, results, verdict and flaky history stay.
- **Survives a restart**: the foreground starts a detached runner through a middle process that exits at once (POSIX: own session; Windows: outside the console, group and job, on the desktop `ompdesk-checks` made with `CreateDesktop`, so a message box never reaches the person's desktop; never on the person's desktop: a desktop that cannot be made, or a runner that ends before it takes over, fails the run with the Windows exit status, `start_on_windows`) and follows its log. The runner journals every step in `<cache>/ompdesk/checks/runs/<id>/` (`run.json`, `log`, `results.jsonl`, `reused.jsonl`, `inputs.tsv`, `verdict.*`) and holds `alive` locked; a free `alive` with a running journal reads `killed`. Killing the starter's process tree leaves it running; `ompdesk check attach [id]` follows it again; starting the same check while one runs follows it only when its results answer the request (the same input digest as now, no `--full`, the same `--release`), else says why and starts another; `status`, `cancel` (a run still waiting for its slot leaves the queue and never starts its command; one about to start checks for the cancel once more). The runner keeps `OMP_GUI_SESSION_TAG`, so closing the tab still ends it (Session processes). It holds one heavy slot while the command runs and decides again if the inputs changed while it waited; a slot it cannot take (the pool folder cannot be written, a full disk refusing the queue's own files) ends the run as `error` without starting the command (fail closed, `crates/cli/tests/check_admission.rs`); `--light` takes none; a check inside another check's command runs as its plain child.
- **No window on a person's screen**: the command gets `CI=1`, `PLAYWRIGHT_HTML_OPEN=never`, `PW_TEST_HTML_REPORT_OPEN=never`, `BROWSER=none` unless set, and no `PWDEBUG`; Playwright already starts Chromium and Electron headless with `--use-mock-keychain` and `--password-store=basic`. macOS has no separate desktop: what remains is a keychain prompt from a test that reaches the user's own keychains. The guard: the runner reads `security list-keychains -d user` before and after the command and puts back a list the check changed, so a test's temporary keychain never stays in the search list; tests that could prompt still belong on a CI runner.
  - On Windows, the checks CLI starts ordinary children through `sys::child_command`. It sets `CREATE_NO_WINDOW` when the parent has no console, including in the detached runner: Windows Terminal can otherwise show a window on the person's desktop even for a program on `ompdesk-checks`. A child of a terminal keeps the existing console and its Ctrl-C handling.
- **`ompdesk checks wait [ID]` and `ompdesk checks status`** (`board.rs`; the local half of `docs/design/check-control.md` §6, whose §13 lists what of that design exists): local commands like the three above, both print JSON only. They exist so an agent never polls a check or reads its log for the result.
  - **`wait`** blocks until the run ends (without an id: this checkout's running run, else its newest) and prints the judgment (`Answer`): `verdict` (`green`, `red`, `unknown`), `commandExitCode`, `inputsStable`, `timing` (registered, queued, acquired, command start/end and finish; an unobserved time is null), `counts`, each failed test (`failed[]`: `test`, `firstError`, `knownFlaky`, `history`; 30 at most, the rest in `verdict.txt`), `blocksRelease` (a `--release` check that is not green), `reused` (`from`, `savedMin`), `next` (`land`, `fix`, `rerun-failed`, `wait`) and `notes`. It exits 0 green, 1 red, 4 unknown (2 usage). Run under bash `async: true`, its end wakes the session.
  - **Never green from results that do not hold**: a pass whose inputs changed while it ran, and a run that was cancelled, killed or stopped, answer `unknown` with the reason in `notes`.
  - **`firstError`** is the first line of the failure, colour codes removed, at most 300 characters, written by the reporters (`error` on a result's line, kept in `verdict.json` beside `counted`, which marks the results people count). A Node wrapper can carry structured Playwright results. With only Playwright text output, the reader keeps the failure location, error class and reported counts from its bounded tail; unstructured text never proves a pass. Without a diagnostic the note names the log.
  - **`next`**: `fix` for a red run, except one whose failures are all quarantined tests (a `--release` check), which gets `rerun-failed` for the first two runs of one input set (`RERUN_CAP`) and `fix` after, the count in `notes`. `ompdesk check` itself never reruns by itself.
  - **`status`** prints `pools` (this computer's heavy slots as one pool: `limit`, `running`, `queued`, `oldestWaitMs`, `lowDisk`, holders and waiters) and `runs` (every run not finished and the newest 20: `id`, `state`, `lane` `release` or `local`, `command`, `folder`, `session`, `mine`, timing, last progress and safe cancellation guidance, `summary`).
  - **Who started a run**: `ompdesk check` records the tab's `OMP_GUI_SESSION_TAG` as the run's `session` (none from a plain terminal, which is the person). **A session cancels only a run it started** (`may_cancel`): `ompdesk check cancel` from a session refuses another session's run and a terminal's, naming who started it; a terminal cancels any.
- **Agents use it by default**: the `check-runs` prompt section (`resources/gui-bridge/modes/check-runs-core.ts`, every session) says the three rules (checks through `ompdesk check`, a check's result from `ompdesk checks wait` and green only from a green answer, other heavy commands through `ompdesk run --heavy`); `command-verdict-core.ts` reads `ompdesk check --` and `ompdesk run --heavy --` as wrappers, so the work card and Pace see the check inside; the Pace line adds `N min saved by reuse` from each run's last line (`reuse saved about … (<n> s)`, once per run id). The work board's check row names a release check's gate and says when the session is woken (work-board.md › Current work).

### App control (`ompdesk_app_list`, `ompdesk_app`)
- Changes the app itself in main; arguments are validated against the action's schema. `agentctl/app/catalog.rs` actions, `agentctl/app/settings.rs` one `settings.<row>` action per Settings row, `agentctl/app/control.rs` the one dispatch point (`app-control-test-rig.ts` is the TypeScript parity rig of its suites, no production caller), `agentctl/app/guard.rs` and `agentctl/app/channels.rs` the agent's own default-deny risk tables. `AGENT_CHANNELS` is typed over every `IpcChannel`: a new channel does not compile until it is `never` with a reason or lists the actions that call it. `IPC_POLICY` is the web device's table, not the agent's.
- `read`/`change` are free; a change is journaled in the caller's session (`agent_control_note`) and shown as a quiet toast with one-step undo when a previous value exists (`AGENT_CONTROL_APP` → `lib/agent-app.ts`, applied live).
- `sensitive` raises no card while full control is on. With it off, it raises the same `[OMPdesk]` card only while `agentControlManage` (default on) is off, **except the actions whose `manage` rule is `always`** (`ManageRule` in `agentctl/app/settings.rs`, a field of `AppAction` and of a Settings row): every `sensitive` action must decide `{ lifts: reason }` or `{ always: reason, when? }`; `app-catalog.test.ts` fails on one that does not, and `app-control.test.ts` pins the `always` list (`agent_power.set`, `fullOnly`, is pinned on its own). `always` asks whatever the manage switch says because the action erases data (`sessions.delete`, `memory.purge`, `memory.delete_page`, `memory.sweep`), runs code (`extensions.install_plugin`, `extensions.install_mcp`, `extensions.mcp_use`), touches credentials or traffic (`accounts.github_sign_in`, `accounts.provider_sign_in`, `extensions.mcp_sign_in`, `settings.proxy`), exposes or connects the computer (`mobile_web.set_enabled` when turning it on, `remote.connect`, `remote.unblock`, `remote.set_allowed_users`) or ends running work (`updates.apply`, `app.quit`). The rest lift (`updates.check`, the four auto-update switches, `rotation`, `remote.block`); an `undo` of a setting asks by its row's rule. `remote.list_tailnet` (read) lists the tailnet's computers for `remote.connect`. MCP servers: see Panels, sidebar and work views › MCP servers.

### Worker contract
- `#openOne` sends each child `agent_control_worker {from}` (local handler → bridge `agent_control.worker`, free in `quota-commands.ts`) once ready and before its first prompt. The child journals one `ompdesk.worker` custom entry; `resources/gui-bridge/agent-control.ts` registers the `ompdesk-worker` prompt section (`registerPromptSection`), appending `WORKER_CONTRACT` for the main agent of a session whose branch holds that entry.

- **The done report is main's job**, so a worker spends no model requests on a report its opener gets anyway. `AgentControl.#autoDone` (`service.ts`, run in `autoClose`'s pass before the close decision) sends the opener a `done` report through `#report` (custody line, MailOutbox, dedupe id, pickup, `aside` + turn) when an agent-opened child's turn ended `ok`, idle and settled, its last answer ends with a `Result` line (`ok` or `problem`), it has no `done` or `review` to the opener on its current dispatch (an earlier progress or note does not count), and no question or blocker of its waits for the opener's answer (`Mailbox` `waiting`, cleared by the opener's next send; a done would read the decision gate as settled). `#autoDoneFor` keeps a failed post from being retried (the MailOutbox still delivers what it was handed). Text is the final answer cut at `MESSAGE_MAX_CHARS`. Never for a failed or stopped turn, a child the person typed into, or a dispatch already reported (a child that calls `ompdesk_report` done itself yields one report); a turn with no verdict line keeps `#nudgeSilent`. **A child a relaunch restored** gets it once a turn of this launch ended (`lastRun`): its dispatch is read back from its journal, its journal's own `done` since its last prompt (`transcriptEnding.reportedDone`) stands for the report, and the report goes to the tab holding the opener's session now (`#openerOf` → `openedBySession`); one restored and not run this launch is skipped (main already told its opener). - **Where a branch lands** (`branchFacts`/`landingFacts`, one rule): the parent checkout's HEAD and the upstream its branch tracks (`<branch>@{upstream}`, else `refs/remotes/origin/HEAD`; refs as last fetched, never fetches, never touches the parent checkout). Agents push their own work (`git push origin HEAD:main`) while the parent's local main stays behind, so a tip in either has **landed** (`BranchFacts.merged`) and its diff is measured from that tip (only uncommitted work is left). An unlanded branch is measured from its merge-base with the upstream when the upstream holds the parent's HEAD, else with the parent's HEAD, so a stale local main never lends a child the upstream's newer commits. `BranchFacts.commitsBehind` counts the commits of that same target (`rev-list --count <tip>..<target>`) the tip lacks: 0 once the branch's own work landed, counted for an untouched branch (its tip still where its reflog says it was made), so the open receipt of a worktree child says `the worktree starts N commits behind <base>` when its `base` was older than where it lands (a paired host older than the field leaves it out: 0).

### Mailbox (`ompdesk_report`)
- A session another session opened reports with `ompdesk_report` (`kind` progress | done | blocked | question | review | note, `text`, `files`, `checks`, `to` a sibling, `dispatch`, `id`). `mail.ts` holds the rules (`Mailbox`, `deliveryFor`, `mailText`); `service.ts` `#report` routes: the opener by `AgentControlHost.parentOf` (this launch's `#parents`, else `IpcTabInfo.openedBy`, else the tab holding `openedBySession`); a sibling only under the same opener, written as `note`; any session to one working in the same checkout or repository (`AgentControlHost.checkoutPeers`, see Sessions sharing a checkout), question/blocked kept, every other kind written as `note`; nobody else. Decision gates go to the parent and the person and are never auto-resolved.
- Delivery is ONE stock custom message in the receiver (`agent_control_mail` → bridge `agent_control.mail` → `pi.sendMessage`, customType `ompdesk.mail` from `resources/gui-bridge/agent-control-contracts.ts`): question/blocked/done/review `aside` + `triggerTurn` (an idle receiver starts a turn, except in plan mode or after the person's Stop, where stock folds it into context); progress/note no turn (`triggerTurn: false`, shown at once when idle). Progress from one sender is coalesced for `MAIL_COALESCE_MS` (2 s, latest wins, `merged` counts the rest); any other report supersedes pending progress.
- **Every report reaches a busy receiver during its turn**. Stock's `aside` is queued and injected at the next step boundary without cutting the tool batch and ends an interruptible `wait` (measured on omp 18.18.9: stock alone waits for the running call to end, and a shell backgrounds itself only after `bash.autoBackground.thresholdMs`, 60 s). **A report that asks for a turn makes a running shell step aside at once**: at each main run's start the bridge wraps the agent's `hasIrcInterrupts` peek (`resources/gui-bridge/agent-control.ts` `watchAsides`/`interruptFor`, touchpoint B63), so a question, blocked, done or review report (and a session's message, below) raises stock's cooperative steering signal (source irc): a running `bash` or `eval` backgrounds itself and the report is read at the next step. ### CI results of a session's pushes
- **A session that pushed to GitHub hears how CI went, between turns, without a new turn** (Orca I1–I12). `resources/gui-bridge/modes/ci-watch.ts` (rules `ci-watch-core.ts`, contracts `ci-watch-contracts.ts`, capability `ciWatch`) watches the `bash` calls of every agent of the omp through `tool_execution_start`/`tool_execution_end` only (no `tool_result` handler: waste-guards.md › What the `tool_result` hook costs): a command with `git push` (not `--dry-run`) or `gh pr create` is read back from its output text. A push's `To <remote>` line and its ref lines give `{host, repo, branch, sha?}` per branch updated, new or forced; rejected (`!`), up-to-date (`=`), deleted (`-`) refs and tags are skipped. A `gh pr create` output's PR URL gives `{host, repo, pr}`. Only hosts gh serves are kept: github.com and `defaultGhHost()` (`GH_HOST`); a push to any other host is no watch, because no host config of gh is read and a guess would poll a host gh cannot reach.
- Each detection is journaled as `ompdesk-ci-watch` `{id, host, repo, branch?, sha?, pr?, at}` (a custom entry: not shown, not in the model's context); an ended watch adds `ompdesk-ci-watch-end` `{id, reason}` (`delivered`, `no_ci`, `superseded`, `expired`). The bridge's first load and every `session_start`/`session_switch` arm again every watch of the branch younger than 24 h with no end entry and no `ompdesk-ci` message (`pendingWatches`), so a relaunch keeps watching.
- **Stock does the GitHub work** (`tools/gh-run-watch`: `fetchRunsForCommit`, `getRunCollectionOutcome`, `getRunSnapshotOutcome`, `isFailedJob`, `resolveGitHubBranchHead`, `GH_RATE_LIMIT_ERROR_PATTERN`; `tools/gh-common`: `parsePullRequestUrl`, `parseRepoRef`, `ghApiHostArgs`, `defaultGhHost`, `GITHUB_HOST`; `utils/github` `github.json` for a PR's head (`repos/R/pulls/N`) and an abbreviated sha (`repos/R/commits/<sha>`)), imported at the first push and listed in `REQUIREMENTS`. One engine per omp, on the main session (the first `install`; a subagent's rebinding only adds the detection hooks).
- Cadence: first read 30 s after the push, then every 60 s while runs are pending; a failed read waits 60 s doubling to 15 min, a rate-limited one 5 min. Ends: a settled outcome is delivered; no workflow run 10 min after the push is `no_ci` (a repository without Actions gets nothing); a newer watch of the same repo and branch makes an older one `superseded` 2 h later (still read until then); 24 h after the push `expired`. Timers are unref'd and stop at `session_shutdown`.
- **Delivery is once per watch and once per commit**: before sending, the branch must hold no `ompdesk-ci` message with that id or for that repo and full sha (a push and the PR made of it). Idle, `pi.sendMessage({customType: "ompdesk-ci", content, display: true, details}, {triggerTurn: false})`, which stock shows and journals at once with no turn; while a turn runs the result is held and goes after `agent_end` once the session is idle. `content` is what the model reads with the next turn (`CI passed for o/r@abc1234 (main).`, `CI failed for o/r@abc1234 (main): <jobs, at most 5>. <run url>`); `details` `CiResultDetails`. The transcript draws it as `chat/CiNote.tsx`: one muted line, a success or danger icon, failed jobs and "Open run" (`openExternal`), `data-ci-note=<outcome>`; malformed details draw nothing.

### Sessions sharing a checkout
- The user's rule: sessions working in the same project folder at the same time know of each other and talk instead of breaking each other's work (without it, one session's work lands in another's commit through `git add -A` or a commit without paths, a shared formatter rewrites the other's files, and `git stash` swaps work across worktrees; guard plus messaging settles even same-file work). Ignored files (`.env`, `dist/`) are never in `git status`, so they are never claims: known limit.
  - **Two kinds of path steps** (the owner's decision, so two sessions that both changed a file are never deadlocked). A *take* (`git add`, `git commit -- paths`) is allowed for a file this session changed too: the overlap notice already asks for a note first. A *drop* (`checkout`/`restore`/`reset --`/`clean -f`/`rm`/`mv`/`checkout-index` of paths, a whole-file write or a delete from any tool) stays refused while a peer holds the file. `git stash` stays refused whatever the files (one stack for every worktree). Write-like targets that are build output (`*.log`/`*.out`/`*.tmp`/`*.pid`/`*.err`, `dist/`, `coverage/`, `node_modules/`, `.cache/`, `test-results/`, …) are never refused. An append (`>>`, `tee -a`) is a line edit: notice, never a refusal. A formatter or fixer (`prettier --write`, `biome format/check --write`, `eslint --fix`, `ruff format`, `black`, `gofmt -w`, `cargo fmt`, …, also behind `npx`/`bunx`/`pnpm dlx`/`bun x`) is an edit of the file it names and a `<folder>/**` replace when it names a folder, a glob or nothing (so it is refused when a peer holds a file there); `--check`/`-l` runs are not.
  - **More git steps judged** (`GIT_RULES`): worktree scope `merge` (not `--ff-only`), `pull` (not `--ff-only`), `rebase`, `cherry-pick`, `revert`, `am` (their `--abort`/`--continue`/`--skip`/`--quit` and `--show-current-patch` pass), `apply` (unless only `--check`/`--stat`/`--numstat`/`--summary`), `bisect` (not `reset`/`log`/`view`), `checkout-index --all`, `symbolic-ref HEAD <ref>`, `commit -a`, `commit --amend`, `commit -i`/`--include`, a commit without paths, `checkout`/`switch` of a branch, `reset --hard` and **any `reset <revision>`** (a word that names no existing file is a revision; `HEAD~N`, a hash, `origin/main`, `@{u}`, a tag), `clean -f` without paths; paths scope: `add` (also `-p`/`-i`/`-e` and any word holding `$` or a backtick: a substituted list is read as broad), `commit` with paths, `checkout --`/`checkout <existing file>`/`checkout -p`, `restore`, `reset --`, `clean -f -- paths`, `rm`, `mv`; short flag clusters take their value (`-vm msg`, `-sm`, `-mmsg`), so a message is never read as a path. Scope `worktrees`: `worktree remove|move` of a repo peer's worktree, or of one a same-worktree peer works in. A branch this session created (`git branch <name>`, `checkout -b`, `switch -c`, `worktree add -b`) it may delete or move; nobody else's. Stash list/show/`--help` pass.

A git run whose folder is inside such a worktree (`git -C <there> stash`, `cd <there> && git reset --hard`) is judged like one in this checkout, against that peer; a write, `rm` or `checkout --` of its uncommitted file there is refused. Writes into this checkout's own spelling of a repo peer's file stay a notice ("will conflict when the branches merge"), never a refusal. A hidden repo peer's worktree stays a known limit.

The ledger drops a claim only when its edit stamp (`CheckoutStatus.stamps`, raised by every call that changes it) is the one main saw, no running call writes it and the retire carries this load's `instance` (`retireFrom`; a restarted omp numbers stamps anew), so a change made after that read stays claimed, and a fresh edit claims a retired file anew. A successful git run in the call that makes files clean (`git commit -- paths`, `restore`, `checkout -- paths`, `git stash push -- paths`) also releases the named own claims and asks main to read (`checkout_files`), so a peer is not held off by a stale claim; which of them it keeps is F4 below. The claims are never capped (up to `CLAIMS_MAX` = 2000; only what peers display is cut).
  - **Claims survive the omp.** The bridge journals its claims as a custom entry (`ompdesk.checkout-claims`, written when the set of files changes at most every 15 s, at every `agent_end` and at `session_shutdown`; nothing when the set is what the journal holds) and reads it back on `session_start` and `session_switch` (a switch takes the new session's journal, or none), so a restart or relaunch keeps protecting uncommitted work; main's next pass retires whatever git no longer lists (it asks at once: `checkout_files` after a restore). **An entry is a delta** (`{front, removed, at}`: the files that joined or were claimed again, newest first, and the files that left) or **a whole set** (`{files, stamps, at}`; every entry before 20 Nov 2026 is one); `nextClaimsEntry` in `modes/checkout-claims.ts` decides: whole when 64 deltas (`CLAIMS_FULL_EVERY`) came since the last whole one or the change is no smaller than the set. **A load reads the branch's journal back to its newest whole set and replays the deltas after it** (`journaledClaims` → `replayClaims`, the same module as `ClaimBook.restore`), never the newest entry alone, which for a delta restores nothing and would lose every claim on a relaunch. Refused: absolute paths, `..`, `.git`, `!`, any match whose real parent leaves the checkout. A symlink inside a copied folder is recreated only when it points inside; one written with an absolute path into the main checkout points at the worktree's own copy once the worktree has one (a tracked file, or one the seed copied; `point_links_at_worktree`), else keeps the main checkout's (a shared store); **on Windows a file link is copied (a file symlink there needs Developer Mode or admin, and OMPdesk never requires one) and a folder link becomes a junction** (`worktree-seed.test.ts` "copies an ignored file link on Windows"; tests that make a file symlink use `itWithFileSymlinks` from `src/main/test-symlinks.ts`, skipped where the OS refuses). Budget: `SEED_MAX_FILES` 10,000 always, `SEED_MAX_BYTES` 50 MB only where the filesystem cannot clone, and 60 s to start new entries (`SEED_BUDGET_MS`, sent with the request); what does not fit is skipped as `budget`. Every file is first asked as a clone (APFS `clonefile`, Linux `FICLONE` on btrfs and XFS; Windows has none); if that works (`WorktreeSeedReport.cloned`, `describePreparation` adds "(reflink)") every later file is a clone too and the byte cap is off; a clone that fails (the first file: a volume without reflinks; a later one: a file on another mount) is copied plainly and the cap applies from there over what took real disk (a file over it is then skipped; `cloned` reports only a seed that cloned every file). `seedWorktree`'s optional `pretendClones` (how many files clone before the volume refuses) lets tests stand in for a volume. Existing files never overwritten; every skip reported (`WorktreeSeedReport.skipped`). **The seed writes only in the new worktree and only reads the main checkout**: every create, link and removal takes a `Place`, which only `Worktree::place` makes after it checked the path (no `..`, no absolute path, on Windows no `:` and no part ending in `.` or a space, the nearest existing folder a real folder whose real path is the worktree or inside it; a refusal is the skip `destination_outside`). Pinned by the Rust test `writes_only_in_the_worktree_and_leaves_everything_else_as_it_was` (a `..` pattern, an absolute one, links and junctions out of the main checkout and out of the worktree).
- Then `.ompdesk/worktree-setup` (`.cmd` on Windows), only when it exists in the new worktree or the main checkout (the core looks and names the log: `git.worktreeHook`), runs in the worktree under the setup supervisor (`/bin/sh <file>`, env `OMPDESK_ROOT_PATH`/`OMPDESK_WORKTREE_PATH`, `SETUP_TIMEOUT_MS` 120 s, process tree killed at the timeout and its exit code then ignored, output in `<worktree git dir>/ompdesk-worktree-setup.log`). A failure is reported in `RpcWorktreeCreateResult.setup`, never fatal. **Merge hooks** (`runWorktreeHook`, the same lookup, supervisor, timeout and tail; `WORKTREE_HOOK_SCRIPTS`; env adds `OMPDESK_HOOK`; log `ompdesk-worktree-<hook>.log`): `.ompdesk/worktree-pre-merge` runs in the child's worktree after the checks and the conflict prediction and before `git merge`: a non-zero exit or timeout returns `MergeOutcome {reason: "hook"}` and no merge starts (`#runMerge` fails with the script, exit, worktree and output tail); `.ompdesk/worktree-post-merge` runs in the parent checkout after the merge commit and never undoes it (a failure is `postMerge` on the outcome, appended to the success text). Both run on the computer holding the worktree (a paired host's `host.git.merge` calls `mergeBranch` there). `ompdesk_merge`'s answer budget gains `MERGE_HOOKS_BUDGET_MS` (2 × `SETUP_TIMEOUT_MS`) on the link request (`host.ts` `#git`); a local merge has no RPC deadline of its own. There is no merge button (the board has no review section). **A hook's script runs in main, not in the core** (native-rust › 2i says why): a hook needs its whole tree ended at its timeout and must never outlive the app, and on POSIX only the setup supervisor's own process beside the command gives both.
- The dialog toasts both (`announcePreparation`, `worktree.seed*`/`worktree.setup*`); `ompdesk_session_open` adds `describePreparation` to its notes. `worktree_create`'s budget includes it and the base fetch below (`WORKTREE_PREPARE_BUDGET_MS`; renderer, agent-control and Autopilot wait 1 260 s, `WORKTREE_COMMAND_BUDGETS_MS.worktree_create`). Pinned by `worktree-seed.test.ts` (real temp repos through the real core; a `.cmd` hook on Windows) and the Rust tests of `git/seed.rs`.
- **A `default`-based worktree starts at the fresh remote tip** (Orca W64–W66, H171–H172; the owner's approval of 25 Nov 2026): `plan` (`git.worktreePlan`) with base `default` and `origin/HEAD` naming a branch first runs `git fetch --quiet --no-tags origin <branch>` from the main checkout (60 s; `GIT_TERMINAL_PROMPT=0` from main's runner), at most once per repository in 30 s (a process-wide map; a create that finds a fetch of the same repository under way waits for it and skips its own). Only the remote-tracking ref moves; no local branch and no checkout is written. A failed or timed-out fetch never fails the create: the worktree is cut from the local ref and the result says why. The result's `base` (`{ref, fetched, behind, subjects, error?}`; absent for `HEAD` or a named ref, so Autopilot's `HEAD` never fetches) reaches the dialog's toast (`worktree.base*`, a warning when the fetch failed) and `describePreparation` (`origin/main fetched: N new commit(s) (…)`, `… not fetched (<error>); cut from the local copy`). The worktree dialog fetches the same way when it opens (`worktree_prefetch` → `git.worktreePrefetch`, its answer ignored), so the create a moment later skips its own. Pinned by the Rust tests of `git/worktree.rs` (a bare origin pushed after the clone) and `worktree.test.ts`.
- **A retried create returns the same worktree** (Orca R102): the new task sheet's create carries the task's id as its `requestId`, and its row's Retry sends it again; a paired device's `host.git.worktreeCreate` carries its own, keyed by the device. `createWorktree` keeps `{caller}:{requestId}` → the create in flight or its result for 10 minutes: the same key with the same arguments gets that answer (so a create that runs the setup hook runs it once; the new task sheet runs it in its own `worktree_prepare` step, which a Retry of that step runs again), the same key with other arguments is refused `invalid_request`, a failed create is forgotten so a retry runs again. No id, no change. Pinned by `worktree.test.ts` and `WorktreeDialog.test.tsx`.
- **The new task sheet** (Orca FB76/79/81/17/40, 26 Nov 2026; `dialogs/WorktreeDialog.tsx`, `stores/new-tasks.ts`, `layout/sidebar/NewTaskRows.tsx`): one sheet picks the computer (this one or an online paired host, whose worktree commands go through a tab of that host), the project, the first message and its files, a worktree of its own or not, its name, base (`HEAD`, `default` or any ref) and sparse preset. An empty name is the first message's title from the session's title model (bridge `suggest_title`, the ✨ button too); without one it is `task-<id>`, and that branch takes the session's first title while never published (`worktree_rename_branch`, core `rename_unpushed`, FS91: still checked out, no upstream, no remote-tracking ref, and no remote whose `ls-remote` names it, an unreadable remote counting as one that does; checked right before `git branch -m` under the lock the Changes panel's push takes in that checkout, and again after it, because an agent's own `git push` takes no lock: a push that landed in between puts the old name back; pinned by the `rename_unpushed` tests in `worktree.rs`). - **Sparse presets, parallel checkout, recorded folders.** `.ompdesk/sparse` in the main checkout names presets (`[name]` then folders, cone mode; core `git/sparse.rs`), and a create with `sparse` checks out only those (`worktree add --no-checkout`, `sparse-checkout init --cone`, `set`, `checkout`; a failure removes the worktree and a branch it made). `worktree add` and that checkout get `-c checkout.workers=4` while the person set no `checkout.workers` (C7-30). ### Worktree names
- Files: `shared/project-origin.ts` (rules), `main/local/git/origin.ts` (git reads), `renderer/lib/project-origin.ts` (`useProjectNames`), `stores/project-origins.ts`, channel `project-origin:get` = `window.omp.projectOrigins.get(cwds)`. A linked worktree's folder (`~/.omp/wt/gui-<name>-<hash7>`) never shows as a project name.
- Git alone says what it is: `--git-common-dir` names the main checkout (`<main>/.git`, else the first `git worktree list` entry for a bare or relocated dir); `--git-dir` ≠ common dir marks a linked worktree; the branch gives its kind (`autopilot/…` → "오토파일럿"/Autopilot, `omp/agent/…` → "병렬 작업"/Parallel work, or the child's title where a one-line `project · title` is shown; any other branch shows as itself).
- No new store: main caches each cwd for 30 s (5 s when git cannot place it); the renderer asks once per cwd and retries an unknown one after 10 s. A lookup that fails (no answer: the computer restarting, a dropped link) is no unknown: the folder keeps what was known and the store asks again by itself every 2 s until one answers (`stores/project-origins.ts` `RETRY_FAILED_MS`; a null would hide a worktree's rows as a removed folder; `project-origins.test.ts`). A folder git cannot place (removed worktree, not a repository, a paired host's path) shows its own name with the `gui-…-<hash7>` dressing stripped.
- Surfaces: in the sidebar a linked worktree's sessions are **rows of their project's own group, never a group of their own** (the user's rule): in the project's order (pins, then recency), each marked at the row's end by what it is for (`data-sidebar-worktree`: `Rocket` for `autopilot`, `GitBranch` for `agent` and a user's own branch), the kind's word (`Autopilot`/`Parallel work`, else the branch) in the row's tooltip and screen-reader text. A project whose own folder has no session gets its group from its worktrees' sessions, keyed and named by the main checkout (its `+` starts there), never by the worktree. The group header and its `+` are the project's only; phone and tablet the same. Title bar and pane header breadcrumb `acme-web › Autopilot › <title>` (`data-titlebar-worktree`, `data-pane-worktree`; an Autopilot run shows the rocket alone, its word for screen readers); work board head `acme-web · Parallel work` (`data-board-project`; a run's is `acme-web` and the rocket, the word for screen readers); window title `<name> — acme-web · Autopilot`; an untitled worktree tab chip reads from `IpcTabWorktree` (`baseCwd` + branch, no git); session and workspace pickers. **A new surface that shows a cwd's folder name goes through `useProjectNames`, never `basename`.**
- An Autopilot run's children (`autopilot/<run>-c<N>-<area>`, `autopilotRunOf`) are no rows of the project's list of their own: they sit right under the run's row, newest first, one step in and with no mark (`data-session-run-child`; `runParentOf` in `Sidebar.tsx`, from the branch git reports or, while git cannot place a new child worktree, the child tab's `worktree.baseCwd`). Parallel work sessions nest under their opener as family rows when the opener is listed (see Sidebar families), else are plain marked rows of the project.
- A session another agent opened (`ompdesk_session_open`, an Autopilot child) reads as its task until stock names it: `agentTaskTitle` (`shared/agent-control.ts`: the body's `Title:` line by `assignmentTitle`, else its first line) of the indexed first message in `sessionDisplayTitle`, and before the index lists it the tab's `task` (`IpcTabInfo.task`), never "New session". The task rides the spawn (`SpawnRequest.task` → `IpcSpawnTabPayload.task` → `SidecarPool.acquire`), so the tab's first status already carries it (set after the spawn, a phone's row would read "New session" for a frame). Only a tab that already exists (one a relaunch restored, named from its saved session by `#nameUntitled`) gets its task afterwards (`SidecarPool.setTabTask`). Pinned by `sidecar-pool.test.ts` ("from the first status any window hears") and `agent-control/host.test.ts`.
