## Settings, layout and look

### Settings layout and rows
- Sections (`settings-catalog.ts` `SETTINGS_NAV`; one name per section in en/ko and the native menu): **App** General (language, notifications, profile, window, GitHub account; Advanced: window placement (default side panel, panel edge, terminal shell) and proxy), Appearance & input (Advanced: follow-agent-theme, paste threshold), Keyboard shortcuts; **Agent** Models & accounts, Agent behavior (Advanced opens with the two auto-panel rows, then the stock groups), Memory (see The Memory page), Tools & extensions, Permissions & security, Projects & launch, Schedules; **System** Devices & connections, Updates & about (versions plus This computer, the machine setup list), Other settings. Older names ("Models & providers", "General › This computer", "Settings › SSH") mean these.
- **Minimal settings, maximum automation** (the user's rule): a setting exists only where people really differ; what has one right answer is automatic; an action is never a setting. A merged or removed setting's stored value is carried once by the core's prefs migration (`native/ompdesk/crates/core/src/prefs/retired.rs`, run on each read of prefs.json from disk: `MERGES` decide the new value, `RETIRED` deletes the old keys; pinned by `retired-prefs.test.ts`). Current state:
  - Thinking: hidden / collapsed / expanded is one choice (`ThinkingDisplayRow.tsx`) over the two prefs it writes, `displayPreferences.hideThinkingBlock` (⌃T, follows omp until chosen) and `thinkingExpanded`; stored values read as hidden if hiding is on, else expanded if expanding is on, else collapsed; hiding keeps the open state for ⌃T.
  - A theme is one of five sets plus one Follow system / Light / Dark choice (Themes below): no card per theme and no System pair selects.
  - The run state in the window title and progress on the app icon are always on (no `titleState`/`showProgress`); across windows one waiting on the person outranks one working, as inside a window (the shell's `tray.rs`: `progress`, `loudest`; the tray's words are `tauri-shell/src/native_labels.json`).
  - Sidebar shortcut pins and nav rows are set on the sidebar (Help › Customize sidebar… sheet `SidebarPinsSheet`, a pinned row's context menu Unpin, a nav row's Hide from sidebar), not in Settings.
  - Agent behavior has no Goal/Autopilot/open-agents action rows (they are the Run chip's, the palette's and the menus').
  - The GitHub update token row shows only while the updater is `auth-required` or a token is stored.
  - One "Keep tools up to date" (`toolsAutoUpdate`, on unless all three old switches were off) covers omp, tool CLIs and extensions.
  - One "Approve new devices on this computer" (`mobileWeb.confirmNewDevices`, on if either old switch was) covers phones and computers.
  - Notifications: "Send a test" is an action on the Notifications row (desktop only; `system:notify-test` answers shown/failed/unsupported, silence for 1.5 s reads as shown because macOS cannot report a refused banner and Electron cannot read its permission there), its result under the row with "Open notification settings" (`system:notify-settings`). The sound row carries the tone `Select` (`notificationTone`: chime, pop, bell, tick, all synthesized in `lib/notification-sound.ts`) beside Play: no new row.
  - The work board has no switch and no close (the user's call; it docks whenever a pane has room, else the strip shows), because a close left no way to open it again.
  - The old bot feature (one always-on session) was removed (0a5d4f0d7). The prefs migration (`retired.rs`) retires `bot`, `botEnabled`, `botConversations` and `botRules`, first turning off the schedules whose `wakeSession` names an old current conversation (a recurring one stays listed, off; a one-time `[agent]` wake is then spent and the hourly `prune` clears it). Existing session files and bot userData files stay on disk, and the bot's sessions list as ordinary ones. Ordinary agent sessions, self-wakes, notifications, dictation and read-aloud remain. Orca's bots come back by the owner's decision of 25 Nov 2026 as a new feature (Shell › Bots, and Settings › Bots: see Bots below). Those retired keys stay retired: the new bots keep their settings on the core's bot record, and whether this device's sidebar shows them is the Bots nav row's own hide (`sidebarFolds.navHidden.bots`), no new pref.
- Curated rows come first. Rare rows and raw stock rows (auto panels, window placement, non-curated schema rows, launch profile, reset passes, account pools, model overrides, proxy) fold under one closed `SettingsAdvanced` disclosure at the section's end; `SettingsPage` opens it before scrolling to a search hit or deep link inside, so every row stays reachable and searchable.
- Settings deep links scroll only `.settings-content`, preserving the target's scroll margin or search-row centering. They never scroll the overflow-hidden app root: scrolling that ancestor lifts the sidebar and every settings pane together and leaves a blank bottom. The tablet usage shortcut regression is covered by `e2e/mobile-shell.e2e.ts`.
- Models & accounts reads connection, then models: Providers & accounts (accounts, live quota, rotation), Custom endpoints, then Model (setup assistant, Model roles, Defaults, Compare models). "This device" / "Selected host" scope lines (`SECTION_SCOPE`) show only while the focused tab runs on a paired host.
- No section intros: `settings.section.*.desc` only feeds nav search. Every section except Memory (App, Agent and System alike) is tip-only (`SettingsTipOnly` in `SettingsPage`): every string description sits behind its info glyph; rows read icon + label + control; a warning or a cost is passed as a node and stays visible.
- Sidebar shortcuts (prefs `sidebar.railPins`, `stores/sidebar-prefs.ts`; the footer draws `FOOTER_PINS`: usage and the side panel views and Background tasks) are off by default. Agents, Schedules and Stats are no longer pins but nav rows (Shell › Nav rows); a saved `agents`/`stats`/`schedules` pin stays in the blob as the core keeps it (`RAIL_PINS`, `crates/core/src/prefs/sidebar.rs`) and draws nothing. Settings and the help menu always stay. Only the usage block is on until a saved `railPins` array (even empty) says otherwise; it lists every subscription account that reports usage windows, grouped by provider like Settings › Models & accounts (see models-accounts › Providers & accounts list › The sidebar's usage block), and renders nothing for API-key-only users. They are set on the sidebar, never in Settings: Help › Customize sidebar… opens `SidebarPinsSheet` (one switch per nav row this view offers, then one per footer pin; a bottom sheet on a phone), and a pinned row's context menu (right click, Shift+F10, long press) has Unpin and Customize sidebar…; `toggleRailPin` is the one writer.
- Compact rows (`settings/SettingsLayout.tsx`): `SettingsRow`/`SettingsSwitchRow` are one dense line (`--sc-control-md` high): optional decorative `icon` (lucide glyph, or `ProviderMark` for a provider, model or vendor CLI), label, muted `description`, control at the right. A string description up to `INLINE_DESCRIPTION_MAX` (56) characters reads inline; a longer one sits behind a `SettingInfo` glyph (tooltip on hover/focus, text kept as `sr-only`); a node description (a cost, a warning) stays a visible small muted note. Collections (accounts, CLIs, devices, schedules, MCP servers, shortcuts) are dense list rows with secondary actions behind an overflow `MenuButton`. New rows reuse these, never a boxed card or a full-width description paragraph. A short fact about a row's control (a version, space used, a last check, an address) is `SettingsRow` `status`, small and muted under the control; `children`/`footer` hold real panels and start at the label column. An empty list is one kit `EmptyState size="row"` (glyph, muted "nothing yet", the filling action), never a centred `EmptyState`. A nested group that holds a collection passes `list`, so its title shows. A row or banner never repeats what a neighbouring badge says (Updates draws no "up to date" banner; an installed tool is its check mark, name, version and path on one line; omp is one row with its update button).
- **Density** (no information removed, touch sizes unchanged): a row's padding is `py-0.5` for a mouse (37 px row) and `py-1` under a finger; groups sit `--sc-space-4` (16 px) apart (`mobile.css` says the same for a phone). Under 700 px of page (`@container settings-root`) the nav is ONE row of title, search and section chips that scrolls sideways beside the section (the open chip kept in view, `SettingsPage`), never a wrapped multi-row bar; a phone's stacked list keeps its rows. Something a paired host's tabs do not follow (reply language, profile) is said once, on General's scope line (`data-settings-host-note`), not under each row. Memory's list rows are the kit `ListRow` (32 px for a mouse, `--sc-row-touch` on touch).
- **Device pills** (the owner's request, 13 Nov 2026: a screenshot of Settings showed one green pill for the paired computer and no way to open another's settings): once a computer is paired, a strip tops Settings, above the section list and the page (`settings/SettingsDeviceSwitch.tsx`, `data-settings-device-switch`): "Settings for", then one kit `Tabs` `pills` row of this device ("This device") and every paired computer, each with a decorative `StatusDot` for its link and the state as an `sr-only` word, the shown device `aria-selected`. Nothing shows without a paired computer (one pill is no choice). There is **no setting of its own**: Settings, Usage and Stats follow the focused tab's device (`useFocusedHost`), so a click focuses a tab on that device through `lib/settings-device.ts` `showSettingsOf` (the tab the person left there, else the first, else a new chat tab in that device's default workspace) and the Settings page stays open; a second path would drift from what a tab picked in the sidebar does. A device that is not online is dimmed (`opacity-60`) and refuses with a toast naming why (`settings.device.offlineWhy`/`connectingWhy`), opening nothing. Arrow keys only move focus over the pills (`onChange` `via` `key` is ignored): Enter or Space shows one, so a sweep never opens a tab on every device it passes. A long name is cut at `max-w-48` with its tooltip; the strip scrolls sideways on a narrow window or a phone (the kit tab list). The banner under it keeps its sentence and no longer holds the device chip (one control, not two). Pinned by `SettingsDeviceSwitch.test.tsx`, `SettingsDeviceScope.test.tsx`, `e2e/settings-device-switch.e2e.ts` (captures `test-results/settings-device-switch-*.png`) and the parity surface `settings-device-switch`.
  - The page stays open because `leavePageOnSessionSelect` (`AppShell.tsx`, which returns from a destination page whenever the focused tab changes) skips the change `showSettingsOf` makes while it runs (`settingsDeviceSwitching`); any other tab change still returns to the session view. The first run of this feature closed Settings on every click (13 Nov 2026, `e2e/settings-device-switch.e2e.ts` on a runner: the new tab on the host took the focus and the page left). Pinned by "keeps Settings open while its device pills move the focus" in `AppShell.test.ts`.
- Outside Settings (Mode popover, dialogs, run settings) `SettingInfo` and `splitDescription` (`common/SettingInfo.tsx`) are shared with `common/Switch.tsx`'s `SwitchField`: the glyph sits outside the `<label>`, so the switch is named by the label alone. A boolean row never stacks a paragraph under its label.
- The composer's Mode popover (`layout/composer/ComposerModes.tsx`, `modes/ModeConfig.tsx`, `modes/AutopilotConfig.tsx`) is built from `SettingsRow`s (`compactControl`; fixed-width `Select`/`Input`/segmented `Tabs` at the right; explanation behind `SettingInfo` in the row's `badge`; `FocusChips compact` within two rows; a one-line `GrowArea` that opens on first focus and never collapses on blur; release-procedure check as a glyph with the sentence as tooltip and name; one short warning line beside Start; no footer line) and scrolls inside `max-h-[min(36rem,calc(100dvh-6rem))]`. Nothing in it may change layout on a blur, because a press blurs the focused field at mousedown and a reflow moves the control from under the pointer so its click never fires. Pinned by `ComposerModes.autopilot.test.tsx` and the guide test of `e2e/autopilot-cycles.e2e.ts`.
- Opt-in captures: `e2e/settings-captures.e2e.ts` (`OMPDESK_SETTINGS_SHOTS=<dir>`; `OMPDESK_SETTINGS_SECTIONS` / `OMPDESK_SETTINGS_SIZES` narrow it), `e2e/mode-captures.e2e.ts` (`OMPDESK_MODE_SHOTS=<dir>`).

### Figure headers
- A box with a title and actions (code block, mermaid/svg figure, a write's figure in its tool card, the Files viewer's mode switch; `chat/FigureHeader.tsx`, `chat/Figure.tsx`) wears ONE header row on its top edge, `--sc-control-sm` high: kind or file name left, lucide icon buttons right (Preview/Code as two `aria-pressed` buttons via `FigureModeToggle`, then wrap, copy, download, enlarge), each with `IconButton`'s tooltip + `aria-label`. Never a separate text-tab row above such a box.
- `Figure` (`data-figure="mermaid|svg"`) owns the box and the Preview/Code state (`mode`/`onModeChange`); `CodeBlock` takes `title`, `headerActions`, `endActions`, `bare` for the same header. Tests: `chat/Figure.test.tsx`, `e2e/figure-header.e2e.ts` (`OMP_GUI_FIGURE_HEADER=<dir>` captures).

### Phone and tablet (web build only; an Electron window keeps the desktop layout byte for byte)
- `common/MasterDetail.tsx` is the one list-beside-detail primitive (`MasterDetail`, `useMasterDetail`, `MasterDetailBack`). Phone (`useShellMode() === "phone"`): one pane at a time, the list, then the row's detail under a back bar; the system back gesture takes a back layer while the detail is open. Tablet and desktop keep two columns. `SettingsPage` uses the hook (`data-stacked` on `.settings-page`: the section list is its own page, search results replace it, a deep link opens the detail); the GitHub center sections and the PR center use `MasterDetail` (the PR store's `deselect` is the back).
- On a phone `SettingsRow` stacks label and description above a full-width control unless `compactControl` (a switch row, or a one-button control such as push "Turn on" and install, stays at the right). Switches and `SettingInfo` glyphs are small with a 44 px hit area, except an info glyph in Settings' content on touch: it heads lines 28 px apart, so it declares `--hit-gap` 20 px (a 36 px target), its line is 36 px tall, and it never takes the next line's taps (`mobile.css`); `ListRow` carries `omp-list-row` (40 px on touch). `e2e/mobile-pages.e2e.ts` covers it on the dev harness in Chromium and WebKit (`OMP_GUI_MOBILE_PAGES=<dir>` captures; `harness.html?rail=all` pins Agents and Stats).
- Scale (`styles/mobile.css`): a tablet and plain touch do NOT resize controls or type (`--sc-control-*` 28/32/36, `--sc-icon-*` 14/16/20, body and transcript 15 stay the desktop's). A **phone's type and layout are denser and its controls 44 px**: the "Phone density" block (`html[data-shell="phone"]`) is the only place that overrides those tokens: `--phone-type-scale` 0.8667 (`applyFontSize` in `lib/theme.ts` multiplies it into `--gui-font-size` and the body size, so the type preference reads 13 px instead of 15 and still scales), `--sc-font-2xs/xs/sm` 12, `--sc-control-sm/md/lg` 24/28/32 and `--sc-hit-min` 24 for layout heights (fields, rows, section heads), `--sc-button-sm/md/lg` and `--sc-switch-box` 44 for controls (below), `--sc-icon-lg` 16, `--sc-row-touch` 36, `--sc-row-action` 44. A new phone rule goes in that block, gated on `html[data-shell="phone"]`, and never changes a ≥ 1200 px or tablet layout. Fields stay 16 px (iOS zooms into anything smaller); sheet items are `--sc-row-action`.
- A phone turned sideways (`html[data-shell="phone"]` under `(orientation: landscape)`, the last block of `mobile.css`) uses the width portrait lacks: composer chips 10 px apart (each reach 5 px, the 26 px + a 36 px tap), the model chip's whole name, 12 px chip badges, a 36 px work strip, a 38 px suggestion row and a 36 px work-card "Steps" row. A work card's 24 px step chips sit 12 px apart under any finger (phone in either orientation, tablet; reach, never drawn bigger). Portrait's 19.4 % chrome budget does not apply sideways. Pinned by the phone landscape test of `e2e/responsive-smoke.e2e.ts` (844×390, zero soft findings on the session surfaces) and the rotate step of `e2e/phone-day.e2e.ts`.
- Chrome budget at 390×844: gutters 12 px (`--omp-column-pad`), header bar 40 px, dock card head 36 px (`--sc-row-touch`, because the whole head is the fold's tap), always-open composer (see "Phone composer"), side-panel title row 36 px and tab bar 40 px; header + work chip + dock + composer stay ≤ 19.4 % of the height while idle (without suggestions; the user prefers the always-open composer to a lower share).
- **On a phone controls are drawn 44 px** (the owner's decision, 25 Nov 2026: "on the phone, draw controls at 44 px"; it replaces "the 44 px rule is a hit area only … never lift a control to 44 px visually"). Every kit `Button`, `IconButton` (so a `MenuButton` trigger, a ⋯ and a toolbar button) and chip built on them reads `--sc-button-sm/md/lg` (falling back to the control step off the phone: `h-[var(--sc-button-md,var(--sc-control-md))]`), and a `Switch`'s touch box `--sc-switch-box`; the phone sets all four to 44. Rows that hold them grow to 44: a switch tile, the drawer's device, folder and Chats headers and a project header (`--omp-sidebar-head-h`), the terminal's key bar (its scroller drops its padding, so a key runs from the bar's top to the panel tab bar). The composer's `+` (`.omp-composer-add`), mic, context ring, Run chip and Send/Stop are 44 px squares in a 44 px controls row, the field row giving back 8 px (6 px above the text, none under it) so the idle box grows only 4 px and the chrome stays inside the 19.4 % budget. **Kept smaller, with the reason**: the top bar's and the drawer header's buttons are 36 px, the bars' own height (`html[data-shell="phone"] :is(.omp-topbar, .omp-sidebar-header)` sets `--sc-button-*` 36, their reach 1 px up and down), because a 44 px bar adds 8 px of header and the idle chrome would pass 19.4 %; at 360 px the model chip is its mark alone (composer › Nothing runs under the action button), since five 44 px controls leave no room for the name. Fields, list rows and section heads keep the dense control steps (they are no controls). Under `html[data-input="touch"]` every `button`, `[role=button|switch|tab|checkbox]`, `summary`, `[data-setting-info]` and checkbox label still gets an invisible `::after` reaching `--sc-touch-target` (`@layer base`, so an element's own `::after` or positioning utility wins; an element with `after:`/`before:` utilities is left alone), which a 44 px control already fills. A tablet's title bar keeps its controls' sizes in the 36 px bar, their reach bounded to it (28 px ones at 10 px, the right group's 32 px ones at 6 px). Pinned by `touch-targets.test.ts`, `e2e/mobile-composer.e2e.ts`, `e2e/mobile-panels.e2e.ts`, `e2e/phone-run-sheet.e2e.ts` and `e2e/responsive-smoke.e2e.ts`. A field has no pseudo-element and is drawn 36 px.
- A hit area never covers a neighbour (the responsive audit's `stolen-tap`): a container of close controls sets `--hit-gap-x` / `--hit-gap-y` to the gap between them and the reach stops at half of it (title bar icons 14 px apart ≈ 40 px hit; composer toolbar, dock header, work chip, sidebar and panel top bar declare theirs); unset, the reach is the full 44 px. The bound counts from the control's own edge, so it must not be tighter than the room around it: a compact settings row resets it (`--hit-gap-y: initial`); a stacked row's own control reaches 7 px up and down on a phone (`--hit-gap-y: 14px`) under its label's 36 px info line; a scroller clips every reach to its padding box (the terminal key bar's key scroller holds the bar's padding so its keys reach the panel tab bar's hit area).
- **36 px through spacing, not size**: a 28 px control (26 inside its border) reaches 36 when its neighbours sit 10 px apart and the container declares `--hit-gap-x|y: 10px`, so on touch (`html[data-input="touch"]`, web build only) clusters are spaced 10 px: page top bars, the side panel's title row and its views' button clusters, the tablet composer row, Settings' button clusters (14 px on a phone, whose icon buttons are 24 px), the context popover's actions, a schedule's days (rows 14 px apart, a 24 px day reaching 7 px up and down), a message's actions (14 px on a phone), a figure's header buttons (reaching 5 px out of its 28 px header; a phone's 24 px ones 14 px apart), a multi-question card's step tabs (a segmented `Tabs`, outranking the segmented bar's 2 px bound), the sidebar update card's Restart and dismiss. Stats' section nav is a kit `Tabs` and takes the tab list's own touch rules (each tab, and a closable tab's box, the touch row's height).
  - Rows that stack flush (tabs, sheet items, Changes rows, the Run sheet's Advanced and Model roles, a host sheet's actions, the children-at-work rows) are a row tall with `--hit-gap-y: 0`. A Changes row's stage box label and file stand as tall as the row, the label as wide; the discard icon keeps its size, reaches the row's height, 14 px from the file; the Changes view's own 24 px controls behind a 1 px border sit 14 px apart, bounded at 14, so each reaches 36.
  - A segmented tab bar (`[data-segmented]`, tabs 2 px apart) declares `--hit-gap-x: 2px`.
  - A wrapping button row or chip list gets room on touch as well as its bound, because a reach is its own box plus half the gap: the Autopilot run's controls 10 px apart, the benchmark's models 12 px, each remote address 7 px above and below inside its row, the import dialog's search and refresh and the terminal's toolbar 10 px; a finished work card's findings and copy button 10 px apart (a wrapped line 14; the outcome's "Result" a touch row); the phone Run sheet's Autopilot buttons 14 px apart; the goal dock bar's Pause, Edit and Drop 10 px apart (`data-goal-dock`), 14 px on a phone (24 px buttons); an Autopilot run's board controls (Pause, End, Stop now) 14 px apart; a section head's own buttons (the run log's copy) 8 px in from its end; a board row's own pin or ✕ reaching the touch row (`--hit-gap-y: 10px`) and only 6 px sideways, so no reach makes a docked board scroll sideways.
  - On a phone (icons 24 px behind a 1 px border, reaching from the 22 px inside) the side panel views' clusters sit 14 px apart, bounded at 14, and a view's lone buttons (`data-terminal-head`, `data-file-viewer-head`, `data-empty-actions`) get the room around them.
  - Tabs and sheet items are `--sc-row-touch` / `--sc-row-action` rows on touch. A docked tablet sidebar's device and folder headers, starter guide and project ⋯ are 36 px boxes; on touch the always-shown project ⋯ takes its own slot beside "+" instead of overlaying the title. The drawer's left-edge strip (`EdgeSwipeZone`) owns swipes only: a tap on it is handed to the element under it (`tapThrough`).
- Pinned by `styles/touch-targets.test.ts` and, for the hit area, `hitSizes()` in `e2e/harness.ts`. The harness page takes `?stress=1` (long URL, wide table, long code line, diff, mermaid, long tool paths) for the responsive audit (`e2e/responsive-audit.ts`).

### Themes
- **Five sets, each a light and a dark theme** (the owner's decision: the OMPdesk default plus four pairs, all contrast-checked, no theme editor). `THEME_SETS` in dependency-free `src/shared/theme-names.ts` is the one table (set ids, halves, picker order; `LIGHT_THEME_NAMES`, `DARK_THEME_NAMES`, `THEME_NAMES` and the id types derive from it): `ompdesk` (`light`, `dark`), `github` (`github-light`, `github-dark`), `solarized` (`solarized-light`, `solarized-dark`), `gruvbox` (`gruvbox-light`, `gruvbox-dark`), `hc` (`hc-light`, `hc-dark`). A sixth set, a theme outside a set or a theme editor changes this decision; it is never just a palette to add.
  - **What was left against the decision** (20 Nov 2026, ten themes and a System card then): OMPdesk and High Contrast were complete pairs. GitHub and Solarized had no dark half, Gruvbox no light half. Sepia (the app's own, light), Nord (dark) and Tokyo Night (dark) had no other half here. No theme editor existed. Added from the authors' published values: GitHub Dark, Solarized Dark, Gruvbox Light. Retired: `sepia`, `nord`, `tokyo-night`. Gruvbox was kept over Tokyo Night with its authors' Day variant because Tokyo Night's page and accent sit a mean ΔE 9.7 from GitHub Dark's (it would be the dark group's closest pair) and Gruvbox is the one warm pair once Sepia goes.
  - `LEGACY_THEME_NAMES` maps every id the app no longer ships to the nearest same-scheme theme (CIE Lab distance of page and accent): titanium and nord → `solarized-dark`, latte and gruvbox → `gruvbox-dark`, tokyo-night → `github-dark`, paper, solarized and sepia → `gruvbox-light`, dawn, frost and matcha → `solarized-light`. `nord` named two palettes over time (Deep Sea, then the published Nord); both are nearest Solarized Dark.
- **OMPdesk Light and Dark are Orca's near-monochrome palette** (the owner's decision, 25 Nov 2026, replacing the indigo pair): white / `#0a0a0a` pages, grays a step apart, an accent near the text color (so a primary button, a switch, a selection read black on white and white on black), and hue only for state: links (`link`, Orca's callout blue), a session waiting on the person (`attention` → `--sc-attention`, Orca's `--agent-question` orange; the work board's Needs you, the sidebar's waiting bar and badge, the waiting title and composer tint), an unseen finish (`unread` → `--sc-unread`, the sidebar's ✓). Other themes leave `attention` and `unread` unset, so they read as their warning and info. Type is Geist (`@fontsource-variable/geist`, OFL; `--sc-font-sans`) with `0.01em` tracking, code in the system monospace (`--sc-font-mono`: SF Mono, Cascadia Code, then the bundled JetBrains Mono); radii 6/8/10/14; three elevations (`--sc-shadow-sm` hairline lift, `-md` floating menu, `-lg` dialog with a top highlight), Orca's values, built for every theme.
- Every theme, `light` and `dark` included, is one compact `ThemePalette` in `lib/theme-palettes.ts` (`ompdeskLight`/`ompdeskDark` for the OMPdesk pair); `lib/theme-builder.ts` derives all 122 `--omp-*` tokens plus the terminal's ANSI 16, six chart series and the focus ring (`themeExtrasFor` writes `--omp-ansi-*`, `--omp-chart-1…6`, `--sc-focus-ring` inline). `theme-light.css` / `theme-dark.css` spell the OMPdesk pair out for the first paint and must match what the builder makes (`styles/tokens.test.ts`). A palette may set its text selection (`selection`, the page's `--sc-selection` through `SC_TOKEN_SOURCES` and the terminal's) and diff washes (`diffAddedBg`/`diffRemovedBg`); otherwise the builder derives them from the accent and status colors.
- A theme swap holds every transition off for two frames (`applyThemeByName` → `html[data-theme-switching]`, global.css; Orca's `.theme-transition-disabled`), so no control eases from the old palette into the new; re-applying the same theme sets nothing. Popovers and menus are the theme's floating glass (`ThemePalette.floating`, `--sc-floating-mix`, `.omp-floating`; opaque where a palette sets none; its muted text is a contrast pair over the page and over the text color behind it). An active list option (`OptionRow`, the palette's row) is a 11 % text wash with a 16 % hairline ring and lifts its quiet text to secondary (`OPTION_ACTIVE_WASH`). Pinned by `themes.paint.test.ts`, `themes.contrast.test.ts`, `tokens.test.ts`.
- **Published palettes keep their published colors** (the owner's request): Solarized, Gruvbox and GitHub Primer, each light and dark (MIT, credited in `THIRD_PARTY_NOTICES.txt` via `scripts/generate-third-party-notices.ts`). ### Motion
- **One motion system** (the owner's ask; record `docs/motion-design.md`). Every duration, curve and distance is a token in `styles/tokens.css` (`--sc-duration-instant/fast/med/slow`, `--sc-ease-standard/enter/exit/emphasized/spring/loop`, `--sc-motion-rise/pop-scale/press-scale/stagger`); an exit runs one step shorter than its enter; enters decelerate, exits accelerate; the spring curve moves and resizes only, never opacity or colour.
- **Motion off in one place**: under `prefers-reduced-motion` and `html[data-gpu="software"]` every duration token and the stagger read `0s` (the tail of `tokens.css`), so every transition, one-shot animation, presence timer and Web Animation timed by a token is instant there. Loops keep their own clocks (`--sc-motion-spin`, `--live-period`, eased on `--sc-ease-loop`): reduced motion rests them (the still poses in `components.css`); software compositing keeps them running, held at ten frames a second by `lib/cue-clock.ts` the way an unfocused window is, because still cues read as the app having stopped (no `html[data-gpu="software"]` rest rule for a loop; pinned by `ComposerLive.test.tsx` and `cue-clock.test.ts`).
- **One implementation per pattern**: enter and exit utilities in `global.css` (sheets in `mobile.css`); exits through `useOverlayPresence(open, exitToken)`, `useHeldOverlay`, `usePresence` or `leaveGhost` (`lib/motion-play.ts`), never a private `setTimeout` matching a CSS duration; disclosures through `common/Collapse.tsx`; a list that changes on screen through `useListMotion` (`data-flip-key`; it watches the list's DOM, so a row whose own component changes it still moves the rest, and positions are re-read after every change as layout offsets, never the drawn box a running glide moves, and never only on the owner's commits or on a frame callback a background window never runs); press through `.omp-pressable` (compact controls only; rows and cards never scale); a finished mark through `.omp-done-pop`, played only on a live finish; Web Animations only in `lib/motion-play.ts`, loaded after the first screen (`loadMotionPlay`, main.tsx), so a list or disclosure that changes before it lands changes at once.

### Focus ring
- One ring for every control: the `@layer base` `:focus-visible` outline in `global.css`; a control's own ring is an outline too (on itself or its `::before`/`::after`), never a border or shadow.
- **A modifier pressed alone after a click never shows the focus of what the click focused** (the owner's report). Chromium counts every keydown without Ctrl, Alt or Meta held as keyboard use (blink `KeyboardEventManager::KeyEvent` → `Node::UpdateHadKeyboardEvent`), so a lone Shift would turn on `:focus-visible` for what a click focused. `lib/focus-modality.ts` (installed from `main.tsx`) sets `html[data-focus-modality="pointer"]` from a pointer press until a key that is not a modifier, except while a text field holds the focus (Chromium always shows a text field's focus). While it is set no focus style applies: `global.css` drops every outline (element, `::before`, `::after`, `!important`); its `@custom-variant focus-visible` replaces Tailwind's (built CSS: `:focus-visible:where(:not(html[data-focus-modality=pointer] *))`, `group-focus-visible:` composes it), so every `focus-visible:bg-*`, `opacity-100`, … utility stays off; a stylesheet `:focus-visible` rule that paints more than an outline or radius carries the same `:where(:not(…))` guard (`tokens.test.ts` fails one without it). Tab, arrows and every other key defer to Chromium again. Pinned by `lib/focus-modality.test.ts`, `styles/tokens.test.ts` and `e2e/focus-ring.e2e.ts`.
