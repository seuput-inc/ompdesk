## Waste guards (`resources/gui-bridge/waste-guards.ts`, rules and text `waste-guards-core.ts`, capability `wasteGuards`)

- **Why**: measured sessions (`scripts/session-pace.ts`) lose much of their time to failed tool calls, polls and `ready.log` waits that can never match (a service start whose stdout goes to a file waits its whole timeout and returns `NOT ready` as a success). The agent-side prose rule is the light-brief guidance in `resources/omp-builtin/skills/ompdesk/references/orchestration.md`; the guards make the repeating cases impossible or visible. They use public hooks (`tool_call`, `tool_result`) and a re-registered built-in; the one internal is stock's `WaitTool` with `Settings.instance` for the Windows broker connection under Guard 4 (`wasteGuards` in `capabilities.ts`). Stock omp is not forked and nothing is installed.
- **Guard 1: a `ready.log` that can never match is refused** (`tool_call`, `{block: true, reason}`, before the command runs). It applies to a `bash` call with a non-blank `ready.log` **and a non-blank `name`** (stock `bash.ts` `normalizeReady`/`execute` ignores `ready` without a service `name`, so refusing it would be wrong) whose command's **last command, in its last pipeline stage,** sends stdout to a file. `readyLogCannotMatch` reads the command with a small scanner (`scan`: quotes, escapes, `$(…)`, backticks, comments, heredocs, `;` `&&` `||` `&` newline, pipes), not a shell: anything it cannot place (a subshell's contents, an expansion) reads as "no redirect" and passes.
  - Refused: `> f`, `>> f`, `&> f`, `&>> f`, `1> f`, `>| f`, `>& f`, `>f 2>&1`, `2>&1 > f`, `2> e > o`, a target of `/dev/null` or a quoted `"$VAR"`, `>&-`, the last command of `a && b > f` or `a; b > f`, the last stage of `a | b > f`, a trailing `&`, a redirect after a line continuation, `cat <<EOF > f` (the redirect on the heredoc's own line).
  - Passes: no redirect, `| tee f`, `2> f` alone, `> f 1>&2`, `> /dev/stdout`, `/dev/stderr`, `/dev/tty`, `/dev/fd/N`, `> >(tee f)`, a redirect in an earlier command of a chain or an earlier pipeline stage, a `>` in quotes or a comment, a redirect only in a heredoc body (bodies are cut before judging), a redirect only inside `( … )`, `< f`, `3> f`.
  - Known cost, as the owner asked: `bun test > f` (stdout only) is refused too; the reason (`READY_LOG_REASON`) names the two ways out (async: true and `wait`, or `| tee file`).
- **Guard 2: one hint at a poll** (`tool_result`, `{content}`: the hint is a second text part appended to the call's own content; never a block, `details` and `isError` stay). **A poll is a repeated status look at the same thing, not a look** (the owner's rule, so a lone failure diagnosis is never hinted or counted). `pollLooks` names the looks of a call, each with a `kind` and, where there is a target, a `key`; `createPollTracker().observe` (the one classifier: the bridge's `createHints` and `src/main/session-pace.ts` `pace()` each keep one tracker per session and import it, no second copy) returns the kinds that are polls. No key = a poll at first sight: `sleep` (`sleep N` followed by another command, or `while … sleep`), `tail-f` (`tail … -f`/`-F`/`--follow`), and a foreground `gh run watch`. A key = a poll from the second look at the same key: `gh-run` (`gh run view`, key = run id, plus `--job` id, or the arguments when there is no id; `gh run list`, key = its normalized arguments), `pgrep` (key = its arguments), `proc` (`read` of a `proc://` path, key = the process id, the first segment after `proc://`: `proc://bg_1`, `proc://bg_1/streams/0` and `proc://bg_1:1-20` are all looks at bg_1). Never a look: `gh run view` with `--log` or `--log-failed` (diagnosis), a heredoc body (cut first), a quoted mention (`gh run` and `pgrep` are found among the command's words), and **anything in a bash with `async: true`** (it runs without the model and delivers once, so a background `gh run list` + `sleep` + `gh run watch` loop is the recommended way). Commands are cut at `; & | newline` outside quotes, so a jq filter's `|` stays in its argument. `createHints()` keeps the kinds already told in one set: **once per kind, per omp process** (one omp is one session; the main agent and every subagent share it); a call that carries several kinds marks them all told. Pace counts one poll per call that is one (the same diagnosis twice counts 1, a lone `sleep 30` counts 0) and each `wait` that came back with nothing (Guard 4). Text: `POLL_HINT`.
  - **Can the hook change the result? Yes, so the hint is appended to it** (the owner's rule: append to the result when the hook may; `sendCustomMessage` only otherwise). Stock's `ToolResultEventResult` (`extensibility/shared-events.ts`, merged by `extensions/runner.ts` `emitToolResult`) takes a replacement `content`, `details` and `isError`, and the changed result is what the model, the transcript and the work board get. The hook returns `{content: [...event.content, {type: "text", text: "\n" + hint}]}` only for a fresh kind; nothing else changes. Not `additionalContext`, because the result the agent reads would then carry no hint.
- **Measured**: with the guards, a service start redirecting to a file is refused at once with `x.log` never created, and of two polling calls only the first result carries the hint.
- **Pinned by** `src/main/bridge-waste-guards.test.ts` ("ready.log that can never match" fixtures, "looks only at a call stock would hold for ready.log", "polling kinds", "poll hints": once per kind, several kinds per call, per instance) and `src/main/bridge-waste-guards-stock.test.ts` (installed omp: "refuses a ready.log that cannot match at once, without running the command"; "hints at the first poll of a kind only"), `src/main/session-pace.test.ts` ("polls are repeated looks": the same tracker counts Pace's `polled ×N`).
- **Guard 3: one hint at a refused edit** (same `tool_result` hook and once-per-process set as the poll hint, kind `edit-misuse`), because refused edits are agent misuse that costs a round trip and a re-read. `editMisuse(toolName, outcome)` is true for an `edit` result with `isError` whose text matches `anchors to lines` or `not from this session` (stock's two refusals; the stale-tag refusal "file changed between read and edit" and the restated-neighbour case name their own fix and get no hint). Text: `EDIT_HINT`, appended to the failed result's content; stock keeps the call an error (`runner.ts` `emitToolResult` returns `isError` as it was, `wrapper.ts` returns the modified result with `isError: true` instead of rethrowing).
- **Guard 3 pinned by** `bridge-waste-guards.test.ts` ("hint on a refused edit": once per process, the two refusal texts, not a success, another refusal or another tool) and the stock test "hints once at an edit anchored to lines the session never read" (a `#0000` edit is refused, still an error with `errorKind: unknown_tag`, ends with the hint; the second gets none).
- **What the `tool_result` hook costs**: stock awaits its handler runner for every tool result once any extension subscribes, which can lose an aborted result in the journal at a quit. A hook added here, or anywhere in the bridge, relies on `quit-journal.ts` (`.omp/rules/interrupted-work.md` › "A quit during a tool keeps the tool's aborted result in the journal"), which holds the quit until started calls have their results; never remove it while a `tool_result` handler exists.
- **Guard 4: `wait` returns only with news**. Stock's `wait` (`tools/wait.ts`) gives each call a window from a ladder (`WAIT_LADDER_MS` 5 s, 10 s, 30 s, 60 s, 300 s; a back-to-back wait climbs one rung, news or a 60 s gap restarts at 5 s) and returns when it runs out with every watched job still running (`## Still Running`, `useless: true`, `details.jobs` all `running`), a model call that only waits again. The bridge re-registers `wait` (public `registerTool` over a built-in) and calls stock's own through the same-tool `ctx.invokeTool` again while `waitWindowElapsed(result)` holds (core: `useless`, `op: "wait"`, at least one job, every job `running`). Anything else is returned as stock built it: a job settled, a service ended, a message or reply, nothing to wait for, an interrupt. A wait on a service alone or for a reply lists no job, so it still returns at stock's window. No limit of its own (the owner's rule): the job's own timeout, a message and the user's stop end it. The definition carries `interruptible` and `handlesToolInterrupt` as stock's tool does (not in `ToolDefinition`'s type; `RegisteredToolAdapter` passes every key through `applyToolProxy`), or a steer would no longer cut the wait short. `invokeTool`, `useless` and the ladder are the same at the 18.18.2 floor. Pinned by `bridge-waste-guards.test.ts` ("a wait that came back with nothing"), `session-pace.test.ts` (an empty wait is a poll, a wait with news is not; nothing in an async bash is) and the stock tests "blocks a wait until the job it watches finishes, past stock's first windows" and "still ends a blocked wait at once when a message comes in".
  - **The two stock `wait` tests hold their job with a file, never a clock** (`bridge-waste-guards-stock.test.ts`: the job loops until `release` exists in its folder; the test writes it once the `wait` has streamed the job running for twice stock's first 5 s window, and again in its cleanup). A `sleep 12` job made the test wait out a clock. The rig's `turn(message, timeoutMs)` fails a stalled run with `Omp.diagnose()` (the frames omp wrote, repeats counted, and its stderr), because the 180 s timeout of a hung run left a CI log with nothing to read.
  - **On Windows a job never finishes when its process first connects to stock's service broker while it runs**, so the bridge connects first. Stock's `wait` lists the project's services before it blocks (`listServicesTolerant`, when `launch.enabled`), and that first list connects the process to the project's broker (`daemonClientForProject`, one client per folder per process). A shell job running at that moment never runs another step: its trace stays at its first frame, `wait` streams it `running` until the job's own timeout, and Guard 4 makes that a wait without end. Measured on omp-latest's Windows runner with omp 18.22.0 and no bridge (`flake-probe.yml`, 17 Nov 2026): 8 of 8 jobs stalled when the first connection came during the job, 0 of 8 when a `wait` connected before the job started, 0 of 8 with `launch.enabled: false`, and 3 of 5 when another omp had already started the broker, so it is this process's connection, not the broker's start; macOS and Linux never stalled. The omp-latest Windows runs of 15, 16 and 17 Nov (omp 18.20.2 to 18.22.0) hung in "blocks a wait until the job it watches finishes" this way; ci.yml's Windows job installs no omp, so the stock suites skip there. The bridge's `tool_call` hook makes the first `bash` of each folder on Windows wait until stock's own `WaitTool` (package index, over `Settings.instance` and a session that owns no job, service or agent, so it returns "Nothing to wait for") has connected that client; stock bounds the connection (10 s) and its request. macOS and Linux keep stock's lazy start. Capability `wasteGuards` requires `WaitTool.prototype.execute()` and `Settings.instance`; touchpoint B60.
  - **The broker keeps the session's folder open for 3 s after omp exits** (stock `DEFAULT_IDLE_GRACE_MS`): it inherits omp's working folder, which a test cannot remove meanwhile on Windows (the `EBUSY: rmdir ompdesk-todo-stock-repo-*` that ended every omp-latest Windows suite since 10 Nov, also after runs whose jobs all finished; with the connection above every stock test whose session runs a `bash` starts one, and `bridge-restore-card-stock` and `bridge-restore-request-stock` failed so). `vitest.setup.ts` sets `OMP_DAEMON_IDLE_GRACE_MS=0` for every test process, which each test's omp and its broker inherit, so the broker ends with omp. The app's own omps keep stock's 3 s.
- **Measured and not guarded**: repeat reads (nearly all distinct ranges or follow-ups stock's declarations-first reads require; a guard cannot save them since the model call is spent when the read is asked) and edits refused for a tag never received (`#0000`, after seeing the file only through `bash` or a `:raw` read, which give no tag; Guard 3's hint covers it). Turning bare code reads into whole-file reads (`tool_call` `input`) was rejected, to keep stock's declarations-first design.
- **Guard 5: no git hooks skipped** (17 Nov 2026, the hub's request after a session pushed a test-only branch with `git push --no-verify` and Main made archive refs through the API because the gate refused their old commits). `tool_call` blocks a `bash` call that runs `git push` or `git commit` with `--no-verify`, `-n` among a commit's short flags (on push `-n` is a dry run and passes) or `-c core.hooksPath=…` (`skipsGitHooks`, words read outside quotes, so a commit message or a grep naming the flag passes); the reason (`NO_VERIFY_REASON`) names the lawful ways the gate now offers: a `probe/<name>` branch (every check but the fix-commit rule, and its commits never land: a push to `main` that carries a commit of a `probe/*` branch, here or origin's, is refused, `probesInPush`) and `refs/archive/*` (not checked). A person's terminal is untouched. Pinned by `bridge-waste-guards.test.ts` ("a git push or commit past the hooks") and `scripts/pre-push-gate.test.ts` ("a probe branch never lands on main").
- **Checks are measured and shown, not hinted at** (12 Nov 2026, `bun scripts/session-checks.ts`: three days of this repository's sessions on one Windows computer, 14 sessions). 14.4 h inside tool calls, 10.8 h of it (75 %) with a check running; 12.5 h in `wait`, 9.4 h of it on a check alone, 0.6 h on a check and a subagent together, none on a subagent alone. 320 check runs, 13.5 h of run time: `check:changed` 4.9 h in 26 runs, vitest by file 2.6 h in 101, CI watches 2.5 h in 50, cargo 2.3 h in 112, type checks 0.9 h in 10. What came of it: the Pace line says each session's checks (control-tools › Worker contract), `check:changed` runs the tests one step away for a change that reaches many, and the type check keeps its build info (e2e-ci-windows › Local checks). **No hint at a whole-project check started again**: of 67 wide runs none started after the same command had passed with nothing edited in between (7 of 849 in a Mac's records), so a hint would have nothing to say.
- **The poll hint stays once per kind**. The 110 journals on that computer hold 47 polls (33 `sleep`, 5 `gh run`, 10 empty waits, those in one journal of 8 Nov, before Guard 4), 22 of them after their journal had been hinted, the most 16 `sleep`s in one 17-hour session of 1,137 tool calls: too few to measure a second hint against. The `polled ×500` and `×620` of two long sessions on another computer are totals of their whole life, which began before Guard 4 stopped the empty waits (10 of them in 24 minutes in that 8 Nov journal); the newest 40 messages of the `×620` one hold no poll. Their kinds could not be read from here, so the Pace line now says them (`pollKinds`), and a cadence is decided only from a total whose kinds show polling that goes on.
- **Guard 6: the gh guard** (20 Nov 2026, Main's request after core sat at 0 of 5000 from about 06:33 to 06:46 KST, half an hour after which another project's customer deployment would have waited on its merge). The GitHub account's REST quota (`core`, 5000 an hour) and GraphQL quota (`graphql`) are one budget for every token, session and project of the user, so one session can empty it for all. Measured that night (19 Nov 20:30 to 21:30Z): on the Mac mini 12 `scripts/watch-run.ts` watches at its then 15 s (about 4 to 6 at once), 1 `gh run watch` at 120 s, 7 `gh run view --log*`, 6 `gh run list`, no stock `github` `run_watch`; the desktop's six sessions of that evening started about 40 `watch-run.ts` jobs at 15 s and one `gh run watch` at 120 s. [inferred] Each look of `watch-run.ts` (`gh run view --json jobs`) is about 2 requests, about 480 an hour per watch at 15 s, so the concurrent watches of both computers alone spend more than 5000 an hour; the log reads are tens.
  - **Where it sits**: a `gh` wrapper (`resources/gui-bridge/gh-bin/gh`, for every POSIX shell and Git Bash, the shell an agent's `bash` runs on Windows too) running `bun resources/gui-bridge/gh-guard.ts` (rules pure in `gh-guard-core.ts`). Main names the folder in the session-owned `OMP_GUI_GH_GUARD` (`sessionEnv`) and puts it first on a tab omp's PATH (`sessionPath`, sidecar.ts), so it runs for every `gh` an agent's shell command starts, piped or from a shell script. It finds the real gh by walking PATH past its own folder and any file holding the `OMPdesk gh guard` marker; without bun on PATH the sh launcher hands the call to the next gh as it is. Not a `tool_call` hook: a hook sees neither a piped log whole nor a `gh` inside a script. **No `gh.cmd`** (removed 20 Nov 2026, 0.136.0's): a bun program resolves `gh` through `PATHEXT`, and bun refuses to start a `.cmd` with any argument holding a cmd.exe special character (`&`, `|`, `<`, `>`, `^`, `%`, `"`) before anything runs, with no stderr (every `ci-run.ts` lane listing, `…/runs?event=workflow_dispatch&per_page=30`, failed with an empty error); cmd re-parsed the rest through `%*`. Pinned by `src/main/gh-guard-launchers.test.ts` (Windows: a bun program's `gh` with an `&` argument answers). Follow-up G20: a `gh.exe` launcher (argument quoting without cmd.exe) so programs that resolve `PATHEXT` reach the guard again.
  - **Only an agent's command**: stock's bash sets `PI_TOOL_CALL_ID` for the agent's tool calls (eval cells too) and every process they start; the composer's `!`/`$` (RPC `bash`) and a terminal run without it, and the wrapper hands those to the real gh untouched. Main sets `PI_TOOL_CALL_ID` empty in a tab omp's environment, so one inherited from the shell OMPdesk was started in never makes the person look like an agent.
  - **A finished log is fetched once** (per session, in `$OMP_GUI_SCRATCH/gh-logs/`, never deleted by the guard): `gh run view <run> --log` / `--log-failed` keyed by run and attempt (`run-<id>/attempt-<n>/log.log`, `log-failed.log`), `gh api …/actions/runs/<id>[/attempts/<n>]/logs` as `api.zip`, a job's log (`gh run view --job <id> --log`, `gh api …/actions/jobs/<id>/logs`) by job id (`job-<id>/…`; job ids are new per attempt). Run ids are unique across GitHub, so the path carries no repository; the header does. A rerun keeps its run id, so a command without `--attempt` first reads the latest attempt (`gh api repos/{owner}/{repo}/actions/runs/<id>`, one request) and serves that attempt's log; when that read fails nothing is served from the cache. `--attempt N` served from the cache costs no request. Only a finished attempt is kept (gh refuses a running one's logs; a job's status is read before it is kept). Every served log starts with `[OMPdesk gh log cache] run R attempt N (owner/repo), --log-failed, fetched <ISO>` (stderr for the zip). A fetch that fails passes gh's output and exit status on as they were.
  - **A floor on what is left**: `QUOTA_FLOOR` 1500 per resource (`core` for REST, `graphql` for `pr`, `issue`, `repo`, `project`, `label`, `status` and `api graphql`). A wide call is refused below it: any `list`, `--paginate`, `run download`, a whole run's `--log`, `api …/runs/<id>/logs`, a new watch. Narrow calls always run: one run's `--log-failed`, one job's log, a status view, a dispatch, a rerun, a cancel, a merge, `api rate_limit`. The reading is `gh api rate_limit` (free), shared by every session of the computer in `~/.cache/ompdesk/gh-budget/rate-limit.json` (`OMPDESK_GH_BUDGET_DIR` overrides), read again at most once a minute or after a resource's reset, by whichever session takes the `rate-limit.lock` folder first (a lock older than 30 s is taken over); a quota that cannot be read (offline, not signed in) lets the call run. The refusal is an error, never an empty result: the wrapper prints it on stderr, exits 1 and leaves it in `$OMP_GUI_SCRATCH/gh-refused/<tool call id>`, which the bridge's `tool_result` hook appends to the call's result with `isError: true`, so a pipeline whose exit status hides gh's still fails. It names each resource's remaining, limit and reset (local time and UTC) and the narrow reads still allowed.
  - **Watches**: `gh run watch` and `gh pr checks --watch` refresh at most once a minute (`WATCH_MIN_INTERVAL_S`; a shorter or missing `--interval`/`-i` becomes 60, a longer one stays). `scripts/watch-run.ts` polls every 60 s at least and, for an agent, starts only above the floor. Stock's `github` `run_watch` polls from omp's own process (3 s for its first minute, then 15 s, constants without a parameter), where the wrapper never runs: the bridge's `tool_call` hook refuses it below the core floor; its interval is stock's.
  - **This repository's scripts** run gh through one helper, `scripts/gh-run.ts` (`ci-run.ts`, `watch-run.ts`, the shard-cost scripts): on Windows a bun script's `gh` is the real gh.exe (no `gh.cmd`, above), so the helper applies the same floor itself with the guard's own rule and the computer's shared reading (`gh-guard.ts` `wideRefusal`; for an agent only, as the guard), and names a gh that never ran (a spawn error or a signal leave no stderr). Pinned by `scripts/gh-run.test.ts`. `ci-run.ts` reads one page each (`gh api …/runs?per_page=30`, a run's jobs, `per_page=1` counts): narrow, so a dispatch is never refused; its `--wait` watch ends the wait with the refusal instead of listing again, and its fallback `gh run list --limit 5` after a dispatch without a receipt is wide (the dispatch already went out). `watch-run.ts` clamps its interval to `WATCH_MIN_INTERVAL_S`, starts an agent's watch only above the floor, its `gh run view --json` looks are narrow and its job log (`gh api --allow-escape-sequences …/jobs/<id>/logs`) is cached; `--release` lists runs (wide). `release-prune.sh` pages releases on a runner with the workflow's token, where no wrapper runs and the account's quota is not spent.
  - **Known limits**: an rc file that puts gh's own folder before the wrapper's when the shell snapshot is taken (measured on this Mac with stock omp 19.0.0: the wrapper stays first) bypasses it. On Windows every program that resolves `gh` itself (Node, which takes only `.exe`/`.com`; bun, PowerShell and cmd through `PATHEXT`; Python) gets the real gh.exe: only an agent's Git Bash command is guarded there until G20. Stock's own `github` tool calls other than `run_watch` are not counted.
- **Guard 7: one hint at a burst of gh commands** (same once-per-process set): `GH_BURST_CALLS` (15) `gh` commands within `GH_BURST_WINDOW_MS` (10 min) in a session's `bash` calls, `async: true` ones included because the quota counts requests, not model calls (`ghCommands`: a word `gh` followed by a gh command in a segment; a quoted mention is none; a loop counts as written). The poll tracker reports the kind `gh-burst` once per burst (its count starts again after), so Pace counts it with the journal's timestamps; the hint (`GH_BURST_HINT`) says the quota is shared, that finished logs are kept and how to watch once. Pinned by `bridge-waste-guards.test.ts` ("speak once at a burst of gh commands").
- **Guards 6 and 7 pinned by** `src/main/gh-guard-stock.test.ts` (stock omp with a fake gh after the wrapper that counts its calls and serves `rate_limit`: a rerun run's latest attempt from the cache, `--attempt 1` beside it and served with no request, watches raised to a minute; below the floor `run list` and a watch refused as errors naming both resources, `--log-failed` still served, one quota reading for all, the person's `!` command run), `src/main/gh-guard.test.ts` (what each command costs, watch intervals, the reading's age and floor, the refusal text) and `omp-launch.test.ts` (the variable is session-owned).

## Edits

The rule the third guard repeats, for any agent working in this repository:
- Edit only lines shown in the latest `read` of that file. After a grep hit, or an elided or declarations-only read, read the exact range first.
- Copy the `[FILE#TAG]` header from that read or from the last edit's response; never invent one (`#0000`) or reuse one from another session.
- After each edit use the tags and line numbers the edit's response returns, not the ones before it.
- Do not re-check that one edit applied: its response already shows the edited lines and the new tag, so a `git diff` of that same hunk or a `read` of lines the response just displayed adds nothing. What a single edit response cannot show stays a normal check: `git status` for unexpected or untracked files, the whole diff before a commit (`git diff`, `git diff --cached`), the combined change across several edits or files, and a `read` of lines outside the displayed range (the next spot to edit).
- Change files with `edit`, never `sed -i`, `perl` or `python` through `bash`.
