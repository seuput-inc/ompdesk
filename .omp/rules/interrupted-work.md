## Interrupted work, quit and diagnostics

### Interrupted turns continue by themselves
- `src/main/turn-resume.ts`, `src/main/connectivity.ts` (since batch H2 the clients of the core's `native/ompdesk/crates/core/src/resume/`: `machine.rs` is `TurnResume`, `connectivity.rs` `ConnectivityMonitor`, `ends.rs` with `hold-ends.json` the end table; a `#name` below is the Rust function of the same name in snake case, native-rust › 9f). Settings › General › Continue interrupted work after relaunch, pref `resumeInterrupted`, **default on** (main reads `!== false`).
- **Two paths, one coordinator (`TurnResume`), driven by `SidecarPool.onRunningChange` (`resumeFacts()`).**
  - **The rules know an outcome by its id, so one finished run is one object in every read.** `ResumeFact.lastRun` (and `retry`) cross to the core as ids (`turn-resume.ts` `idOf`, by object identity): the core judges an outcome once (`judged`), and every hold, probe and armed retry ends when the tab shows another one (`otherOutcome`). The core's pool numbers each finished run (`Tracking.last_run_serial`, in `resumeFacts` as `lastRun.id`) and `SidecarPool.resumeFacts()` hands out one `lastRun` object per id (`#outcomes`, as `#retries` does for stock's saga). A fresh parse per read made every look a new outcome: a retry was never armed, and Cancel on a wait was judged again and held again (the Windows e2e of 16 Nov 2026: `scheduled-retry`, `interrupted-resume` Cancel). Pinned by `sidecar-pool.test.ts` ("one outcome object per finished run") and `run.rs` (`an_outcome_keeps_its_serial_until_the_next_run_ends`).
- **① Relaunch.** Eligibility is a marker file `<userData>/interrupted-turns.json` ({window, tab, peer, sessionPath, cwd, kind, startedAt, reason}) rewritten atomically on every run-state transition. NEVER write it in a quit hook: SIGKILL/crash runs none. `InterruptedTurnStore` writes through `writeFileAtomicDeferred` (one attempt now, retries on a timer) because on Windows the rename fails (`EPERM`) while any process reads the file and a running turn has no later transition to rewrite it; it logs `markers not saved` (source `turn-resume`) only when every try failed.
  - Present while a turn runs (`running`); cleared on normal completion and on the user's Stop (`SidecarPool.noteStopped`, called by the RPC dispatcher for `STOP_COMMANDS` `abort`/`abort_and_prompt`/`abort_and_restore_queue`, so a kill before the run's end event leaves none); kept as `asking` while blocked on an ask/approval (the relaunch re-runs the cut-off call, the card reopens; not "continuing"). An omp that exits or restarts takes its open asks with it (the pool forgets owners on any non-ready status).
  - A quit (`quitApproved()`) freezes writes: tearing tabs down must not read as turns ending. Closing the last shown window on Windows with close-to-tray off is such a quit, asked for before the window goes (`tauri-shell/src/last_close.rs`).
  - A marker whose session the user deleted (`deletedSessions()` tombstone) is dropped at launch, never continued, not even into a fresh tab. A never-written session has no tombstone and still continues.
  - `TurnResume.launch()` (after saved windows exist): each marker finds its tab by session path (deferred tab: `SidecarPool.startTab`; missing from the layout: opened) and continues through stock: `restore_interrupted` (local handler → bridge `composer.restore_interrupted` → stock `restoreSession`, what `omp --restore` runs) for a cut-off turn, `retry` (`/retry`) for a failed one (a turn that waited for the connection, `network`, or for a provider's limit, `limit`: see Limit wait). A killed OMPdesk's omp usually closes the turn itself on stdin EOF, so `restoreSession` finds nothing; the relaunch then runs stock `retry`, which replays the failed tool batch or aborted reply and does nothing for a turn that really ended.
  - **A turn cut before its next model call**: stock records a closed stdin as a `normal` `session_exit` (with `pendingToolCalls` only while a tool runs) and may never journal the abort, so `findUnfinishedTurn` reads the turn as ended and `/retry` finds nothing. The bridge's restore (only for a marker of a running turn) checks `requestCutAtExit` (`restart-core.ts`: the replaced process's clean exit record, nothing after it, a prompt or tool result before it that nothing answered) and appends stock's own interrupted-turn record (`session/exit-diagnostics` `createInterruptedTurnAbortMessage` over the branch without that exit) before stock `restoreSession`, which continues from the recorded tail: no tool reruns, no prompt sent twice. A prompt journaled only as its process ends lands after the exit record and needs nothing. Pinned by `bridge-restart.test.ts`, `src/main/bridge-restore-request-stock.test.ts` (installed omp) and `e2e/interrupted-resume.e2e.ts` (the fake omp records stock's exit record on stdin EOF).
  - **An aborted turn with a note after it**: a custom message journaled after an aborted reply hides it from stock's `retry` (`turn-recovery.ts` `conversationEnd` skips eval snapshots only). The bridge's restore (`turnCutBehindNotes` in `restart-core.ts`: last message an aborted or failed reply of the replaced process, a non-eval custom message after it, nothing typed since) continues it with the relaunch's one follow-up (`ompdesk-restart-turn`, or folded into the jobs/subagents one; details `turn: true`; the transcript's muted line "Continuing the work the restart cut off", `data-restart-turn`) and reports `followUp`/`turnCut`; `TurnResume` counts `followUp` as continuing and sends no `retry` on top (log `restored: "turn-behind-notes"`). It reads the journal only. Pinned by `bridge-restart.test.ts`, `turn-resume.test.ts`, `MessageBubble.test.tsx` and the note case of `bridge-restore-request-stock.test.ts`.
  - **A quit during a tool keeps the tool's result in the journal**: with more than one stock `tool_result` handler the aborted result lost the race against `#doDispose` sealing the journal, and stock cannot skip a handler (`ExtensionToolWrapper` emits whenever any extension subscribes). So `quit-journal.ts`' `session_shutdown` handler (after `session_exit` is recorded, before dispose's `agent.abort()`) aborts the loop itself and waits, at most `QUIT_TOOL_SETTLE_MS` (1.5 s), until every call that started (`tool_execution_start`) has its result message (`message_end`, role `toolResult`); with nothing running it returns at once.
  - **A stop lets a running command finish** (B1 of the owner's 20 Nov 2026 list: "a relaunch never cuts or repeats an agent's work"). Before that abort, a running `bash`, `eval` or `ssh` call gets up to `QUIT_COMMAND_DRAIN_MS` (20 s) to return: the handler prints `… (up to 20 s)` on stderr, which the core's stop reads as an exit hold (`sidecar/stop.rs` `Hold`, so it does not end omp after its 5 s grace), and the `context` hook holds the loop's next model request until the abort. Stock caps each `session_shutdown` handler at 2 s (`SESSION_SHUTDOWN_HANDLER_TIMEOUT_MS`); the module raises the cap with stock's own setter (`extensibility/extensions/runner` `testSetSessionShutdownHandlerTimeoutMs`) to the wait plus the settle. The bound stays inside main's 30 s quit watchdog. The real result reaches the journal after `session_exit`, then the aborted reply; `requestCutAtExit` reads that tail and stock continues the turn from the result. A command still running after 20 s is aborted as before.
  - **A command runs once across a relaunch**: stock's replay (`restoreInterruptedTurn` closes a cut call with "outcome unknown", then `retry` → `toolReplayStart` reruns a batch whose every result is an error, same call ids and arguments, after moving the leaf back to the batch's reply) ran a cut command a second time, and a command that really failed too (the owner's report, 20 Nov 2026: the same empty commit made twice when a turn resumed). `quit-journal.ts`' `tool_call` hook refuses a `bash`/`eval`/`ssh` call whose reply is the branch's last message and was journaled before this process started (`replayOfEarlierLife`; entries other hooks journal after it, `ompdesk.checkout-claims`, stock's `tool_execution_start`, are no messages). The refusal is the call's result: what the earlier process returned (its tail), or that its outcome was not recorded, and to check what it changed before running it again. The agent decides; OMPdesk and stock never rerun it. A person's own `/retry` in the same process is a call this process journaled and runs. **Except a plain `bash` call that never ran**: the module wraps the embedded shell's `Shell.prototype.run` once and appends the call id to `<session artifacts>/ran-commands` (`RAN_COMMANDS_FILE`) right before the shell runs it, so a crash cannot lose it; a replayed plain bash call (no `pty`, no `name`) missing there was cut before it started (its approval card waited) and runs, asking again, as the card restore needs (`bridge-restore-card-stock.test.ts`, the approval card; red on the runner without this). `eval`/`ssh` have no such record and are always refused. Model-checked by `formal/relaunch-once` (`AtMostOnce`, `ShortCommandNotCut`). Pinned by `bridge-restore-request-stock.test.ts` ("a command a stop or a crash cuts": a counter file stays at one run after a stop, a failing exit and a kill) and `bridge-quit-journal.test.ts`.
  - **The hold leaves `wait` alone**: a `wait` cut by a graceful quit never reaches the journal with a result, so stock's restore reruns it silently (`turn: true`); holding for it made stock read the turn as ended and the parent got the revived-subagents follow-up as a new turn. `quit-journal.ts` (`LEFT_PENDING_TOOL`) does not hold the quit for a `wait`. Pinned by `bridge-restore-subagents-stock.test.ts` ("while the parent waited on it").
  - **From omp 18.18.2 the dying turn's own aborted records reach the journal after `session_exit`, a `wait` and a first-request prompt included**: the journal ends `session_exit`, the prompt or aborted `wait` result, then an `aborted` reply "Request was aborted", which stock's `findUnfinishedTurn` reads as ended. `requestCutAtExit` returns `{ exit, abort }` when the last message after the replaced process's clean exit is such a reply (not stock's own interrupted-turn record, not one journaled after this process started, not one a custom note follows: `turnCutBehindNotes` owns that), builds stock's interrupted-turn record without the exit and that reply, and stock continues the turn: the tool's aborted result stands (a cut `wait` does not rerun; the parent still gets the revived-subagents follow-up as a steer, once). Pinned by `bridge-restart.test.ts` (`requestCutAtExit`), `bridge-restore-subagents-stock.test.ts` and `bridge-restore-request-stock.test.ts`. `[sidecar] stock stream metadata unavailable: unknown method stream_metadata.start` in a ci log is a fake omp in `link-traffic-relaunch.test.ts`, not this.
  - Pinned by `bridge-restore-request-stock.test.ts` ("a quit that aborted a tool, with a note journaled after the abort": the journal ends on the aborted reply or tool result, never the call) and `bridge-quit-journal.test.ts` (nothing pending goes at once; every started call has its result; a tool that never returns is waited for no longer than the bound).
  - A continuation waits for its tab's omp with no deadline (the owner's rule: no time limit ends or blocks work). `TurnResume.#whenReady` ends only when the tab reads `ready`, its omp fails (`error`, not a held session) or exits, the tab closes or the continuation is called off. `SidecarManager.dispose` drops listeners without emitting a status, so `sync()` ends the waits of tabs no longer in the pool's facts (`#endReadyWaits`), and a Stop, Cancel, new prompt or a superseding omp exit (`#dropWait`, `#exited`) ends them with the generation bump: no status listener outlives its continuation. The resuming row's Stop, the waiting row's Cancel and a new prompt on a held tab call it off even during the wait (a per-tab generation checked before every command). Pinned by `turn-resume.test.ts` (a day of fake time, no failed try; a closed tab and Stop leave no listener).
  - **A failed continuation keeps its marker** (its omp failed or exited before ready, or every command it sent threw, had no connection or was answered `bridge_unavailable` by its local handler: "GUI bridge closed", an RPC timeout): the marker stays in `#pending` and in `interrupted-turns.json`, and `#run` goes again, under the same `stale()`/`HOLD_ENDS` checks, when the tab's sidecar next emits `status: ready` (a listener, never a poll), at most `LAUNCH_CONTINUATION_ATTEMPTS` (3) failed tries per marker; past that nothing more is sent this launch, the "continuing" row goes and Autopilot's `goalSettled` hears `none` (once per continuation, at its end, never per failed try). An omp that answered with nothing to continue is no failure: the marker goes, and it still leaves when the turn runs, on Stop/Cancel, a new prompt, a move, a closed tab or the setting off.
  - **An omp update never restarts a tab under its relaunch continuation** (the Mac mini, 19 Nov 2026: the launch's update finished 23 ms before a restore failed, `restartOnNewOmp` having read the tab idle because stock had not started the restored turn yet). `ompRestartDecision` (`omp-restart.ts`) waits for a tab whose continuation is owed (`relaunchContinuation` is `after_restore`; `SidecarPool.continuationOwed`, `LocalHostServices` through `attachResume`) as for a running one; `goalSettled` (once per continuation, at its end) calls `ompRestartIfWaiting` a tick later, which restarts the tab if no turn runs, else its turn's end does. Second line: `restore_interrupted` is a local handler, so a bridge that closes under it anyway reaches the core as a response with code `bridge_unavailable`, not a throw; `Inst::send` counts it as no answer, so the try fails and goes again at the new omp's `ready` (counting it as an answer had dropped the marker and the turn sat idle). Pinned by `turn-resume.test.ts` ("a restore an omp update's restart cuts") and `sidecar-pool.test.ts` ("relaunch continuation is owed", "restored turn started").
  - `restore_interrupted` and `retry` get `RESUME_COMMAND_TIMEOUT_MS` (2 min), not the RPC client's 8 s default, because stock's restore reads every subagent transcript first.
  - No toast: each resuming tab shows its own calm row ("Continuing where it left off…", `data-resuming`, one per tab, `setResuming` → tab `resuming` → `TurnStatusRow`; not for a reopened card) with the Stop on it (`resume.stop(tabId)` → `TurnResume.stopResumed(tabId)`: that tab only, noted as the user's Stop so its marker goes and Autopilot's goal resume ends `cancelled`). The only resume indicator.
  - Rank order: focused tab, other panes of its split, then background tabs (`ResumePool.resumeRank` ← `SidecarPool.resumeRank`).
  - Setting on: a quit (⌘Q, tray, last window on Windows) and "Restart to update" ask nothing (`quitNeedsConfirmation(risk, resumes)` in `quit-guard.ts`, `confirmQuit()` in `app-quit.ts`, the updater's `UPDATER_APPLY`); off, they ask before stopping running work. Exception, a person's update restart (`confirmUpdateRestart`, `updateRestartConfirmation`): running background subagents and jobs start over after a relaunch, so it names them first (`app-updater.md`, "Running background work holds the restart too"); the automatic install waits for them instead.
  - **A run whose turn had ended is never retried** (marker `background: true`, `deriveMarkers` from `ResumeFact.settling` = `runSettling`: only background subagents or async jobs kept the run on). Its continuation is `revive` (`launchAction`): stock's restore alone, which revives the subagents and lets the bridge name the stopped jobs; stock `retry` is never sent. A marker without the field (an older app's) reads as before.
  - **A goal session idle between its turns has a marker too** (B4 (1) of the owner's 20 Nov 2026 list: stock pauses an active goal when its session loads, and a goal session idle at the quit had no marker, so it stayed paused). The pool keeps stock's `goal_updated` (`Tracking.goal_active`, fed by `sidecar-pool.ts`' event filter as `{goal: {status}}`), reports `ResumeFact.goalActive`, and a change of it syncs the rules. `derive_markers` keeps such a tab as `running` with `background: true`, so the relaunch (or an omp exit) revives it, and the restore's `goalPausedByExit` resumes the goal. A person's Stop keeps none. Pinned by `resume/facts.rs` and `sidecar-pool.test.ts` ("says when a session's goal is active").
  - **A scheduled retry is in the marker file while it waits** (B4 (4): it lived in the process only, so a relaunch before its time dropped the turn). The machine marks each tab with an armed transient retry (`Fact.retry_armed`, never from the pool) and `derive_markers` writes reason `retry` (after `limit`, before an active goal); `planned` syncs right after it arms, as the limit wait does. `launchAction` retries it (stock `retry`), and an omp exit leaves it to the armed timer, like `network` and `limit`. Pinned by `resume/facts.rs` and `turn-resume.test.ts` ("is in the marker file while it waits").
- **An omp that dies while the app runs is a relaunch for its tab**: `SidecarPool` and `LocalHostServices` count each `restarting` of a tab's own omp (`ResumeFact.exits`; a paired host's link status is no exit, nor Windows ending the session), and `TurnResume.#exited` turns the marker the tab had before that sync (running, asking or background; never `network`, whose wait and marker outlive the omp) into a launch marker in `#pending` and runs it as `launch()` would once the next omp is up: the resuming row, the person's Stop, prompt or move ending it, the setting off offering it instead (next bullet), Autopilot's `relaunchContinuation` reading `after_restore`, the log's `marker` line with `via: "exit"`. A continuation already on its way when the omp dies again is superseded (its marker in `#superseded`, the tab's generation bumped): it sends nothing more (no `retry` into the next omp) and leaves the marker and the goal report to the new one. Pinned by `sidecar-pool.test.ts` ("an omp that ends under its work continues on the next one"), `turn-resume.test.ts` ("TurnResume after the omp died under its tab"), `host-services.test.ts` ("a device tab's omp dies under its background work") and `e2e/interrupted-resume.e2e.ts` ("goes on when its omp dies under it").
  - **A turn that does not go on by itself is offered to the person** (the owner's decision, 25 Nov 2026, after Orca's bounded restart and its manual Continue). `TurnResume.#exited` continues at most `EXIT_CONTINUATIONS` (3) exits of one tab's omp under the same session within `EXIT_WINDOW_MS` (5 min) (`crash_loop`: an omp that keeps dying under the same turn makes no progress); the next one, an exit with the setting off, and a launch marker whose `LAUNCH_CONTINUATION_ATTEMPTS` ran out are an **offer** instead (`offer`, `State.offers`): the log's `marker` line adds `skipped: "crash-loop" | "off"`, the tab's status carries `cutOff` (`IpcTabInfo.cutOff`: `off` | `crash-loop` | `failed`; pool `set_cut_off`), and `TurnStatusRow` shows one calm row (`data-cut-off`, `chat.cutOff.*`) with **Continue** (`resume.continueCut` → `RESUME_CONTINUE` → `TurnResume.continueCut`: if the tab neither runs nor moved since the offer, the marker the cut left goes back into `#pending` and runs the same continuation, the resuming row first; a person's Continue clears the tab's crash count) and **Dismiss** (`resume.dismissCut` → `RESUME_DISMISS`: the turn stays cut; a launch marker whose tries ran out leaves the file). The offer ends by itself when the tab runs (the person's prompt) or shows another session or branch (`end_offers`, `moved_since`). With the setting on an offer stays in the marker file, so the next relaunch continues it; with the setting off the file stays empty and a relaunch offers nothing (a crash with the setting off is not offered: telling it from the person's "Quit anyway" needs the previous run's end line, not built). Only a window's own tab gets an offer (a hosted device tab's turn is its device's to judge), and every view of it shows the row as the connection wait is shown: the phone page reads the tab's status; a paired device's view gets the `cutOff` tab event (`TabCutOffArg`, pool `emitView`, re-sent on `tab.open` and in the view's snapshot) and its Continue and Dismiss go back as `tab.continueCut`/`tab.dismissCut` (`RemoteSidecar.continueHostCut`/`dismissHostCut` → `HostedTabView` → `SidecarPool.onCutOff`). A session an agent opened tells its opener of each offer and each Dismiss with one `blocked` report of its own (`ResumeDeps.cutNote` → `AgentControlRuntime.reportFor`), and auto-close leaves a child with an offer open (`ControlTab.cut_off`). Pinned by `turn-resume.test.ts` ("TurnResume cut-off turns the person continues") and the `turn-cut-off` parity surface; unchecked by formal/turn-resume (`SCOPE.md`).
- **A lost core is a relaunch for every tab it ran** (the Mac mini, 18 Nov 2026: the core went under 14 running tabs and nothing came back for 6 h). The core ends every omp it runs, and the pool and turn resume live in it, so the new core's pool reads each tab idle and its `exits` start at 0: no `#exited`, and the next `sync` would drop the markers. `TurnResume.#lost` (only after this launch's `launch()`) makes the next instance run `launch` before any other call (`#continueAfterLoss`): the marker file still holds what ran when the core went, each marker finds its tab by session path and continues once the tab's next omp is up, as after a relaunch. Pinned by `e2e/interrupted-resume.e2e.ts` ("a turn running when the app's core dies continues on the next core").
  - **A tab's start never waits without a bound** (`SidecarManager.#onResolve`): every input but the session owner's wait (its own `SESSION_FREE_WAIT_MS`) goes on as failed after `START_INPUT_MS` (45 s), logged `omp-start-input`; the system proxy lookup has 5 s in the core (`LOOKUP_BOUND`, `crates/core/src/proxy.rs`), because a PAC or WPAD lookup can hang (the Tauri host's hung main thread once held every start), and one past it is logged `omp-start-input` `proxyEnv`. A tab not ready `RECOVERY_NOTICE_MS` (3 min) after the loss (no omp, or one that never answers) logs `core-loss stuck`, shows an error with Restart, sends its opener one `blocked` report through the mail outbox (`AgentControlRuntime.reportFor`) and counts in one OS notification per loss (`noteRecoveryStuck`). Pinned by `sidecar-core-loss.test.ts`.
  - A lost hub wait's reason names which side was silent (`lossTrace` in `core/hub.ts`: whether the hub's thread took main's wait, when the core last sent a line), so the next `abandoned` line tells a starved worker from a core that stopped answering; the `ended` line of an abandoned core carries `exitMs` (abandon to exit), and seconds there mean the whole computer stalled. `HUB_CALL_DEADLINE_MS` stays 2 s. Measured (R8, 20 Nov 2026): hub waits that reached the slow-step log on Windows runners ran p90 206–335 ms, worst 560–787 ms outside one stall; in that stall (parity run 44640593095) both apps lost their core in the same minute while unrelated processes stalled too (a stock worker request 7.7 s, the hosts' page calls 74–80 s, the killed cores ending 12 s and 41 s later, a new core not connected in 4 s), so no deadline main's thread may hold (under the hang watchdog's 5 s) would have kept it. Main's failed-run nightly logs had no hub-deadline loss in 1,267 app launches.
- **One conversation stays one session across a relaunch**: a tab whose session file exists starts on it (`--session`), the continuation answers into that file, the sidebar lists it once.
  - A start on a stored session first waits (up to `SESSION_FREE_WAIT_MS`, 60 s) until no other live omp holds stock's ownership lease on it (asked every 250 ms for 5 s, then every 2 s) (stock helper `sessions.owned`, `tryAcquireSessionLease` keyed by the header's id, read past stock's title slot with `parseTitleSlotFromContent` as stock's `readSessionHeaderIdSync` does; `src/main/session-free.ts`, SidecarOptions `sessionFree`), because an omp that opens a session owned elsewhere moves it to a new file (stock `"open-elsewhere"`).
  - Still owned when the wait runs out (an omp run in a terminal): the start opens nothing; the tab is `error` with `omp.sessionOwned` ("still open in another omp … Close the other one: it opens here by itself then, or press Restart"), Restart waits again, and the tab keeps waiting by itself and opens the session the moment the owner lets go (`#whenSessionLetGo`).
  - Its status carries `sessionHeld`, shown everywhere as a wait (warning, "Waiting for the session", `sidecar.heldTitle`), never a failure: the pane's `SidecarBanner`, an opener's child row (`IpcTabInfo.sessionHeld`), the title bar (`SessionSummary.sessionHeld`, `sessionRun`, panels-sidebar.md › A row is live; `titlebar.status.sessionHeld`, the hollow pending dot), the tray (`trayStatusOf`: not an error), every split pane header (a spinner), the Work tree (`work-tree.ts`), every sidebar row of the session (a paired device's tab here included), a paired device's pane (`TabStatusArg.statusPayload.sessionHeld`, kept by `RemoteSidecar`). A relaunch's continuation keeps waiting for that `ready` (`TurnResume.#whenReady`, no deadline) instead of dropping the cut-off turn; pinned by `turn-resume.test.ts`.
  - The lease is an OS lock, so a dead owner never holds it; a helper that cannot tell lets the start go on (the two stock internals are the `sessionOwner` feature in `capabilities.ts` and `health.ts` `LOADERS`, reported like any missing internal). A wait over 1 s, or one that runs out, is a `session-owner` line in `gui-runtime.jsonl`.
  - Pinned by `session-free.test.ts`, `session-free-stock.test.ts` (installed omp), the two start cases of `sidecar.test.ts`, `e2e/interrupted-resume.e2e.ts` (no second file, one indexed row, after kill and normal quit), `e2e/real-update-restart.e2e.ts` (a)/(a2) and the SIGKILL test of `e2e/real-resume.e2e.ts`. Two rows in the README resume clip were the fake omp writing a second journal (see the fake omp under Build, test), never OMPdesk.
- **Every spawn of a tab launches one bundle on the tab's own session** (`src/main/omp-launch.ts`: `sessionOpen`, `ompArgs`, `sessionEnv`; `SidecarManager.#spawn` gathers the facts). A new tab, a stored session, a relaunch's saved tab started later, an interrupted turn's tab, an omp update's restart, a paired device's tab and that tab revived get the same extensions and OMPdesk settings; only the session flag, the bridge socket and a device tab's `OMP_GUI_PROMPT_ORIGIN` differ.
  - The tab keeps the session it is on (the file it opened, then what `get_state` reports), so a restart that names none (a crash, machine setup starting a tab that waited for omp, the desktop slot's stop) reopens it.
  - A session stock never wrote starts a new one in the folder (`--config fresh-launch.yml`), never omp's `autoResume`; a tab stays new (`#isNew`) until `get_state` names its session, not merely until `ready` (formal/tab-session F1).

### What a relaunch continues beyond the cut-off turn
Measured on the real omp by `e2e/real-update-restart.e2e.ts` (opt-in `OMP_GUI_REAL_WORK=1`; "Restart to update" = an approved quit while work runs).
- Stock: a foreground bash call is journaled "outcome unknown" (or "Command aborted") and its replay would run it again; OMPdesk lets a stop finish it and refuses the replay (› A command runs once across a relaunch). Subagents (awaited or background) are revived by `restoreSession` (the parent gets the result, a waiting `wait` included, when stock continues its turn); an open ask/approval reopens.
- **Agents are told a relaunch continues their work**, so none ends its turn to wait for one (B4 (3) of the owner's 20 Nov 2026 list: agents read "every running turn ends" in `ompdesk_app`'s `updates.apply`/`app.quit` and pstack's "Pause safely … on an OMPdesk restart", ended their turns to wait, and nothing woke them after). The catalog (`agentctl/app/catalog.rs`, pinned by `captured/list.json` and `meta.json`) says running turns go on when OMPdesk starts again while Continue interrupted work is on; pstack's adapter (`resources/omp-builtin/pstack/adapter.md`) says an OMPdesk restart is never a reason to pause or end a turn, and `sync-pstack.ts` translates Pause safely's trigger to "an omp restart you start yourself". A turn an agent ended anyway is not woken.
- OMPdesk handles seven things stock leaves behind:
  - **Background bash jobs keep running through the relaunch** (B1 of the owner's 20 Nov 2026 list, `resources/gui-bridge/kept-jobs.ts`, capability `keptJobs`). The main agent's `bash` call with `async: true` (no `pty`, no `name`, a command naming no session URL path, `keepable`) does not run in omp's embedded shell, which the relaunch ends: the module wraps `Shell.prototype.run` once, copies the session shell's exports, functions and aliases as stock's `#sessionSeed` does, and starts stock's shell process (`exec/shell-process` `shellProcessCommand`) under `ompdesk keep start <dir>` (`native/ompdesk/crates/checks/src/keep.rs`: detached as `ompdesk check`'s runner, in its own session on Unix, outside the job on Windows), `<dir>` = `<session artifacts>/kept-jobs/<call id>` (deleted with the session). The job reads `output.log` as it grows and `exit` at the end; a cancel or timeout writes `cancel` (the runner ends the tree); the main session's `session_shutdown` leaves it running. The restore (`reattachKeptJobs`, before stock's `restoreSession`) registers every unsettled job of the branch whose folder exists (`unsettledJobs`, any earlier life) again with the bash tool's `asyncJobManager` under its own id: `wait`, `jobs` and stock's delivered result work as before, and the follow-up does not name it. The runner carries the tab's process tag, so closing the tab ends it. Main hands the CLI's path in `OMP_GUI_KEEP_CLI` (`KEEP_CLI_ENV`, `sessionEnv`); without it (tests, a fake omp) jobs are stock's. ### Batched notifications
- `src/main/notification-batch.ts`, always on, no Settings row (the `batchNotifications` pref is retired, `crates/core/src/prefs/retired.rs`; it also governs Web Push). `SYSTEM_NOTIFY` carries `kind` (`completion`|`error`|`ask`, from `maybeNotify`); main batches per window: the first event shows at once and opens a fixed 4 s window (`BATCH_WINDOW_MS`), followers are recorded one per tab (ask > error > completion), and at the end with followers the first banner is closed and one summary ("3 tasks finished · 1 needs you", `batch.*` in `i18n-text.ts`) replaces it; a click focuses needs-you first, then failed, then the latest finished.

- A bot chat's turn whose last reply is a quiet result (`isQuietResult`, last line `NO_REPLY`, src/shared/bots.ts) notifies nothing: `notify-triage.ts` `quietBotTurn` drops its completion before the dedupe (the reply is the pool's last `idle` outcome, kept in `ipc.ts`), and `index.ts` keeps its `idle` from Web Push.

### Scheduled retry
- `TurnResume`, follows stock's `retry.enabled` (Settings › Agent behavior › Retry; the `scheduledRetry` pref is retired, `crates/core/src/prefs/retired.rs`). Once stock's own auto-retries are spent and a turn ends in a transient error (`isTransientError`: stock's retryable pattern with word-bounded 5xx codes, minus auth, quota/rate limit, bad request, context overflow, certificates), main arms stock `retry` after 30 s, 2 min, 10 min (`SCHEDULED_RETRY_DELAYS_MS`; `OMP_GUI_RETRY_DELAYS_MS`, comma-separated ms, shortens them for e2e), then **again every 10 min, with no limit, for as long as the failure stays transient and nothing calls it off** (the owner's rule: never hold agent work back). The attempt number counts on and nothing says "of N" or "gave up": `IpcScheduledRetry` is `{at, attempt}`, the card reads "Retrying in 10:00… · Attempt 12" (`turnError.scheduled.attempt`, en/ko). A failure that is not transient ends the chain (red card, Retry). `TurnErrorNotice` shows it ("Retrying in 0:30…", Cancel through `RESUME_CANCEL_WAIT`, Retry now) from `scheduledRetry` on the pool entry (`IpcTabInfo`, so a renderer reload re-reads it).
- Guards: never a hosted/peer tab, a tab without a session file, after Stop, unless stock's `retry.enabled` reads `true` (`get_settings`), or for a network error the connection wait already holds. Called off by any run that is not its own retry, Cancel, a session change or a `TOUCH_COMMANDS` move (`touched` on the pool entry, counted only once the command worked and was not cancelled: `movesTab`), stock's `retry.enabled` reading off at fire, tab close, quit; a fired retry whose omp is still coming up is called off by a move made meanwhile (`#run` looks again once the omp is up). "Branch from here" (`fork_from`) is no move: it writes a new session for another window and leaves the tab on its own. A retry due while offline goes to the connection wait. The attempt count resets when a retry ends in anything but a transient error or the user runs something new.
- **A continuation held for the connection is shown the whole time and released within a minute of the network returning**. The wait has no timer of its own, so the offline state must never outlive the outage: besides the events and the wake's probe loop, an offline state nothing is recovering asks the resolver every `REPROBE_INTERVAL_MS` (15 s, `ConnectivityMonitor#reprobe`; a probe times out at `PROBE_TIMEOUT_MS`) and goes online the moment it answers, whatever the link flag says, so `flush()` runs. Every surface shows the wait while `awaitingConnection` holds: the pane's row, the tab strip and sidebar signal (`tabSignalPresentation`, "Waiting for the internet connection", `titlebar.status.connectionWait`, below a question, a run and the tab's own down state), and the sidebar row of a paired device's tab on this computer (`SessionSummary.awaitingConnection`, pushed as it changes). Pinned by `connectivity.test.ts`, `turn-resume.test.ts` ("a continuation held for the connection"), `tab-signal.test.ts`, `host-services.test.ts`; model `formal/turn-resume` (`WaitEnds` with `LinkUpMissed`/`Reprobe`, `NoGiveUp`).
- A paired device viewing the window's tab shows the same countdown and its Cancel calls it off here (tab event `scheduledRetry`, time left rather than this computer's clock; see The host owns the turns). A device never arms one for a host's tab.
- Pinned by `turn-resume.test.ts`, `TurnErrorNotice.test.tsx`, `e2e/scheduled-retry.e2e.ts`.

### Limit wait
- **A turn that ended at a provider's limit waits for the limit and goes on by itself** (the owner's report, 12 Nov 2026: a tab his MacBook hosted for the paired desktop ended three turns with `429 … rate_limit_error … retry-after-ms=319918000`, the model's weekly limit, and sat for 37 minutes until another session wrote to it). Stock ends such a turn at once: a wait past `retry.maxDelayMs` (5 min) with no credential or model to switch to (`turn-recovery.ts` `exceedsDelayCap`; its chain walk skips a fallback model whose window cannot hold the conversation, `contextFitsModel`). `TurnResume` takes it up with the scheduled retry's machinery (one armed retry per tab, `#scheduled`), under the same `retry.enabled`, with another rule for when it fires.
- **What**: `isLimitError` (`turn-resume.ts`): a limit by its wording (`isLimitWording`, `src/shared/quota-reset.ts`: 429, rate limit, quota, usage limit) that is no account out of money (`isBillingCap`: the wordings of stock's `isBillingCapUsageLimit` and HTTP 402; a copy because main judges the text with no omp to ask, held against stock's function by `quota-reset-stock.test.ts`) and none of sign-in, a rejected request, a context that does not fit or certificates (`NEVER_RETRIED`). Never while stock's own saga runs (the run has not ended), and never for a live Autopilot run's session (`ResumeDeps.limitHeldElsewhere` = `Autopilot.holdsLimitWait`: the run's own `waiting_quota`, autopilot.md).
- **When**: the wait the failed reply carries (`retryAfterMs`: stock's ` retry-after-ms=<n>`, counted from the failure), else the provider's first reset over stock's usage reports, else `QUOTA_FALLBACK_MS` (15 min): `quotaWaitUntil`, the one rule Autopilot's wait reads too.
- **Earlier once it lifts**: every `LIMIT_LOOK_MS` (10 min, never more often per tab; `OMP_GUI_LIMIT_LOOK_MS` shortens it for e2e) the wait looks (`#look` → `#readLimit`): `get_settings` (`retry.enabled`, `retry.fallbackChains`), `get_state` and `get_usage` on the tab's own omp. **A look sends no request to a model**: `get_usage` answers stock's cached reports, which stock reads again from the provider's usage endpoint only once they are older than its 5 min. The retry fires early when the reports no longer say every account of the provider is limited (a reset pass was spent, another account is free; a provider with no report at all counts as well, since nothing then says the limit holds) or when the session's model or the fallback chains differ from when the wait began (a chain that now holds a model the conversation fits). A read that fails changes nothing. A try the provider refuses again is a new failure and a new wait, so a tab sends at most one request per look.
- **Shown and called off as the scheduled retry**: `IpcScheduledRetry.limit` on the pool entry; the card reads "Tries again by itself at {time} · in {countdown}, or sooner once the limit lifts." (`turnError.limitWait`, `data-limit-wait`) with Retry now and Cancel. The end table is the scheduled retry's (`turn-resume-ends.ts`, check `armed`/`firing`); a look syncs first, so a session file that moved on an idle tab ends the wait at the next look. **There is no booking** (the windows' click-to-book resume, `use-quota-resume.ts` and pref `quotaResume`, is gone and the pref retired): a limit nobody waits for (after Cancel, with stock's retry off, on an Autopilot run) still names the provider's reset on its card (`turnError.resume.resetsAt`).
- **A hosted tab too**: `notRetryable` lets a limit wait hold for a `peer` tab; the backoff retry still never does. What the exclusion guarded against was a retry nobody at either computer sees, so `index.ts` hands a hosted tab's wait to `LocalHostServices.setScheduledRetry`: the device gets the tab event `scheduledRetry` (`limit: true`, time left) on its own tab, shows the same card, and its Cancel is `tab.cancelWait`. The grace period keeps a waiting tab while its device is away (`#startGrace`) and `tabs.kept` names it `waiting`.
- **Across a relaunch**: a tab with an armed limit wait keeps a `limit` marker (`deriveMarkers`' `limited`; written when the wait is armed, gone with it, a running turn's `running` comes first), and the launch continues it with stock `retry` as it does a `network` one: one request per waiting tab per relaunch, and a provider that still refuses starts the wait again. An omp that dies under an armed wait changes nothing (`#exited`: the timer is main's).
- **Log**: source `turn-resume`, message `limit`: `{tab, session, wait: "armed", by: retry-after | usage | fallback, ms, peer}` when the wait starts, `{wait: "due"}` or `{wait: "lifted", by: usage | setup}` when it tries (the `continue` line follows).
- **Background work does not end the wait**: a look that finds the tab still running (the failed turn's background jobs or subagents) fires nothing and looks again a pace later, where the backoff retry is dropped at `busy`; a result of that work starts a turn of its own, which ends the wait as any new run does, and a tab whose jobs end quietly is tried at the next look.
- Known limits: stock's report marks an account limited while any of its windows is exhausted (`usageResetAtMs` over every limit, not the model's own), so without a `retry-after-ms` a short limit on an account whose other model's weekly window is spent waits for that window; stock trusts a model's own weekly row only at full exhaustion (`usage/claude.ts`), so a row that reads short of it makes each look a try.
- Pinned by `turn-resume-limit.test.ts`, `turn-resume-ends.test.ts` ("an armed limit wait"), `shared/quota-reset.test.ts`, `quota-reset-stock.test.ts`, `remote/host-services.test.ts` ("a hosted tab's wait for a provider's limit"), `TurnErrorNotice.test.tsx`, `e2e/usage-resume.e2e.ts`, `e2e/scheduled-retry.e2e.ts`, `e2e/remote-resume.e2e.ts`; model: formal/turn-resume's armed retry (`SCOPE.md` › The limit wait).

### Close to tray
- Closing the last shown window hides it instead of ending the app (the shell's `tauri-shell/src/last_close.rs`, for the window's own close and main's `BrowserWindow.close()` alike; pref `closeToTray`, default **on**: only an explicit `false` keeps the Windows quit). Main pushes the pref as stored (`app.closeToTray`, at start and on every change); the close never waits on main.
  - Windows needs a tray (`tray::exists`; headless runs have none and quit) and shows a one-time "OMPdesk keeps running in the tray" Notification (pref `closeToTrayNoticeShown`, which main stores when the shell says it showed it).
  - macOS hides regardless of the pref (it has no Settings row): window, tabs and omp keep running; `app.on("activate")` shows the same hidden window (spawns one only if none exists).
  - **After `quitApproved()` nothing rebuilds a window**: `activate` (`activateAction`, `quit-guard.ts`) and every `spawnWindow`/`spawnWindowWithLayout` path (tray, menu, deep link, second instance) do nothing, and the saved desktop session is never rewritten (`layoutsToSave`, `saved-layouts.ts`, used by `persistTabLayouts` for both the tab-change and the window-closed hook; the web layouts and the resume markers are frozen too), because the teardown closes tabs and windows one by one and a stalled quit would otherwise save the session smaller or rebuild it on disposed services. A window the user closes before any quit still leaves the saved set. Pinned by `quit-guard.test.ts`, `saved-layouts.test.ts`.
  - A non-last window closes as before and ends its tabs: hiding it would leave no Dock or tray way back.
  - A hidden window stays in `getAllWindows()`, so tab inventory, notifications (a click shows it), keep-awake, badge and tray counts keep working.
  - Real quits (menu, ⌘Q, tray, logout/update restart) still go through the quit guard; once `quitApproved()` every window closes.
- Tests: `quit-guard.test.ts`, `last_close::tests` (the decision, the pref, the notice once), the macOS `desktop-tabs` e2e (close during a fake turn, then `activate`), the `@smoke` tray test in `desktop-surfaces` (default pref), `tray::tests` (the menu's items per updater state and what each click calls).

Nothing else goes in (no status line, model/thinking/approval/context lines, usage, workspaces, quick start or quick settings, language); the menu sends no `MENU_ACTION`.

### Keep awake, lid closed while charging
- The user's rule: closing the lid of a laptop that is charging never stops OMPdesk's running work; on battery the OS sleeps on a lid close as usual. No setting of its own: it is part of General's one "Keep this computer awake while it is used" (pref `keepAwakeWhileWorking`, `KEEP_AWAKE_WORKING_PREF`, default **on**: only a stored `false` turns it off), which covers both the work blocker and the host role's (devices connected or running a session here). The host's old `remote.keepAwake` is merged into it once (`MERGES` in `retired-prefs.ts`) and retired: a choice the person stored decides (a stored host `true` turns a stored-off work switch on), and a work switch stored off beside a host switch never touched stays off, because the old key is deleted after the merge and a later launch could not tell that state from a person turning the one switch off; Devices & connections shows only a "Keeping awake now" row while devices hold it.
- Electron's `powerSaveBlocker` `prevent-app-suspension` (`KeepAwakePolicy`, `remote/keep-awake.ts`, whose holds and quiet period the core decides: `crates/core/src/keepawake.rs`, native-rust › R5) is an idle-sleep assertion a lid close ignores. So `LidAwake` (`src/main/power/lid-awake.ts`, pure, injected backend) wraps both keep-awake blockers (`wrap(blocker, "work" | "host")` in `index.ts`) and, while any is held, holds a platform `LidBackend` as long as the computer is a laptop (has a battery, asked once) on AC (`powerMonitor.isOnBatteryPower()` at start, `on-ac`/`on-battery` flip it at once). It converges one step at a time, logs one `gui-runtime.jsonl` line per change (source `keep-awake`: `held`/`released` with `reason` `work` | `charging` | `work-ended` | `on-battery` | `quit`, plus `skipped` no battery, `recovered`, `failed`), retries a failed step only on the next input change, and releases synchronously at quit (`lid-awake` teardown step). Never in a test launch (`OMP_GUI_HEADLESS=1`: a killed test app would leave the setting changed) or a second instance.
- **macOS** (`lid-backend-mac.ts`): stock `/usr/bin/caffeinate -s -w <main pid>`, a PreventSystemSleep assertion macOS honours on AC only (verified to keep a closed-lid Mac awake on AC); `-w` ends it with the app, so a crash holds nothing. No admin, no `pmset disablesleep`. A caffeinate that ends while the hold stands (killed by someone else) is started again after `RESPAWN_MS` (30 s), doubling up to 16× while it keeps ending, each a `keep-awake` `restarted` line; a release stops it and any restart that waits (`lid-backend-mac.test.ts`).
- **Windows** (`lid-backend-windows.ts`): the active scheme's AC "lid close action" (`SUB_BUTTONS`/`LIDACTION` by GUID) goes to 0 (do nothing) with `powercfg /setacvalueindex` + `/setactive SCHEME_CURRENT` (no admin), and back to the user's value when work stops. The DC (battery) value is never touched; a user who already chose "do nothing" is left alone; a value the user changed while it was held stays theirs. The original is written to `<userData>/lid-awake.json` before the change and put back at the next launch (`recover`), so a crash or kill is undone. `powercfg /query` labels are localized, so the AC value is the first of its two `0x` lines. A desktop (no `Win32_Battery`) does nothing.
- **A powercfg failure never loses the user's value**: the backend keeps the original (`#held` and the marker) until a restore succeeded, so a failed release is retried on the next change, at quit (`dispose` always asks the backend) or at the next launch; a hold made while a restore is still owed reuses that original instead of reading the 0 it left; a hold that fails after changing the value rolls itself back.
- Pinned by `power/lid-awake.test.ts` and `power/lid-backend-windows.test.ts` (fake powercfg, English and Korean output, crash recovery, injected failures); `e2e/desktop-tabs.e2e.ts` (default on: the blocker is held during a turn, the switch turns it off).

### One stop, one start at a time
- Why: many omps started at once can stall, stuck omps that outlive a quit stall the next launch, and a second omp on a tab whose first still runs breaks its session; OMPdesk must survive a stock stall.
- **One stop** (the core's `sidecar/stop.rs`, native-rust › 9c) for every path (tab close, restart, sleep, a revive, the quit): SIGTERM (Windows: its stdin ends), so stock journals `session_exit`; still running `STOP_GRACE_MS` (5 s) later, SIGKILL to its process group (every omp spawns in a group of its own on POSIX; Windows keeps `taskkill /T /F`). **An omp that says it waits to save is not killed meanwhile**: stock's exit writes "<what it waits for> (up to N s)…" to stderr when it holds on one thing (`EXIT_HOLD`; the login refresh, up to 125 s, because the provider already swapped the refresh token and a kill before the save leaves a spent token in the store every omp shares, so the account drops off the list at its next refresh), and the kill then waits for the time named plus 2 s, at most `STOP_HOLD_MAX_MS` (130 s) from the stop; each chunk is searched together with the unread end kept from before (bounded only after the search), because the pipe may cut the line anywhere or bury it in other output, and the longest wait printed counts (`sidecar/stop.rs` tests, `sidecar-exit-hold.test.ts`). **An omp that ends because its stdin closed waits for that save too** (`resources/gui-bridge/exit-drain.ts`, `exit-drain-core.ts`): stock ends such an omp with `process.exit` right after it disposed the session (rpc-mode.ts `disposeAndExit`) and does not await the cleanup pass the `exit` event starts, so the save was dropped on every stop that closes stdin (Windows, and everywhere with the ai-memory grace) while a signal's exit awaited it. The main agent's `session_shutdown` therefore replaces `process.exit` with one that runs stock's awaited pass first (`postmortem.quit`, then `postmortem.exitProcess`); the pass then prints the same line, which holds the kill. An idle omp ends as fast as before (measured, 3 runs each: 44 to 76 ms with it, 40 to 83 ms without). Pinned by `bridge-exit-drain.test.ts` and, on the installed omp, `bridge-exit-drain-stock.test.ts` (a cleanup shaped as the refresh's is finished and announced; without the hook the omp ended 36 ms after its stdin closed and the save never ran). The quit's own bound (the app then exits and the omp finishes alone) and a later launch's reap of a leftover pid (`stopOmpPid`, which sees no stderr) do not wait for it. It resolves only once the process exited (or 2 s after the kill) and is shared by every caller of the same child. The ai-memory grace (`gracefulStopMs`) is its `stdinGraceMs`: stdin first, then the same steps.
- **A replacement waits for its predecessor**: the tab's lane in the core (`sidecar/lane.rs`) keeps the exits of the omps it stopped and starts the next only once all of them exited; `whenExited()` (`sidecar.whenExited`) covers them too.
- **One start queue** (`sidecar/queue.rs` in the core, one per app; `sidecar-factory.ts` puts every local tab in it): at most `OMP_STARTS_AT_ONCE` (2) omps starting; a place goes to the next start once the omp answered, ended or was stopped, after `START_SLOT_CAP_MS` (15 s), or once the omp is slow (`START_SLOW_MS`). A tab that waits for a place, for the launch's reap (`sidecar.holdStarts`) or for its previous omp to exit reads `starting` with `queued: true` (the lane's spawn), shown as "Waiting to start" on the title bar's status in every view (the session summary's `queued`, read by `session-run.ts`) and passed over the link (`TabStatusArg.statusPayload.queued`); no deadline: it starts when its place comes.
- **A tab reads `ready` only once its omp answered** (`#answered`: stock `get_state` after `ready` and the protocol negotiation, before the start gate; no deadline, the lane's `get_state` with no deadline). Until then it reads `starting`. **A live omp is never stopped or failed for being slow** (the owner's rule: a limit that stalls work is worse than what it guards).
  - Past `START_SLOW_MS` (20 s) without an answer (`#startIsSlow`) its start-queue place goes to the next tab, and an `omp-slow-start` runtime-log line keeps its stderr tail, its own log's tail (`ompLog`: `ompLogTail`, `src/main/omp-log-tail.ts`, the last 8 lines of stock's `<logs>/omp.<local day>.<pid>.log`, compacted), `ready` (omp printed `ready`, so it is past its startup; stock's startup watchdog prints "Still starting after Ns" to stderr every 10 s only before that) and `unanswered` (the stock commands the lane holds unanswered, oldest first).
  - The tab reads `starting` with `slow: true` and `message` = the stderr tail, or the log tail when stderr is empty, re-sent as stderr grows (`SidecarStatusPayload.slow`; pool `startWait` → `IpcTabInfo.slow`; over the link `TabStatusArg.statusPayload.slow`; a slow or queued re-send keeps the host tab's `omp` id and the page's state). Every view (this window, a paired computer, the phone) shows the amber `SidecarBanner` "omp is taking long to start" with the tail and Restart; Restart is the person's call, and `error` comes only from the omp exiting or failing to spawn.
  - A paired computer has no start deadline of its own (`.omp/rules/remote-devices.md` › A host tab never waits silently), and an agent's `ompdesk_session_open` waits for a starting child however long (`#whenReady`: only closed, exited or a non-held `error` fail it). `OMP_GUI_START_SLOW_MS` shortens the bound for e2e. There is no ready-time health check. `dispatchRpcCommand` (`ipc.ts`) waits for a tab that reads `starting` or `restarting` (`START_WAIT_MS`, 60 s) instead of answering `sidecar_not_ready`; the omp is not stopped when that wait ends.
- **A hung network does not hold the first answer**: stock defers MCP, model discovery (`refreshInBackground`), credential usage (`prefetchCredentialUsage`) and connection prewarm past the `get_state` answer, and OMPdesk's extensions do nothing on the network at `session_start` (verified with every outbound request hung, proxies, a black-holed route, a hung project MCP server and a cold models cache). Find the next slow start's cause from its `omp-slow-start` line, not from network errors of the same minutes.
- **The quit waits for every omp** (`OmpProcesses`, `src/main/omp-processes.ts`; `installQuitGuard`'s `settled`, which also waits for the schedules' journal: machine-setup-updates › Scheduled runs): `will-quit` is held (every `will-quit` listener, the relaunch swap included, has run by then) until `stopAll()` saw every omp exit and the core took each exit out of the file, or `QUIT_OMP_STOP_MS` (12 s: the longest one stop, ai-memory's stdin grace included) passed, then `app.exit(0)`. An update's relaunch quits the same way. The stop of each omp is the core's (`sidecar.stopAll`, native-rust › 9c), which holds the child, the stdin whose end asks an omp on Windows and the stderr on which an omp asks to be left to save a login; the teardown stops the core only once that stop answered, because the core's end takes every omp with it.
- **A launch reaps what an earlier one left** (a crash, a forced quit): the core (`native/ompdesk/crates/core/src/omp`, native-rust › 5a) keeps every running omp named in `<userData>/omp-pids.json` (`{omps: [{pid, started?}]}`, 0600; `omp.track` at each spawn and `omp.exited` at each exit rewrite it, requests nothing awaits), and `reapLeftovers()` (`omp.reap`) stops every listed omp that is still this app's, with what it started.
  - POSIX: the pid's command line holds this app's gui-bridge path, read again before each signal; SIGTERM, `STOP_GRACE_MS`, SIGKILL to its group.
  - Windows: the recorded pid is the shim omp runs behind (`omp.cmd`, bun's `omp.exe`), told by its creation time (`GetProcessTimes` in ms equals `started` exactly, because Windows reuses a freed pid within a fraction of a second and a slack would kill another program; read by the core when the spawn is recorded: no PowerShell, no WMI, no retries). Windows ends the shim with the app, however the app ended (node keeps its children in a job closed with it), and the real omp runs on (measured on the built app, 12 Nov 2026: 16 of 16 kills). So when the recorded process is gone the reap looks for what it left: a process whose parent id is the recorded pid, started no earlier than the shim, that no later holder of the pid started, and whose command line holds this app's gui-bridge path. Its stdin ended with the app, so it gets `STOP_GRACE_MS` to end by itself and is then ended with its tree through handles opened on those processes (no `taskkill`). A shim that still runs is ended at once with its tree. An entry with no `started` (a file an older OMPdesk wrote, a process the core could not read) is left running.
  - An entry leaves the file when its pid is gone and it left nothing, is another program's, or what was stopped for it is gone; one that cannot be told, or whose stop something survived, stays for the next launch. The start queue holds every start until the reap is over (`holdUntil`), at most 15 s when the core does not answer (logged as a warning); a reap that stopped something writes an `omp-reap` line. A session the launch does not bring back has its processes ended by the session sweep as well (control-tools › Session processes), whichever comes first; only the reap ends the stuck omp of a session that does come back.
  - A leftover that was still saving a login when the app quit past its bound (`STOP_HOLD_MAX_MS`) is ended by a launch within that time, on every system: the dead app's stderr, where the omp asked to be left, is gone.
- Pinned by `sidecar.test.ts` ("one stop, one start at a time": SIGTERM ignored → killed at the bound; replacement after predecessor's exit; queue limit; a slow omp is never stopped or failed, gives its place away and reads ready once it answers; empty stderr shows its own log and logs `ready` and `unanswered`), `omp-log-tail.test.ts`, `sidecar-pool.test.ts`, `remote/remote-sidecar.test.ts`, `stores/tabs.test.tsx` and `SidecarBanner.test.tsx` (the slow start reaches every banner as a wait), the `session-slow-start` parity surface, `omp-processes.test.ts` (a quit's stop leaves none; a launch reaps its leftover and spares another program) and `app-quit.test.ts` (the exit waits in `will-quit`). ### Watchdogs
- **Quit watchdog** (`src/main/quit-watchdog.ts`, electron-free, injected clock/log/exit; wired in `app-quit.ts`): once a quit is committed (the shell sends the `teardown` step, after `finalize`, which may still be asking the user; or after an NSIS installer's first-launch receipt, `details.watchdog: "update"`) the process force-exits (`app.exit(0)`, a runtime-log line `source: "background-task"`, `details.watchdog: "quit"`) if still alive after `QUIT_EXIT_TIMEOUT_MS` (30 s), because a wedged teardown otherwise strands the updater's swap helper or installer waiting for this pid. `app.exit` skips `will-quit`, so the relaunch swap registers `onQuitForcedExit` and starts through one once-only call (`updater.ts` `launchStagedSwap`). A failed `quitAndInstall()` (autoUpdater `error`) disarms the update countdown (`disarmQuitWatchdog("update")`). Idea: Orca's `update-install-exit-watchdog.ts` (MIT), reimplemented. Pinned by `quit-watchdog.test.ts`.
- **Quit order** (`tauri-shell/src/quit_chain.rs`, PROTOCOL.md `app.quit`/`app.quitHook`): the shell decides the order and sends each step to Node (`app.quitHook`), which only runs the step's prompts, listeners and effects (`app-quit.ts` `setQuitEffects`). Each committing step (`finalize`, `teardown`) is sent once; a veto after it resumes at `before` without re-sending it; a stale answer (a confirmation an approved quit overtook, a step an installer's pending launch fenced) is dropped. An NSIS update (`nsis-updater.ts`) holds the quit with `installerPending` and then sends the first worker's receipt (`started` pid or `failed`), never a stock fallback's: `elevate.exe`'s pid names the helper, not setup, and the `openPath` fallback has no pid; a failed first launch still quits, as before. Pinned by `quit_chain.rs`'s tests, `app-quit.test.ts`, `create.test.ts` and `nsis-updater.test.ts`.
- **Main-thread hang watchdog** (`src/main/hang-watchdog.ts`, `tauri-shell/src/watchdog/`): after `app-ready`, only the primary instance asks the host to consume its previous marker. Node writes `main-thread-hang` and any `machine-state` sample to `gui-runtime.jsonl` before starting observation; steps are joined by ` > ` because log details are primitives. The primary packaged app (or `OMP_GUI_HANG_WATCHDOG=1`, never Vitest) then posts its PID, 1 s heartbeats, phase/step, suspend, resume and shutdown over the existing authenticated shell connection. The host routes these before UI dispatch. Its own thread writes `<userData>/logs/main-thread-hang.json` after more than 5 s without a beat, with the eight most recent steps as of the stall. It adds a machine sample after 1 s and rewrites `selfRecovered` and the stall duration on the next beat. `detectedAt` remains the time of the latest rewrite. A tick gap over 3 s or resume restarts the wait; suspension suppresses detection. Shutdown or Node disconnection ends observation. Nothing kills or restarts Node. Idea: Orca's hang watchdog (MIT), reimplemented. Tests: `watchdog::{engine,sample,tests}`, `hang-watchdog.test.ts`.
- **A stuck page comes back by itself** (the owner's report, 19 Nov 2026: the Mac mini's window showed one frame for hours while its WebKit WebContent main thread waited in `IPC::StreamClientConnectionBuffer::tryAcquire` for room in WebKit's log stream to the app process, whose "Log work queue" slept; every IPC call there was a `fetch` to `ipc://` writing a resource-load log line, about six per call). - **GPU fallback and crash-loop guard** (`tauri-shell/src/launch_protection.rs`). ### Probes for symptoms without a repro
- Four reports came with no repro (a black console window on Windows, "Windows feels slow", an 18-hour wait, two cores lost in one minute on a computer where everything else stalled too), so each has a probe that writes its next occurrence to `<userData>/logs/gui-runtime.jsonl`. **Observation only**: none stops, retries, hides or wakes anything. Read them with `rg '"source":"console-window"' gui-runtime.jsonl*` (or `slow-step`, `turn-wait`, `machine-state`); Copy diagnostics and the diagnostic bundle carry the newest `DIAGNOSTICS_PROBE_LINES` (30) of the whole log and its `.1` in a section of their own (`## Probes`, `Selection::Probes` in `tauri-shell/src/diagnostic_logs/reader.rs`), since such a line can be days behind the last 100 entries. The log keeps only primitive `details` and a line's first 24 keys, so a probe writes flat keys, the ones every line needs first.
- **Console window** (`src/main/console-window-watch.ts`, source `console-window`, Windows only): every `CONSOLE_POLL_MS` (1 s) main asks the core for the desktop's visible console windows (`procs.consoles`, `crates/core/src/procs`: classes `ConsoleWindowClass` and Windows Terminal's `CASCADIA_HOSTING_WINDOW_CLASS`; a look never starts a core, and the process list is read only for a new window) and writes one line per window that was not there at the look before, at most `CONSOLE_LINES_PER_HOUR` (30; `dropped` counts the rest). Windows that stood before the first look are skipped unless ours.
  - `details`: `class`, `title` (conhost and Windows Terminal put the program's path there), `pid`, `exe`, `cmd`, `ageMs`, `ours`, `via`, `session`, `chain`, `parentCmd`, `recent`. `ours`: the window's process descends from main, the host or the core, or carries a tab's process tag (`SESSION_TAG_ENV`, which outlives a dead parent). `via` is the nearest of those three (`main`, `host`, `core`), `session` the tab's session file, `chain` the process and its ancestors (`git.exe(900) < ompdesk-core.exe(300) < node.exe(200)`), `parentCmd` the command line of the process that started it: together the spawn site.
  - **Windows Terminal's window is the terminal's own**, whatever program it shows, so such a line reads `ours: false`; `recent` then names what OMPdesk's processes started in the `CONSOLE_RECENT_MS` (30 s) before (name, pid, age, command line), and the title the program.
  - Known limit: a window that opens and closes within a second can be missed (the `shortcut:` note in the file names the upgrade, a `SetWinEventHook` in the core).
  - **Starts are hidden by rule**: `spawn-hidden.test.ts` holds every `child_process` start of `src/main`, `src/preload` and the bridge to `windowsHide: true`; its `WINDOWLESS` table names the starts that need none and why (macOS-only tools, window programs). The core gives itself a console that is never shown (`ensure_console`), so what it starts inherits that one even without `CREATE_NO_WINDOW`; `ompdesk check` runs its command on a desktop of its own.
  - Pinned by `console-window-watch.test.ts`, `spawn-hidden.test.ts` and the `procs` Rust tests (`names_what_the_roots_started_lately_the_newest_first`, `says_whose_a_console_window_is_only_while_it_is_new`).
- **Slow step** (`src/main/slow-steps.ts`, source `slow-step`, message `<kind> <name> took <ms> ms`, `details` `kind`, `name`, `ms`). Each kind is timed where it already runs:
  - `loop`: main's thread was kept from its timers for 200 ms or more (Node's event-loop delay at 100 ms resolution, read every 5 s; over 30 s counts as the computer's sleep), with `cpuMs` (main's own CPU in that window: far below `ms`, it waited for the disk, another process or a CPU and computed nothing), `during` (the handlers and hub waits that held the thread 20 ms or more meanwhile) and the longest of those as `name`, else `unknown`.
  - `ipc`: a handler's answer took 1 s or more, or held main's thread 100 ms or more before its first await (`syncMs`); timed in `IpcRegistry.handle`/`on`, the channels the core serves included. A handler that waits for a person (a dialog) reads slow too, once per channel in ten minutes.
  - `hub`: one synchronous wait of main on the core of 100 ms or more (`Hub.call`). `stock`: a stock helper request of 1 s or more (`StockHelper.request`). `tab-open`: an omp's start up to `ready` of 5 s or more, with `lane` and `stages` (`resolved 40ms > launch 45ms > spawned 900ms > ready 7000ms`, each counted from the lane's ask for the start's inputs; `SidecarManager.#startStep`).
  - **Rate**: one line per kind and name in `SLOW_REPEAT_MS` (10 min), the next one carrying `again` and `worstMs` for the times between, and `SLOW_LINES_PER_HOUR` (60) overall (`dropped`). A stall past 5 s that never ends stays the hang watchdog's; `omp-slow-start` and turn stages are unchanged. Pinned by `slow-steps.test.ts`.
  - `ipc.invoke.slow` (the host's own log, `<userData>/tauri-shell.jsonl`, not gui-runtime): a page's invoke that main answered after 10 s or more, or never (`code: "timeout"` at the host's 180 s limit), with `wcId`, `channel` and `ms`. A parity run once saw every page call of a window stand still for 180 s with nothing in main's log; this line names the call it waited on.
- **Long wait** (`src/main/turn-wait-watch.ts`, source `turn-wait`, message `still waiting`): every `WAIT_SWEEP_MS` (1 min) main reads each tab's resume facts; a tab with a run on or a wait held that made no step for `WAIT_REPORT_MS` (10 min) awake writes one line, then again at 20, 40, 80 … minutes (`report` counts them).
  - **A step** is the pool's `step` activity (a tool call started or ended, a reply written) or an answered question. A run that starts or ends is none, and a failed run's step is dropped, so a retry that fails every ten minutes for a day is one wait.
  - `details`: `tab`, `session`, `on` (every wait that holds, the most telling first: `ask`, `connection`, `limit`, `retry`, `stock-retry`, `resuming`, `background`, `turn`), `waitedMs`, `asleepMs` (of it, how long the looks stood still: the computer slept), `retryAt` and `attempt` of an armed retry or limit wait, `lastStop`/`lastError` of the last run, `tools` and `toolsMs` (the tool calls of the journal's last reply that have no result, by name, and since when), `journal`/`journalMs` (its last message), then the omp's own `get_state`: `omp` (`answered`; `no answer: <error>`, with the tab's `status` beside it; `no window tab`), `status`, `streaming`, `compacting`, `queued`, `asyncWork`, `settled`, `messages`.
  - A tab this computer runs for a paired device announces no steps to main, so only its held waits are read (`peer: true`), never its running turn; a paired host's tab is its host's to write. Pinned by `turn-wait-watch.test.ts`.
- **Machine state around a stall** (`src/main/machine-state.ts`, source `machine-state`; CI parity run 44640593095: both apps lost their core in one minute, "the hub did not answer within 2000 ms", while a stock worker, the host's page calls and the killed cores' exits stalled too, and no line said whether the computer or OMPdesk's own load held them). **Trigger**: a `core-loss` `abandoned` line (`trigger: "core-loss"`), or a `slow-step` line of kind `loop` or `hub` with `ms` of `STALL_MS` (2 s) or more (`trigger: "loop"`, `"hub"`); both wired in `index.ts`. **Two lines**, messages `<trigger> before` and `<trigger> after`: `when: "before"` is the newest sample taken before it, with `ageMs` and `trail` (`availMB/cpuBusyPct/appCpuPct` of the `STATE_SAMPLES` (12) kept samples, a minute, oldest first); `when: "after"` is a fresh read on the next turn of main's loop, with `afterMs`, and `timedOut: true` when the core's answer took `SAMPLE_TIMEOUT_MS` (4 s). No `before` when no sample exists yet (a stall before the memory watch's first look). One pair per trigger in `STATE_REPEAT_MS` (1 min) and `STATE_PAIRS_PER_HOUR` (20) in all; `dropped` on the next `after` counts the stalls left out.
  - **A sample** rides the memory watch's look every 5 s (`MemoryWatchDeps.sampled`, no timer of its own): the core's `memory.reading` and `memory.processes` beside what main reads itself (`readOwn`: `os.cpus()`, `os.freemem()`, `os.loadavg()`, `process.cpuUsage()`). A sample the core did not answer keeps main's part (`availMB`, `totalMB`, `cpus`, `cpuBusyPct`, `load1`, `mainCpuPct`, `elMaxMs`) and says `core: "no answer"` (or `no reading`, `no processes`). The tabs' omp pids are the ones the watch last read: the probe never asks the pool, which is a wait on the core.
  - **Keys**, flat, 23 at most: `trigger`, `when`, `ageMs` or `afterMs`, `availMB`, `totalMB`, `cpus`, `cpuBusyPct`, `load1` (not on Windows), `mainCpuPct`, `commitPct` (Windows: the commit charge of its limit), `swapMB` (macOS), `pressure`, `runQueue`, `diskQueue`, `diskBusyPct` (Windows), `appCpuPct`, `hostCpuPct`, `coreCpuPct`, `workersCpuPct`, `ompCpuPct`, `ompCount`, `appMB`, `elMaxMs` (main's longest event-loop delay of the last 5 to 10 s, `slow-steps.ts` `loopMaxMs`; a p99 over 50 intervals says the same and is left out), then `core`, `timedOut`, `trail`, `dropped`. Every `…CpuPct` is a share of all processors since the sample before (100: every one busy; one pegged thread reads 100 / `cpus`), so `cpuBusyPct` less `appCpuPct` is what other programs used. A process counts for the nearest of OMPdesk's own above it in the listing: `host` (the window's shell and its webview processes), `main`, `core`, `workers` (what the core started besides the omps: the stock helper's workers, a git, a gh), `omp` (each tab's omp with everything under it); `appCpuPct` and `appMB` sum them all, `mainCpuPct` is main's own `process.cpuUsage()`.
  - **Reading one occurrence.** The computer: `availMB` low or `pressure` not `normal`, `commitPct` near 100 or `swapMB` high, `diskQueue` standing with `diskBusyPct` near 100, or `cpuBusyPct` near 100 with `runQueue` (`load1`) well above `cpus`, each while `appCpuPct` is a small part of `cpuBusyPct`. Our load: `appCpuPct` is most of `cpuBusyPct` (the `…CpuPct` beside it names which processes), or `appMB` is most of `totalMB` less `availMB`. `mainCpuPct` near 100 / `cpus` with a high `elMaxMs` is main computing; a high `elMaxMs` with `mainCpuPct` near 0 is main waiting on a call. A `before` whose `ageMs` is far past 5 s says the samples themselves stopped: main's thread, or the whole computer, stood still. Both lines quiet and still a stall: no load at all, one process stuck.
  - **A hang** (`trigger: "hang"`, `when: "during"`, message `hang during`): while Node is stalled the shell samples machine memory (`availMB`, `totalMB`), processors (`cpus`, `cpuBusyPct`), the one-minute load average (macOS only) and CPU time of Node's PID (`mainCpuPct`, not the shell's). The next launch writes the marker's `machine` sample right after the `main-thread-hang` line, with `at` for when that was. A stall that recovers within 30 s writes the `loop` pair too.
  - **Limits**: macOS reads no disk and no queue (`swapMB`, `pressure` and `load1` stand in); a process whose parent ended (a daemon) and macOS' WebKit processes (launchd starts them, not the shell) are in nobody's share; a process that started and ended between two samples is not counted; a reused pid can put one stranger under ours for one sample (the `shortcut:` note names the upgrade). Cost: one reading 1.6 ms on Windows (native-rust › 3b); `os.cpus()` once per sample in main.
  - Pinned by `machine-state.test.ts` (a lost core's pair with every key, a slow step under 2 s, a core that does not answer, the rate, 24 keys), `hang-watchdog.test.ts`, `watchdog::tests`, `memory-sampler.test.ts` (the real core's new fields) and the `memory` Rust tests.

- Settings › Updates & about, `settings/DiagnosticsRow.tsx`; channel `diagnostics:build` = `window.omp.runtime.diagnostics()`, `host-admin` in `ipc-policy.ts`; builder `src/main/diagnostics.ts`, registered in `index.ts` via `registerDiagnosticsIpc`, electron-free like `tools/ipc.ts`. Copy puts exactly that text on the clipboard. **Nothing is uploaded or written**; no network. A private `app.diagnosticLog` host request reads the fixed `logs/gui-runtime.jsonl` or `.1` under the shell’s own user data on a blocking worker, without the core. Each entry window is 1 MiB and 3,000 nonempty lines; probes search up to 5 MiB per file. `runtime:log-tail` remains a separate feedback-dialog read.
- **A runtime-log source is a compile-time contract** (`gui-runtime.jsonl`), so no line is written as `unknown` and loses its area. `writeRuntimeLog` / `appendRuntimeLogAtPath` take a `RuntimeLogReport` whose `source` is `RuntimeErrorSource` (`src/shared/ipc-types.ts`), so a new source is added there with a doc comment and as a row of `RUNTIME_ERROR_SOURCE_TABLE` (`Record<RuntimeErrorSource, true>`, `runtime-log-core.ts`; tsc fails without it). Only the renderer's IPC payload is untrusted: `ipc.ts` runs it through `normalizeRuntimeErrorReport`, which turns a name outside the union into `unknown` and keeps only flat details. Main's own details stay flat too, except one array per source named in `STRUCTURED_DETAIL` (`runtime-log-core.ts`; today only `bridge-health`'s `unavailable`), kept as an array: its source bounds it by whole entries and records how many it left out (`unavailableOmitted`), and a list still past 4 096 characters is left out, never cut into a string. There is no top-level `level`; a severity is `details.level`.
- **A repeating line folds into a count** (`appendRuntimeLogAtPath`, `runtime-log-core.ts`): the 0.134.0 quit wrote 6,175 copies of one rejection in 0.23 s, and the two 4 MB files then held nothing from before it. A line identical to one written within `REPEAT_WINDOW_MS` (10 s) of its last copy (every field but the timestamp: source, message, stack, details, context) is not written; its copies become one line under the same source, `repeated N times in T ms` (`details`: `repeatOf`, `count`, `spanMs`, `first`), written when the copies stop, before the next new line, every `REPEAT_REPORT_MS` (1 min) while they go on, and at process exit. Lines that differ only in details (three `turn-resume` `marker` lines) are each written. Pinned by `runtime-log-core.test.ts` ("a line that repeats").
- **A call into the core after it shut down is one handled line, never a crash** (`src/main/main-failures.ts`, source `core-shutdown`): once `shutdownCore` ran (the quit's `core` step, or `endMain` when the shell's connection ends, which runs no teardown), every call is refused (`isCoreShutdown`), and timers, listeners and promise chains still alive reach it from many places. Main's last-resort handlers write such a refusal as `core-shutdown` (not `main-unhandled-rejection`/`main-uncaught`, so e2e does not count it as a failure) and do not end main on it; any other uncaught exception is logged and ends main with exit code 1 as before. - `resources/gui-bridge/redactor.ts` (`redactDiagnosticsText`; `redactSecretText` is its credentials group alone; pure, import-free: the memory extension embeds it for turn conclusions, see Memory quality) hides, in order: URL userinfo, PEM blocks, JWTs, vendor tokens (`gh*_`, `github_pat_`, `sk-`, `xox*-`, `AKIA…`, `AIza…`), `Bearer` values, `key=value` whose key names a secret (`tokens` counts and `true/false/null/numbers` stay), hex runs ≥ 32 and mixed-case base64-ish runs ≥ 32, emails (`git@host` stays), tailnet addresses (100.64.0.0/10, `fd7a:115c:a1e0::`, `*.ts.net`), LAN addresses (10/8, 172.16/12, 192.168/16, `fe80::`, `fc00::/7`), home folders (`/Users/<name>`, `/home/<name>`, `C:\Users\<name>`, also JSON-escaped, spaces in a Windows name) → `~`. A new secret or address kind a log can hold gets a rule and a test there. Idea (five families): Orca's `observability/redactor.ts` (MIT), reimplemented.
- **Turn stages: a turn that waited long without saying why**: `resources/gui-bridge/turn-stages.ts` (core `turn-stages-core.ts`, contracts `turn-stages-contracts.ts`, area `turn-stages`, capability `turnStages`) keeps a timestamp per stage in memory and writes ONE `gui-runtime.jsonl` line (source `turn-stages`, bridge frame `turn_stages` → `src/main/turn-stages-log.ts` → `sidecar-factory.ts`) per model call only when its first output (the first `message_update` of the assistant message) came more than 30 s after the wait began (the prompt for a run's first call, its `turn_start` after a tool batch), written as that output arrives, or when the run ended (`agent_end`) aborted or errored with the call having produced nothing, and one per prompt whose setup ended more than 30 s after the prompt without starting its run (below). A normal turn writes nothing and sends no frame; nothing per token; no timer, watchdog or abort (a stall that never ends, or a killed process, leaves no line). `OMP_GUI_TURN_STAGES_LATE_MS` shortens the 30 s threshold for tests.
  - **A prompt's wait belongs to its own `prompt` call** (the main session's `prompt`, wrapped once on the instance: `promptStarted` .. `promptSettled`; the wrapper hands back its result or error unchanged). Its runs' `t0` is the `input` hook of the same text (at most 10 minutes earlier; text another extension's `input` hook rewrote: the `prompt` call's own time), else the call's start. A run outside any `prompt` call (a queued follow-up, a continue, a retry, a goal continuation) counts from its own first event and says "no prompt seen". Stock ends a setup cancelled before `agent_start` (Stop, a newer prompt, usage preflight, cost cap, a thrown "No API key") with no agent event, so the call's return or throw is the only sign: a setup over 30 s writes `outcome: cancelled` (or `error` with the thrown message) ending at `setup_end`, never for a slash command. Everything a prompt left unstarted is dropped at the next `input` hook and the next `prompt` call, so a stopped setup never lends its times to the next prompt; a `before_agent_start` pass on a run whose handlers already ended starts a fresh run unless the same `prompt` call is still setting up (stock re-runs the handlers when the tool set changed: `AGENT_START_POLICY_MAX_ATTEMPTS`).
  - Stages, as `at.<stage>` = ms since the prompt: `handlers_start`/`handlers_end` (every extension's `before_agent_start` handlers: the main session's `ExtensionRunner.emitBeforeAgentStart` wrapped once on that instance), `agent_start`, `turn_start`, `provider_request` (the call's first request: the payload callback of the options the main loop hands the main agent's `streamFn`, wrapped once on that instance), `stream_open` (first provider-stream event reaching the agent loop), `provider_response` (that callback set's last response: headers arrived), `first_output`, `compaction`/`compaction_end` (a compaction opens a run only inside a prompt's setup), `agent_end`, `setup_end`. Other keys: `outcome` (`late`/`aborted`/`error`/`cancelled`), `call`, `waitedMs`, `lastStage`, `longestGap` (`from>to <ms>ms`: the transition that took longest), `providerRequestSent`/`providerRequests` (the main loop's own request bodies in this call: one per model call plus each body stock rebuilds and resends after some 400s, NOT per HTTP attempt), then the optional `error`, `provider`, `model` and OMPdesk's own time inside the handlers: `memoryRecallMs` (`modes/memory-recall.ts`), `sectionsMs` (`prompt-sections.ts`). At most 24 keys (`runtime-log-core.ts` `MAX_DETAIL_KEYS` keeps the first 24): the core keys and every `at.*` come first, the optional ones fill what is left in that order. Requests before `agent_start` are ignored. No `context`, `message_update`, `before_provider_request` or `after_provider_response` extension handler is registered (cost per request or per token, and the provider hooks also see advisors' requests): the first output comes from the session's own `subscribe`.
  - **Only the main loop's requests count**: stock runs the provider hooks for side requests made with the session's `onPayload`/`onResponse` too (each advisor's own `Agent` in `session-advisors.ts`, side calls through `session-provider-boundary.ts`), which skewed the stage times. Every request through the main agent's `streamFn` is the main loop (stock's own comment, `sdk.ts`).
  - **The same wrapper feeds the working cue**: each main-loop request also goes to the windows as `model_request` (`sent`, then `answered` for headers below 400), and a request unanswered for 30 s reads "Waiting for the model's response · n" instead of "Thinking…" (rules in `.omp/rules/composer.md` Working cue). It is the only frame the tracer sends per request; the log line stays one per late call.
  - **Read it so**: a refused connection and a silent server both leave `at.provider_request` then nothing until `stream_open` just before `agent_end`, with no `at.provider_response`: `longestGap` `provider_request>stream_open` is the whole request phase. Stock's Anthropic provider retries inside that phase without another callback (up to 10 retries, backoff 0.5 s doubling to 8 s), and each attempt of a silent server is aborted by the first-event timer at `PI_STREAM_FIRST_EVENT_TIMEOUT_MS` (300 s by default, `idle-iterator.ts`). A stall before the request names itself: `prompt>handlers_start` (stock's preparation: usage preflight, API key/OAuth refresh, MCP discovery, memory auto-recall), `handlers_start>handlers_end` (the extension handlers; `memoryRecallMs`/`sectionsMs` say whose), `handlers_end>agent_start` (auto thinking, auto plan classification, pre-prompt compaction), `agent_start>turn_start`/`turn_start>provider_request` (context transforms, image normalization, `getApiKey` for the request).

### Diagnostic bundle
- "Save diagnostic bundle" ("진단 묶음 저장") in a session row's context menu and touch action sheet (a paired host's rows too) and in Settings › Updates & about beside the diagnostics Preview (focused tab). The plain item is stock `/dump all`; holding Option/Alt or the "(anonymized)" item is stock `/dump anon`. A stored session no tab holds has the item disabled (stock's dump runs inside the tab's omp).
- Over stock RPC `/dump all|anon` only prints the archive path in a `command_output` frame and rides the prompt queue. The `session_dump_redacted` bridge method (`resources/gui-bridge/session-dump.ts`, feature `sessionDump`) calls the same `dumpSessionArchiveToTmpDir()` / `dumpAnonymizedArchiveToTmpDir()` inside the tab. The local `dump_session_archive` and `discard_session_archive` command shapes and quota rules are unchanged.
- **Every member is redacted, both variants** (the UI promises it). The bridge opens stock's private ZIP and writes only a redacted ZIP to the core's reserved destination. Every UTF-8 text member passes through `redactDiagnosticsFile` (`redactor.ts`); non-text members are omitted and reported by redacted name in `dropped`. `/dump anon` keeps stock's anonymizer before that pass. The bridge removes stock's original on success and failure. No original archive, raw member or unredacted path goes to main or the core. `redacted: true` is required; main refuses an unredacted archive (`remote_protocol`, never saved). `archive.discard` verifies the recorded path and private receipt even after a core restart. A new redaction need goes into `redactor.ts`, never a second redactor.
- Main's `sessions:dump-bundle` (`src/main/diagnostic-bundle.ts`): save dialog first (cancel makes nothing), then the dump on the tab's omp, then `ompdesk-diagnostics.txt` (the Copy diagnostics text) added as a zip member by `diagnosticBundle.save` in the Rust core, written, and the temp archive deleted even on failure. A paired host's tab dumps on the host through `tab.command` and reads the bytes back with `host.fs.readBinary` (`FS_BINARY_REMOTE_MAX_BYTES` 11 MB, else `file_too_large`); the host's temp zip is discarded. A web page picks the path on the computer through the host browser's save mode (`destination: {kind: "path"}`).
- Agents: `ompdesk_app` `sessions.dump_bundle {session?, anonymized? = true, path?}` (tier `change`, no card): anonymized unless asked otherwise, written to the absolute `path` or Downloads (never overwriting), refused for a session hidden from agents.
