## Models, accounts and held stock defaults

### Desktop slot
- One session at a time drives the desktop. Files: contract `resources/gui-bridge/desktop-slot-contracts.ts`; bridge `desktop-slot.ts` + `desktop-slot-core.ts`; main `src/main/desktop-slot.ts` + `desktop-slot-host.ts` + `local/desktop-slot.ts`; renderer `stores/desktop-slot.ts`, `DesktopSlotIndicator.tsx`, the waiting line in `ToolCard.tsx`; capability `desktopSlot`.
- WHY: each omp has its own `ComputerSupervisor`; stock only refuses input while another operation owns focus, never queues, never spans observe → act → verify, and nothing crosses processes. So the native core (`hub/desktop_slot.rs`) owns one slot per computer and the bridge patches `ComputerSupervisor.prototype.run` once (feature-detected; without `run`/`revokeControl` the slot is `unavailable` in capabilities/health and stock behaviour stays).
- A `snapshot.readOnly` run (screenshots, `capabilities`) never waits, nor does a run under stock's `computer.backgroundFallback: "refuse"` (`needsSlot` in `desktop-slot-core.ts`), because stock then refuses anything that would take the foreground (`worker.ts` `refuseForeground`), so such runs of several sessions go side by side (`runBackground`: with no slot held it runs at once; while the session holds the slot, lets go of it or failed to revoke, it is an acting run, so a revoke aborts it and a failed revoke blocks it). Under the default `takeover` an acting run takes the slot.
- The first acting run takes the slot (`desktop_slot_acquire` → `desktop_slot_bridge`) and keeps it until `agent_end`, `DESKTOP_SLOT_IDLE_MS` (20 s) without a computer run, Stop, abort, tab close/crash, or lease expiry (`DESKTOP_SLOT_LEASE_MS` 120 s without `desktop_slot_touch`).
- Waiters queue FIFO. An acting run that had to wait does **not** run once granted: it returns `DESKTOP_SLOT_STALE_NOTICE` so the agent re-screenshots and repeats.
- **Handoff**: abort the holder's in-flight input run, await stock `ComputerController.revokeControl()` on every controller the bridge saw, only then grant the next session.
- **Never handed on unconfirmed.** A `revokeControl()` that rejects (holder's acting runs get "input is blocked") or is silent for `DESKTOP_SLOT_REVOKE_TIMEOUT_MS` (10 s) leaves the holder `revoke-failed` (`DesktopSlotState.holder.revokeFailed`): nobody is granted, main retries every `DESKTOP_SLOT_REVOKE_RETRY_MS` (5 s; a late answer counts), the indicator offers "다시 시도" (`desktop_slot_retry`) and "그 세션 중지" (`desktop_slot_kill`: abort + `restart()` of its omp, SIGTERM only).
- Only a confirmed revoke or exit of the holder frees the slot. The host binds each grant to the core generation, spawn and bridge-reported omp process. Exit of a Windows launcher alone does not free the slot. Permission errors and an unconfirmed kill do not prove exit. A bridge `desktop_slot_release` follows only a confirmed revoke.
- UI: app-wide "화면 사용 중: <title> · 대기 N" with Stop (`desktop_slot_stop`: aborts the holder's turn, hands off); a waiting `eval` card says "화면 차례를 기다리는 중 (N번째)".
- Hosted tabs for a paired device join this slot; tabs on a remote host use that host's slot (main skips `sidecar.device` tabs). Autopilot never takes it (its `eval` is off). No "run marked done" release (stock has no marker).
- Tests: `desktop-slot.test.ts`, `desktop-slot-host.test.ts`, `bridge-desktop-slot.test.ts` (rejecting/silent revoke, holder death, kill), `e2e/desktop-slot.e2e.ts`.

### Account rotation
- Settings › Models & accounts pref `accountRotation` (`quota` default = stock's usage ranking | `even`; `src/shared/account-rotation.ts`, `providers/RotationModeControl.tsx`). Each spawn gets `OMP_GUI_ACCOUNT_ROTATION` and the shared ledger `<userData>/account-rotation.json` (`OMP_GUI_ACCOUNT_ROTATION_STATE`); a change or bridge connect pushes `account_rotation_set {mode}` to every live local sidecar and every tab this machine hosts (`LocalMachine.setAccountRotation`, `src/main/account-rotation.ts`). A paired host's tabs follow the host's pref (`host.accountRotation.get|set`).
- **Even**: the bridge's `account-rotation.ts` (`before_agent_start`) gives an account-less session the unblocked account handed out least recently across all local omps, as an automatic warm pin (`authStorage.sessions.pin(…, {restoredAtMs})`). A session keeps it until blocked (idle pin renewed, not re-ranked); stock's 429 blocking/failover is untouched.
- **Quota re-ranks at turn start.** Because stock re-ranks an automatic pin only when cold, blocked or spent and every request refreshes last-use, so a busy session never left its first account. `rerankBeforePrompt` (`account-rotation-core.ts`) runs in the same hook for the main agent only (`ctx.agent.kind === "main"`; subagents keep the spawn copy via `sessions.inherit`); mid-turn checks are below.
- It asks stock, not our own policy: the account stock's selector would give a pinless session now (`authStorage.keys.getWithCredential(provider, <stand-in id>, {…, recordAffinity: false})`). It moves the pin (automatic warm pin, `restoredAtMs: now`) only when ALL hold, else stock decides: >1 account; pin exists and is warm; pin is automatic (read via the `include(provider, explicit)` callback of `sessions.inherit` with a stand-in target returning `false`; no provenance = left alone); session unrestricted (`sessions.permits`) and no account has a stock policy (`oauth.policy`), because pools/policies are the user's choice; pin not blocked; both accounts measured and stock's comparator (`orderUsageRankedCandidates` over `RankedOAuthCandidate` rows from both `usage.report`s, mirroring `#rankOAuthSelections`) still ranks the other first after the pin's required drain is multiplied by `RERANK_DRAIN_MARGIN` (2).
- The margin is OMPdesk's only addition, because every switch rewrites the provider's per-account prompt cache. Only the plain drain order gets it; stock tiers (blocked, spent, 85% 5h demotion, unmeasured) move a pin at once. Proper fix belongs in stock.
- **Between two model calls of a long turn** (`after_provider_response`, main agent only; capability `accountRotation` lists the session member `extensionRunner.emitAfterProviderResponse()` and `AgentRegistry.prototype.list|isRunning`; a module probe of the runner would be a second module graph): the same decision runs again (`rerankMidTurn`) because a main session here runs turns for hours and only moved after a 429 otherwise. Why this hook: it fires after every response and before the next request's key is resolved, so a pin written there serves the next call and the stream in flight keeps its account; stock holds the response body until extension handlers return, so the check is **not awaited** (single-flight per session, at most once per `MID_TURN_CHECK_MS` = 60 s, reading only stock's cached reports). A `context` hook would also reach the next request but makes stock clone the whole context on every request (`context-hook.ts`), and `turn_start`/`tool_execution_end` are pushed on an event stream the loop does not wait for. **The move rule is one pure function, `decideMove` (`account-rotation-core.ts`), with a table test**:

  | phase | usage read | pin / top pick | answer |
  | --- | --- | --- | --- |
  | either | one account unread | - | stay `usage-unreadable` (never "unmeasured, so the sibling wins") |
  | either | both read | the top pick's window for the session's model is spent or full (`limited`) | stay `target-limited` |
  | either | both read | pin near limit (5h window at stock's 85% demotion step, `HOT_PRIMARY_FRACTION`, or allowance spent), top not | move `near-limit` |
  | turn start | both read | stock ranks top first after the 2x drain margin | move `better` |
  | turn start | both read | otherwise | stay `within-margin` |
  | mid-turn | both read | top near limit too | stay `no-better` |
  | mid-turn | both read | top's required drain >= `MID_TURN_DRAIN_MARGIN` (8x) the pin's, on the first window both are measured in (stock compares the 7d one first) | move `much-better` |
  | mid-turn | both read | otherwise | stay `mid-turn` |

  The other stays are `rerankSession`'s cheap checks (`mode`, `no-model`, `single-account`, `no-pin`, `cold`, `unknown-provenance`, `explicit` = pinned by the person, `restricted`, `policy`, `blocked`, `subagents`, `no-choice`, `same`, `pin-refused`). **A session never moves mid-turn while one of its subagents runs** (`subagents`): a subagent holds the account it was spawned on, so a parent that moved would split the task over two accounts. 8x is a choice, not a measurement: the log of 12 Nov 2026 shows a session going 8 → 7 → 8 → 7 inside 90 minutes at turn start with the 2x margin, so mid-turn moves on plain drain are made rare. **A target whose window for the session's model is spent or full is never moved to** (`target-limited`, `AccountFacts.limited`, the owner's top finding from the logs: a move onto an account whose Fable cap stock still read as usable was answered 429 on the first request): the bridge reads the windows stock ranks for that model (`scopeLimitsForReserve`, else `scopedUsageLimits`, so a model's own weekly row counts, unconfirmed or not) and calls the account limited when one is exhausted by stock's own predicate (`isUsageLimitExhausted`) or a non-shared row of the model is at `MODEL_WINDOW_FULL` (98%), because stock gates a Fable row only at 100% with a live reset time (pi-ai `usage/claude.ts` `isConfirmedExhaustedTierRow`). A pin that is itself limited counts as near its limit. Limits of this check: it reads the cached report, so a cap spent since that report (up to the 5 min cache) is not seen. **Measured on 18.20.0** (`bridge-account-rotation-stock.test.ts`, first CI run of the case): with the sibling's Fable row at exactly 100% and no reset time, stock's selector kept the pin on the account at the 85% step instead of picking the sibling [INFERENCE: `remainingUsageFraction` 0 reads as `allowanceSpent`, which ranks above the 85% demotion]. So the case this check adds is a row short of 100% that stock neither gates nor counts as spent, and the real-omp case puts it at 99% with no reset time on the account stock picks (the pin's account at the 85% step): the pin stays, and with the row at 50% it moves.
- **Every decision leaves a log line** (`gui-bridge: quota re-rank moved|kept the session's account`, fields `phase`, `why`, `from`/`to`, both accounts' facts `pin`/`top` and `topFirstWithMargin`; info at turn start and for a move, debug for a mid-turn stay). The core keeps the last decision per session (`recordDecision`/`lastDecision`, 64 sessions), and the bridge carries it as `UsageReport.rotation {why, moved, phase, at}`. The renderer shows no ranking or rotation explanation, including in tooltips (the owner's call, 14 Nov 2026); rotation logic and diagnostic data stay unchanged.
- **A person's Refresh is answered at once.** `get_usage`/`get_provider_accounts` with `refresh` drop stock's cache for every provider with a report whatever the report's age (the 60 s `REFRESH_FRESH_MS` suppression stays only for the credits-only ChatGPT fetch outside a refresh); `refresh` is sent by the explicit button only, never by the poll, and it is the only read that goes through the failure backoff (`useUsageRead`, tested in `use-usage-reports.test.tsx`). **The in-use account reflects response headers as stock allows**: `usage.ingestHeaders` merges them at most once a minute per account (`USAGE_HEADER_INGEST_INTERVAL_MS`, stock; except a window that reads exhausted, which is persisted at once), so the gauge of the account in use can lag the real figure by up to that minute plus the read gap. **While reads fail, the poll keeps its doubling backoff (5, 10, 20 min) and holds the focus and turn-end reads** (`watchUsage`; the owner's call, 13 Nov 2026: a failing day reads about 73 times, as before, never more; test: a simulated day with a turn ending every two minutes, at most 720 reads healthy, 74 failing). The 22 Oct incident (313 `/usage` calls in a day on one Mac) must not come back.
- **A usage read says what it is** (C18, 20 Nov 2026: one read of a ChatGPT account said "limited until" and the next, on the same computer, "warning" on the same 100 %, while another computer kept using it). The bridge's `usage` answer carries the reading omp's Credit use (`creditSpend`), and each report `limitedUntil` (`usage-standing.ts`: an exhausted account-wide row by stock's `omp usage` pool rule, so a model's own week such as Fable or a Codex Spark meter never limits the account; with Credit use off also the plan's reset, which credit-spend.ts refuses until), `planSpentUntil` (`planSpentUntil` of credit-spend-core.ts) and `credits` (ChatGPT's from the fetch's `raw`, else the account's last fetch). `resetAt` keeps stock's rule over every row, because the limit waits (`quotaResetAt`) must wait out a model's own week. `usage.read` (core `describe_usage`) opens with the computer, time and Credit use of the read, prints every account's read time, "limited until" only from `limitedUntil`, "plan used up until X; requests still allowed" while the provider still allows it, and the credit balance as a balance. **It never says requests run on credits or that money was spent** (Main's call, 20 Nov 2026): a 100 % row the provider still allows (stock's `warning`: an explicit allow or credits funding overage, which the cached report does not tell apart), a balance, Credit use on or a served answer prove no debit. Two logins of one email (a Pro seat and the same person's Team seat share stock's email-first match) are told apart by the report's account id (`matchReportAccount`). A change of Credit use writes one `gui-runtime.jsonl` line (`source: "credit-spend"`). Pinned by `bridge-usage-standing.test.ts`, `bridge-usage-standing-stock.test.ts` (touchpoint C19), `bridge-accounts.test.ts` and the usage cases of `app-control.test.ts`.
- **Cases from this computer's logs and sessions (13 Nov 2026: `~/.omp/logs`, session files of 7-13 Nov; the other computers' logs were not reachable).** The log counted 29 `quota re-rank moved` lines and no line for any other decision, so only the session files (`credential_pin` entries, each assistant message's `credentialId` and 429 `errorStatus`) could show what happened next. (1) **A move into an account that answered 429 on its first request**: of the 4 pin changes at a turn start that could be followed to the next request, 3 (10→7 twice on 10 Nov 09:14-09:15, 10→8 on 11 Nov 14:05), all on `claude-fable-5-2`, with `retry-after` 3.7 h and 54 min. [INFERENCE] the move trusted the 5h/7d windows of the usage report while the provider's limit for that model was spent. (2) **Stayed on the blocked account after the 429**: the same prompt failed four times in four minutes on the account moved to (11 Nov 14:05-14:09), and one session's next prompt five minutes after its 429 went to the same account (10 Nov 09:19); the pin changed at 14:11:51 and after 09:24. Stock ends the turn with the 429 when `markReached` finds no usable sibling (`turn-recovery.ts`, "No sibling credential is usable right now"). [INFERENCE] the siblings' usage was unreadable then: the logs hold 167 `Claude usage fetch failed` 429s and 20 403s, up to 22 an hour (10 Nov 00-06 h); no log line records the failover itself. (3) **Flip-flops**: 8↔7 three or four times inside 90 minutes on 12 Nov 08:15-09:52 in three sessions, each rewriting the prompt cache; this is what the 8x mid-turn margin guards against. (4) A Fable weekly 429 (`retry-after` 6939 min) was answered by stock's model fallback to Opus, not by an account move: not a rotation failure. Not found in these files: an account with room left unused for long.
- **Why a never-used account with no 5h window is not chosen: stock working as designed, not an OMPdesk defect.** Stock ranks by required drain, headroom per hour to reset (`windowRequiredDrain`, pi-ai `auth/usage-report.ts:256-269`; order in `auth/rank.ts` `compareUsageRankedCandidatePriority`, 7d drain first): an account whose 7d window has not started (no reset clock) counts the full 168 h as remaining, so its drain is the smallest of all, and the account whose week ends soonest drains first ("use it or lose it"). It is chosen when the in-use account's 5h window reaches the 85% demotion (`rank.ts` `PRIMARY_WINDOW_HOT_FRACTION`), since a missing 5h window reads 0.5 used (`normalizeUsageFraction`) and is never hot. A 7d reading of 0% means only that the weekly usage read 0%, not that the account was never used.

### Credit use
- The owner's rule (12 Nov 2026): no money leaves an account because OMPdesk kept working past the plan, unless he turned that on. Settings › Models & accounts › Credit use (`providers/CreditSpendRow.tsx`, under the rotation control), one switch for every account, pref `creditSpend` (`src/shared/credit-spend.ts`), **off by default**. Each spawn gets `OMP_GUI_CREDIT_SPEND` (`0`/`1`, `sessionEnv`); a change or bridge connect pushes `credit_spend_set {enabled}` to every live local omp and every tab this machine hosts (`syncCreditSpend`). A paired host's tabs follow the host's pref (`host.creditSpend.get|set`). Agents never switch it (`app-channels.ts` `SPEND`, `ROW_NOT_WRITTEN`).
- **OMPdesk never buys credits or switches a top-up, and sets none up** (the owner's call, 20 Nov 2026). A provider's auto top-up (ChatGPT's "automatic reload", Claude's extra usage) fires only when credits are spent; neither usage answer tells stock whether it is enabled, so OMPdesk can only avoid triggering it by not spending. Under the switch stands one visible line, "OMPdesk never buys credits. Auto top-up is set at the provider:", with one ghost link per provider (`TOP_UP_PAGES`: `https://chatgpt.com/codex/settings/usage`, `https://claude.ai/settings/usage`, through `lib/open-external.ts`; `data-credit-top-up`, `data-credit-top-up-link`). Nothing else about top-up belongs in the row: no control, no state read.
- **With the switch off there is no exception** (the owner's call, 20 Nov 2026, closing the two gaps this section used to pin: the first request and the wait for ChatGPT's next usage report). Every path below is checked where stock hands a request its account, in the process's one `AuthStorage`.
- Why stock spends: ChatGPT's plan-spent report with `credits.has_credits` reads allowed (pi-ai `usage/openai-codex.ts` `hasPlanCreditOverage`, `buildPlanMeterState`), and whatever a report says, stock's selector ends on a last-resort pass that takes a blocked account (`auth/select.ts` `resolveOAuth` passes `allowBlocked: true`) and reads no usage at all with one account (`#oauthUsagePolicy`: `credentials.length > 1`). Measured on 18.18.9: one spent ChatGPT account with credits is sent every request; with a sibling that has plan left stock already moves to it.
- **Off** (`resources/gui-bridge/credit-spend.ts`, rules `credit-spend-core.ts`): ChatGPT's usage provider is stock's own wrapped as a runtime override (`usage.providerFor` → `usage.setProvider`, its own `cacheVersion` namespace so a terminal omp's "allowed on credits" report never reaches it): `/wham/usage` reaches stock's parser without `credits`, the report's `raw` keeps the real answer for the credits figure, a report whose answer held credits is marked (`metadata.ompdeskCreditsHeld`), and `x-codex-*` headers are parsed without the 2xx verdict so 100 % reads spent. The account stock picked is checked on both ways a request gets one, `keys.getWithCredential` and `oauth.access` (the prompt-time probe `keys.get` stays stock and sends nothing): plan spent by its report (`planSpentUntil`: a plan window at 100 % with its reset ahead, or Codex `limitReached`), or a provider's answer said it is past its plan (the ledger below), is refused with a `usage_limit_reached` error carrying stock's `retry-after-ms` hint; stock then blocks the account (`limits.markReached`), rotates, walks `retry.fallbackChains` or shows the error. **On**: the override is removed, the checks pass everything, the ledger is emptied.
- **Every path, and where it is closed** (stock locations are omp 19.0.0):
  - The agent loop, subagents (in-process and worker threads, whose `AuthStorage` is a proxy of the main thread's: `thread/services/auth.ts`), advisors, titles, compaction and branch summaries, commit messages, image questions, speech, memory, the bridge's own one-shot calls (`modes/auto-title-engine.ts`, `next-prompt-engine.ts`, judge assists): all resolve through `modelRegistry.resolver` → `keys.getWithCredential` (`config/model-registry.ts` `getApiKeyWithCredentialForProvider`).
  - **A forced token refresh** (stock's answer to a 401: `auth/cascade.ts` `resolver`, `forceRefresh: true`) goes through the same `keys.getWithCredential`, so the refreshed key is refused like any other.
  - **Codex web search and the live transport** (`web/search/providers/codex.ts`, `live/transport.ts`) ask stock's selector for the account itself through `oauth.access` (`auth/oauth.ts` `access`, `auth-retry.ts` `withOAuthAccess`), which the key check never saw: wrapped the same way.
  - **The first request of a process.** The checks are installed when the bridge's areas load (main's connection at `ready`, or the first prompt's `input`), from the spawn env alone, not at the first `before_agent_start` or `credit_spend_set`: a one-shot call needs no turn.
  - **A Claude model's own week** (Fable, Opus, Sonnet): `planSpentUntil` also reads the windows stock counts for the request's model (`scopeLimitsForReserve`, else `scopedUsageLimits`, as account-rotation.ts does); one spent refuses that model before its first request (a row without a reset time for stock's default 30 min), the account's other models go on.
  - **What a response said, for every session.** Claude's `overage-in-use` header (`after_provider_response`, `overageUntil`) is kept until the claimed window resets in one file of the agent directory, `ompdesk-credit-limits.json` (beside the credential store its ids belong to; `parseLimited`), which every OMPdesk omp of that directory reads at each check: a new session's first request is refused. **An overage answer stops only what its window covers** (`overageCoversAccount`): the whole account for a window all its models share (`five_hour`, `seven_day`), only the served model for a model's own weekly window or a claim this build has not heard of. A reset pass spent on the account drops its entries (`forgetLimited` from `reset_pass_redeem`).
  - **A ChatGPT plan that runs out between two usage reports.** Stock never hears a served Codex request's limits (`providers/openai-codex-responses.ts` calls no `onResponse`; the hook never fires for Codex), so the account went on on credits for the rest of the report's life, about 5 minutes. For an account whose answer held credits the check decides how far its report can be trusted (`reportTrust`): under 90 % of a plan window a report may be as old as the plan it shows left (all of stock's 5 minutes untouched, 30 s at 89 %), then it is read again and a failed read changes nothing (`aging`); from 90 % (`NEAR_SPENT`) nothing goes out once this omp sent a request since the read, or 15 s passed (`unconfirmed`), until the usage is read again: one read per request, through the override's own `fetchUsage` with stock's fetch context, one at a time per account. A read that fails there holds the request 60 s (`UNREAD_HOLD_MS`, `UNREAD_USAGE_ERROR`, which stock's retry waits out) and is tried again no sooner than 15 s. An account without credits is left to stock: the provider itself refuses its spent plan.
  - A paired host's tabs run on the host's omps with the host's switch (`host.creditSpend.*`, `syncCreditSpend` over hosted tabs). Account rotation only moves a pin; its ranking probe (`recordAffinity: false`) goes through the same check and counts as no request. `stock-helper` workers, the stats host, the MCP hub and the boot-model script call no model.
  - **An `omp -p` OMPdesk starts beside its sessions** has no bridge, so stock alone served it from credits: a scheduled run (`schedules.ts` `ompRunLauncher`) and a PR draft (`local/git/pr.ts`, through the tab's `ctx.omp`: `withCreditSpendRuns` in `sidecar.ts` `#localContext`) get `-e <gui-bridge>/credit-spend-run.ts` and `OMP_GUI_CREDIT_SPEND` (`creditSpendRun`, `omp-launch.ts`); that extension installs credit-spend.ts alone, whose `before_agent_start` puts the checks in before the run's first request. Measured on 19.0.0 (`bridge-credit-spend-stock.test.ts`, "an omp -p run beside the sessions"): off sends a spent ChatGPT account with credits nothing and the run ends on the refusal, on sends it. Pinned by `omp-launch.test.ts` (only `-p` gets the flags, the switch read at each run) and `schedules.test.ts` (a run's argv and env).
  - **Memory's own model calls** are omps the core starts: the upkeep's and the curation's `omp -p --no-extensions` (`native/ompdesk/crates/core/src/upkeep/model.rs` `run_smol`, also the cheap-model judge of `care/judge.rs`) and the memory judge's host (`care/judge.rs` `run_host`, `omp --mode rpc -e memory-judge-host.ts`). Main hands the core how omp starts once (`ai-memory/core-asks.ts` `ompLaunchOf`, `OmpLaunch {bin, env, args}`), so the switch goes there: `configureModelRuns` (set in `index.ts`) adds `creditSpendRun`'s `-e credit-spend-run.ts` as `args` and `OMP_GUI_CREDIT_SPEND` to `env`, read at each launch, and the core puts `args` right after `-p` (before the host's own `-e`, so the check's hooks are in place first). The host never runs a turn, so credit-spend.ts also applies at `session_start`. An explicit `-e` stays loaded under `--no-extensions`. Measured on 19.0.0: the upkeep's exact arguments off send a spent account nothing; an omp that loads the check alone and asks one model after `session_start` sends nothing. Pinned by the core's `upkeep::model` test (argv), `ai-memory/core-asks.test.ts` and the stock test.
  - **The commit-message button** runs stock `omp commit --dry-run` (`local/git/scm.ts`), which takes no `-e` and builds its own `AuthStorage` with no extension hook (`commands/commit.ts` flags, `commit/pipeline.ts`: `discoverAuthStorage`, `new ModelRegistry`), so nothing can ride along. With the switch off the tab's omp, which carries the checks, is asked first (`withCreditSpendRuns` → gui-bridge `credit_spend_commit_check`): it picks the models that run will pick with stock's own selection (`commit/model-selection.ts` `resolvePrimaryModel`, `resolveSmolModel`) and resolves each key through the checks. A refusal, or a check that could not run (an omp too old, a bridge that is gone), ends the press before `omp commit` starts, with one line saying why (`CreditSpendRefusal` → code `credit_spend_off`, `ipcError.credit_spend_off`); the person can still write the message. With plan left the run goes as before, unpinned (the same selection in the same agent directory; stock ranks an account with plan left ahead of one running on credits, measured for the sibling case above). On: never asked. Why not refuse outright: the button would be dead for everyone at the default. Why not a guarded `omp -p` with a prompt of our own: a second commit pipeline beside stock's. - **A todo list from earlier work** (`resources/gui-bridge/todo-stale.ts`, text `todo-stale-core.ts`, capability `todoStale`). New requests add to unfinished work; they do not cancel it.
  - At the start of a turn a new request opens (`before_agent_start`, main agent only, `todo` active, not an Autopilot run), `todoStaleness` reads the journal with stock's `tools/todo` `getLatestTodoPhasesFromEntries` and `getLatestTodoSnapshotIdentity`: stale when every item is done or dropped (at once), or items are open and a whole earlier request went by after the list's last change (`UNTOUCHED_REQUESTS` 1).
  - One hidden custom message (`ompdesk-todo-stale`, `display: false`) names the phases and done/total. For a finished list, it suggests `init` for new work.   - A question or an acknowledgement never gets it (`isNewRequest`, the one rule the panel's received instructions below use too). - **Do not reset unfinished work** (`resources/gui-bridge/todo-compact.ts`, capability `todoCompact`). Stock 19.1.0 `todo init` creates new tasks from their text. Even identical text does not preserve status. With synthetic `blocked` and `in_progress` tasks in that order, `init` changed their statuses to `in_progress` and `pending`. Stock also infers `init` from a nonempty `list` with no `op`.
  - The `tool_call` hook checks the calling agent's live `getTodoPhases()` before either form can run. Empty lists and lists containing only `completed` or `abandoned` tasks can be replaced. Otherwise the agent must `append` in a named phase or explicitly transition individual items. An unreadable list is not safe to reset. Other agents' lists never enter the decision.
  - Stock checks an entire response's tool calls before executing any. An `init` cannot overlap another pending todo mutation of the same agent; an unrelated tool or a `view` can still run beside it. The bridge retains call IDs only until the result or the end of the turn. Stock owns all task state.
  - After an `append` leaves more than 20 items with at least 10 finished, `tool_result` adds a reminder to keep history and append new requests by phase. The panel can collapse phases without changing their tasks. Never rebuild a live list to shorten it or re-block rows afterward. Stock 19.1.0 no longer accepts `block` and reads a persisted legacy `blocked` row as `pending`; the bridge does not change that stock migration.

  - **What counts as a received instruction** (`isNewRequest`, todo-stale-core; the stale-list reminder above uses the same function): a user message that is not synthetic or agent-attributed, at a turn's start or steered in, that is another session's message (`<ompdesk-agent-message>`, a hub's steer to its worker, at any length) or a person's request. Code rule, no model call, no length cut, because short Korean orders carry the whole task ("배포 중단", "되돌려", "푸시해", "탭 닫아" count; the hub's report, 20 Nov 2026). Left out only:
    - a `/`, `!` or `$` command; a single character, or text with no letter or digit;
    - a message made only of acknowledgement words (`ACK_WORD`: 응, 네, 예, ㅇㅇ, 좋아, 그래, 고마워, 계속, 진행해, ok, yes, go on, continue, thanks and the like, with spaces, punctuation, symbols or ㅋㅎ between and after them). "계속 진행해 주세요" and "Continue please." are such a message and do not count; a listed word beside any unlisted one ("계속 배포해", "ok, now revert it") counts;
    - a question: a trailing `?`, a Korean question ending (not `죠`, since "푸시하죠" proposes the work) or a question word first (English only `what which where why how who whose`; "do …", "have …" are as often orders), unless it holds a request word (`줄래`, `고쳐`, `can you`, `please`) or presses for work not done (`PUSH_CUE`: `아직 안`, `안 했`/`못 했` and kin, `n't`, `yet`), so "왜 아직 안 했어?" and "Did you push yet?" count while "why did the build fail?" and "아직 빌드 중이야?" do not. Questions stay out because counting one nudges the agent to give it a todo row and makes it pad its list; the push cue catches the questions that are orders.
